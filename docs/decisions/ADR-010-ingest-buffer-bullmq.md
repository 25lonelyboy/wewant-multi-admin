# ADR-010 接入层缓冲：BullMQ 作为平台消息缓冲

## 背景

[ADR-009](ADR-009-iot-platform-p1-stack.md) 已定 P1 的 Broker（EMQX）与遥测存储（TDengine），但**接入与存储之间是否加缓冲层、用什么**未决。这份决策把它定下来。

一个必须先纠正的认知：**MQTT Broker 自带的队列 ≠ 平台的缓冲层**。EMQX 的队列是对**每个订阅者的投递保证**（QoS、会话持久化、离线消息），作用域是单连接/单会话；平台的缓冲层解决的是另一类问题——**跨组件的解耦、多消费者、重放**。因此"已经有了 EMQX 为什么还要消息队列"不成立，两者不是同一层的东西。

本仓库自身的规划里，BullMQ 已经是既定组件而非候选：`backlog.md`「Redis 键空间已为 BullMQ 预留」／「第二个外部中间件适配器（BullMQ / 对象存储等）引入」是 `common/ → src/infra/` 二分的触发条件／「第二运行时依赖（BullMQ）」是 server 冒烟生产级演进的信号之一；`backend-evolution.md` F 阶段含「BullMQ 事件化」。P1 的"工程级"定义（标准协议、**真实中间件**、可靠性工程、可观测性、压测报告）也要求这一层真实存在。

## 决策

### D1 引入缓冲层，选 BullMQ

在接入与存储之间加消息缓冲，实现选 **BullMQ**（Redis 基）：

- **复用栈内既有客户端**：本仓库已用 `ioredis@^6.0.0`，满足 BullMQ 的 peer 要求（≥5），不引入新的 Redis 客户端
- **作业语义完整**：重试、退避、延迟、并发控制、优先级开箱可用——这些是"自己写一个 Streams 消费循环"要反复补的部分
- **许可与许可无关**：MIT；版本 6.3.11（2026-10-01）
- **可观测性现成**：Dashboard 与 OpenTelemetry 集成（`bullmq-otel`）可直接接入增量 6 的观测项

### D2 链路位置

```
设备/模拟器 → EMQX →（iot 域订阅）→ BullMQ →（消费者 worker）→ TDengine
                                                     ↘（未来）告警、AI 异常检测、冷数据归档各自加消费者
```

**消费者独立于接入**：新增一个消费者不需要动接入层代码——这是本决策最核心的收益。

### D3 做它的理由（写清楚，避免"为了加而加"）

1. **解耦**：将来新增消费者（增量 5 的告警、P3 的 AI 异常检测、归档任务）**不改接入层**
2. **可靠消费**：消费端崩溃时消息仍在队列，可重放、可重试——直写存储做不到
3. **接入层不被下游拖慢**：先收下、尽快确认，下游处理速度不反压设备侧

**不把"削峰"当作 P1 的理由**：百级设备量下削峰体现不出来，拿它当论据是空话。削峰的真实证据要到增量 6 的压测才出现——**那时才是它的证据时刻**。

### D4 队列与业务缓存不共用连接语义

e2e 套件会用 `flushdb` 重置限流计数（见 `apps/nestjs-server/AGENTS.md` 的 e2e 隔离规范）。若队列与限流缓存落在同一 Redis 实例的同一 DB，`flushdb` 会把队列状态一并清掉，造成测试间的隐藏耦合。

**方向**：P1 为队列起**独立 Redis 实例**（compose 新增一个服务），或至少独立 DB index；**倾向独立实例**——BullMQ 不推荐依赖 DB index 做隔离，且与限流缓存分实例后语义更干净。最终形态在增量 2 落地时确认，此处只锁方向。

### D5 依赖落位

`bullmq` 只被 `apps/nestjs-server` 消费，**不满足 catalog 判据**（≥2 个 workspace 消费 / 框架级 / 刻意固定版本），因此**留在应用本地 `package.json`**，不进根 catalog（遵循仓库既有依赖规则）。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| **不加缓冲，订阅后直写 TDengine** | 与仓库既定路线冲突（BullMQ 已三处预留）；接入层被下游速度反压；新增消费者必须改接入层；消费端崩溃即丢数据 |
| **Kafka** | 能力更全（分区、持久化、生态），但运维与资源成本与 P1 规模不匹配；留作增量 6 万级压测后的评估项——有压测数据再谈才有依据 |
| **EMQX 规则引擎 / 数据桥直写存储** | 把平台逻辑塞进 Broker，绕过 iot 域（平台的核心业务逻辑所在）；可控性与可讲性都差，且换 Broker 就要重写业务逻辑 |
| **RabbitMQ** | 死信与路由能力更强，但要新增一个独立中间件；Redis 已在栈内、ioredis 已就位，P1 复用更省 |
| **Redis Streams 原生** | 更轻、无额外依赖，但缺作业管理（重试/退避/延迟/并发/面板），等于自己实现半个 BullMQ |
| **用 EMQX 的会话队列当缓冲** | 概念错位：那是投递保证，不解决平台内部的解耦与重放（见背景） |

## 影响

- `apps/nestjs-server` 新增运行时依赖 `bullmq`（应用本地，不进 catalog）。
- **触发两条既有 backlog 条目**：`common/ → src/infra/` 二分（"第二个外部中间件适配器引入"这一触发条件已满足）；「server 冒烟生产级演进」（"第二运行时依赖"信号已出现）。
- **compose 可能新增一个队列专用 Redis 实例**——若落地，则 `ops/check-digests.sh` 中写死的预期 pin 数量（当前为 10）需同步更新，镜像沿用 digest pin 约定。
- **消费者扩展模式**：增量 5 的告警、P3 的 AI 异常检测按"新增消费者不改接入层"的方式接入——这条收益要在增量 5 真实兑现一次，才算验证过。
- **可观测项**：队列深度、失败率、重试率进入增量 6 的指标清单（BullMQ 自带 OTel 集成）。
- 实施细节（队列命名、遥测消息信封、重试与死信策略、worker 部署形态）写入 `docs/architecture/` 与增量 2 的任务目录，本 ADR 不承载。
