# ADR-007 后端演进方向：长期模块化单体 + 终态微服务的分段路线

## 背景

nestjs-server 已完成基架（P1-P5）、Tier 1 速赢与 Tier 2 安全/冒烟主题，backlog 沉淀了约 28 条待处置项。需要以企业级最佳实践为长期目标，明确宏观演进路径：当前处于什么位置、后续如何一步步演进、各阶段满足什么条件后触发。经讨论确认方向性决策 D1-D4 与两项范围性决策。

## 决策

1. **D1 架构路线**：长期维持**模块化单体**，终态为按域抽取的**微服务**。单体期通过限界上下文纪律、查询门面、contracts 先行、观测先行压低未来抽取成本；微服务化在抽取触发信号（见架构文档）出现前不启动。
2. **D2 可观测性**：基于**开源自建栈**（prom-client + Prometheus/Grafana + Loki + OTel 追踪 + Alertmanager），不采用云厂商托管监控。因 D1 终态微服务，OTel 追踪升级为「服务抽取前必备」，与日志/指标三件套统一落地。
3. **D3 制品与部署**：后期**自建 registry**（Harbor 类）；部署形态 VM docker 起步、K8s 或裸机 VM 均可能。OCI 镜像兼容两者，现有 Dockerfile 无需返工。
4. **D4 近期部署意向**：短期可能在 VM 以 docker 形态部署试点，时间点未定；因此阶段 A（生产部署前必备包）是最近的下一站。
5. **阶段 A 范围性决策**：
   - 审计日志基础版范围：登录事件（成功/失败/锁定）+ 管理员敏感操作（改权限、软删除、重置密码、改密）；业务全量审计待监控域立项再扩。
   - 备份形态：pg_dump 定时 + 副本异地/异盘存放 + 恢复演练脚本（轻量）；不引入 pgBackRest 类重型方案（K8s 或数据规模化时再评估）。
   - 供应链加固：Renovate 走**公有 GitHub App**（安装 + `.renovaterc.json` 配置，工时 ≈ 0）；Trivy **入 CI 报警式**（docker-build job 加一步扫描 + 漏洞库缓存，工时 ≈ 半天）。check-digests 季度刷新脚本在 Renovate 落地后退役。
6. **演进阶段框架**：A 生产前必备包 / B 观测闭环 / C 规模化 / D 第二域扩展 / E 协作与 CD / F 服务抽取，每阶段由现实信号触发而非时间表（详见 `docs/architecture/backend-evolution.md`）。

## 被否决的替代方案

| 方案 | 否决理由 |
| --- | --- |
| 现在启动微服务化 | 五表 RBAC 规模下分布式事务、服务发现等成本无回报，属纯负资产 |
| 观测栈采用云厂商托管监控 | 与开源自建路线不符，引入厂商绑定 |
| 审计日志一次做全量 | 业务域未立项，全量审计必然返工 |
| 引入 pgBackRest 类重型备份 | VM 单机试点阶段过度设计 |

## 影响

- 新增 `docs/architecture/backend-evolution.md`：目标图景、当前定位、阶段路线与触发条件、微服务抽取铺路约束。
- backlog 条目细化：供应链加固（Renovate/Trivy 形态）、CD 制品策略（自建 registry + VM 优先）、OpenTelemetry（追踪为抽取前必备）、审计日志（基础版范围）、数据库备份（轻量形态）。
- 阶段 A 立项时按本文档确认的范围执行，无需重新讨论。
