# IoT 平台 P1 阶段地图

这张图是 P1 的「总」：**能力层 × 增量阶段**。任何单项决策必须挂到下面某一格；挂不上即不属于本期。单格内的细节不进本图，落在对应的 `docs/tasks/` 与 ADR 里。

## 1. 能力层

| 能力层 | 现在有什么 | P1 结束时的形态 | 缺口 |
| --- | --- | --- | --- |
| **接入** | EMQX 6.3.1 单节点（1883 与 Dashboard 仅绑回环，无认证 / 无 TLS）；模拟器 100 台（5.0 / 3.1.1 各半）；订阅端通配订阅 + 身份校验 + 投队列 + 本地落盘兜底 | 保持单节点、只上行 | 无认证 / TLS；无下行通道（校时、改配置、重注册）；单实例 |
| **存储** | 四个实例：业务缓存 Redis、队列 Redis（`noeviction` + `appendonly`）、PG（状态）、TDengine 两库（`wewant_iot` 原始 + `wewant_iot_ds` 降采样）；原始超表 `telemetry` + 100 子表，降采样三级超表 + 300 子表 | 原始 3 年 / 分钟级 3 年 / 库级 10 年；预建子表 = 已注册 | 子表只增不减（现原始 100 / 降采样 300，均与注册表对齐，审计可核；e2e 已自清残留）；备份无自动化；压缩比与容量未实测 |
| **计算** | `apps/iot-worker`：消费环（攒批 500 条 / 2 s、批内去重、STMT1 逐子表写入、A/B 分类、2 槽连接池）+ 降采样环（BullMQ Job Scheduler 三级平级，每次重算最近 K 个已闭合窗口） | 消费延迟秒级内；降采样逐条对账干净 | 单实例；K 之外的自愈盲区；未登记子表致整级失败；每子表一条语句的规模上限未压测 |
| **查询** | 无（只有 TDengine SQL 与对账脚本） | REST 查询 + WebSocket 推送 | 整层未开始；契约、鉴权、分页与聚合口径、时区 / 业务日规则 |
| **应用** | pure-web 无 iot 视图 | 设备列表 / 详情 / 实时曲线 | 整层未开始 |
| **运维** | pino 结构化日志；compose 健康检查覆盖 postgres / redis / redis-queue / emqx / tdengine / server / worker（worker 以 Redis 心跳键判活，卡死可被 `docker ps` 看出） | 指标出口 + 压测报告 + 混沌演练记录 | 无指标出口；告警只落日志、无接收方；无规模压测；无备份 / 恢复剧本 |
| **治理** | `packages/contracts`（主题 / 载荷 / 队列名）、`packages/device-registry`（静态 100 台单点）、ADR-009 / 010、`doc:lint`、全局 backlog | 物模型三元组 + 可注册的档案 | 档案静态；物模型未建立 |

## 3. 接缝（跨层，无单格归属）

增量 2 的实测教训：跨两个分项的约束**没有任何一格负责**，直到写代码才撞上（子表名跨超表唯一，`1565`）。P1 内已知的接缝：

| 接缝 | 涉及 | 归属增量 | 现状 |
| --- | --- | --- | --- |
| 档案 ↔ 子表预建 | 治理 × 存储 | 3 | 增量 2 定名 `{deviceId}_{pointKey}` / DS 加 `_{level}`，「表存在 ⇔ 已注册」靠预建保证；**注册流程必须同事务建子表**，否则不变量断 |
| 物模型 ↔ 单位与量纲 | 治理 × 存储 | 3 | 单位随行落库、降采样取窗口内最后一次；测点单位变更的处置未定 |
| 物模型 ↔ 告警规则 | 治理 × 计算 | 5 | 阈值挂物模型属性还是挂设备实例，未定 |
| 查询契约 ↔ 推送 | 查询 × 应用 | 4 | REST 与 WebSocket 共用一套 DTO，未定 |
| 降采样粒度 ↔ 看板 | 计算 × 应用 | 4/6 | 曲线读原始还是 `telemetry_1m`、缩放时怎么切级，未定 |
| 设备注销 ↔ 子表清理 | 治理 × 存储 | 3 | 只读审计已落地（表存在 ⇔ 已注册，四桶，任一非空退出 1）；**审计工具无删除路径**，删除分别由开发环境重建库与注销流程承担；子表仍只增不减 |
| 压测规模 ↔ 连接与会话上限 | 运维 × 存储 | 6 | 每 worker 实例 2 条 TDengine 连接；服务端会话上限（`0x80000022`）未标定 |

## 4. 行业成熟形态对照（只写差异）

| 成熟平台有的 | P1 有 | 差异的代价 | 何时补 |
| --- | --- | --- | --- |
| 设备影子 / 期望状态（AWS IoT Device Shadow 【已核实：AWS 官方文档】） | 无下行通道 | 断线期间的命令与状态对账做不了 | P1 之后 |
| 物模型版本化与迁移 | 增量 3 只做最小三元组 | 属性改定义后历史不可解释 | 增量 3 立项时定版本策略 |
| 多租户隔离 | 不做 | 单组织使用 | 不做 |
| OTA / 边缘网关 | 不做 | 设备升级与本地自治靠人工 | 不做 |
| 时序查询服务（聚合 DSL） | 增量 4 的最小 REST | 复杂聚合由前端或人工 SQL 承担 | 增量 4 |

【AI 判断，待验证】上表「差异的代价」列是按本仓现状推的，未与任何具体产品逐项对照。

## 5. 基线

- **本基线自 2026-11-01 生效**：整体顺延 13 天，各增量时长不变。
- 增量 2 于 2026-10-31 完成（原窗口 10/06–10/19）；增量 3 自 11/02 起。
- 新窗口：3 → 11/02–11/15；4 → 11/16–11/29；5 → 11/30–12/06（M2）；6 → 12/07–12/27；7 → 12/28–2027-01-10（M3）。
- 该基线按「每周 8–10 小时、每增量 2 周」排定。增量 3 若超窗，沿用原计划的风险杠杆口径：**宁砍范围、不拖里程碑**。

## 6. 本期不做

多租户、OTA、边缘网关、可视化告警编排、AI 特性层（异常检测 / 自然语言问数 / 根因摘要 / 手册 RAG）——均属 P2 及以后。
