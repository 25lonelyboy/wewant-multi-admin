# D1 前置材料 · 档案承载与 worker 读取形态

- **日期**：2026-11-06｜服务于 S5（消费与降采样接线）
- **状态**：前置材料，结论已收口于 [D1 决策卡](2026-11-07-d1-decision-card.md)（2026-11-07）
- **不重开**：D2（模型 → 超表）、D3（注册原子性）、D4（时间戳与报文上限）已定；本页只问**worker 从哪里、以什么形态读到档案与模型**
- **按轴自检**：第八节是脚手架，先由决策人按轴过一遍、写下「本增量必须现在定」的项，AI 再补漏

## 1. 这个决策锁死什么

| 项 | 定错的代价 |
| --- | --- |
| worker 的进程依赖 | 定了直连就多一个 PG 连接池与 Prisma schema 依赖；两个应用对同一张表各有一份理解，改表时不会报错 |
| 「生效」的时延口径 | 判据 A 只说「不重启」，没说多久。没定口径，验收时无法判定通过与否 |
| 多实例的一致性 | worker 可多实例（增量 2 的设计前提）。形态若带进程内状态，实例间会答出不同结果 |
| 失效与回退 | 档案改错时怎么撤回；读不到档案时的行为（丢弃 / 沿用上一次 / 停摆） |

## 2. 四个本仓事实（2026-11-06 核对）

1. **worker 读的是编译期常量**：`apps/iot-worker/src/consumer.ts:72` 的 `new ResolveCache(p1DeviceRegistry, CACHE_TTL_MS)`，`p1DeviceRegistry` 是 `packages/device-registry` 里的模块级常量，由 `p1DeviceRecords()` 构造。**档案变了只能重新构建并重启**。
2. **缓存连负结果一起缓存**：`ResolveCache`（`registry-cache.ts`）把 `unknown-device` 也存进 Map，TTL 5 分钟（`consumer.ts:23`）。即使档案来源变成动态的，**一台已经上报过、当时查档失败的设备，最多要等 5 分钟才会被重新查**。判据 A 的「不重启」因此还有一个隐含的等待上界，必须在 S5 里显式定。
3. **降采样环也读同一个常量**：`downsample/ring.ts:79` 的 `registryModelCodes()` 从 `p1DeviceRegistry.allSubtables()` 取模型编码去重。新注册的模型**不进降采样环**，同样要重启。
4. **worker 只有队列 Redis**：`config.ts` 里只有 `QUEUE_REDIS_URL`，没有业务缓存 `REDIS_URL`。而 AGENTS.md 明写队列 Redis 与业务缓存是**两个实例**（BullMQ 要求 `noeviction`，那是实例级配置）。任何走 Redis 的形态都要先答「放哪个实例」。

补充两条与接口相关的既有约定：

- `DeviceRegistry` 的三个方法（`hasDevice` / `resolve` / `allSubtables`）是**同步**的。S2 因此没有实现它，只做了异步的 `DeviceRegistryRepository`。D1 若选直连或服务，**这个同步签名必须改**，改它就等于动了 S2 说的「接口一字不动」。
- 范围定稿 §2 把遗产「`iot-worker` 不碰 PG」**重估**为「worker 不与 PG schema 耦合」——注意后者松一档：碰到 PG 可以，**耦合 schema 不行**。

## 3. 判据 A 拆成可验条件

判据原文：「注册一条档案 + 一个物模型（纯数据），**不重启 worker** 即可查档成功、落库到新子表」（[README](README.md) §1）。

拆开看，它其实要求四件事同时成立：

| # | 条件 | 今天卡在哪 |
| --- | --- | --- |
| A1 | 新档案能被 worker 看到 | 档案是编译期常量 |
| A2 | 看到之后能查到子表名 | 同上 |
| A3 | 新模型能被降采样环看到 | `registryModelCodes()` 读同一个常量 |
| A4 | 「不重启」的时延可判定 | 没有口径；且负结果缓存 5 分钟会掩盖真实时延 |

A1–A3 是同一件事的三个读者（消费环查档、消费环写入、降采样环枚举）。**它们必须走同一个来源**，否则会出现「查档成功了但降采样环还在算旧模型」这种半生效状态。

A4 是本页最容易被跳过的一项。三种形态的时延特征完全不同：直连是请求即时、快照是刷新间隔、服务是请求即时但可能被缓存。**没定口径，验收只能各说各话。**

## 4. 三种形态

三种都能满足 A1–A3。下面是机制与它把什么定死——**不是推荐**。

### 4.1 直连：worker 自己连 PG

worker 新增一个 PG 连接池与只读查询，自己查 `IotDevice` / `IotDeviceModelUsage` / `IotModelVersion`。

- **它把什么定死**：worker 对 PG 表结构的直接依赖。加一列、改个字段名，worker 要跟着改，且**编译期发现不了**（SQL 是字符串）
- **时延**：请求即时，只受缓存策略影响
- **多实例**：天然一致（都查同一个库）
- **代价**：两个应用各持一个连接池；「不与 PG schema 耦合」这条目标直接放弃；worker 的部署多了 DATABASE_URL 与迁移时机的耦合（worker 镜像启动时库可能还没迁移）
- **可撤回性**：改档案立刻生效（配合缓存失效）

### 4.2 快照：server 发布，worker 全量拉取

server 在注册成功后把「全部 ACTIVE 档案 + 模型声明」写成一份带版本号的快照（Redis key 或 PG 里一张快照表），worker 定期拉取、整份替换内存。

- **它把什么定死**：快照的结构就是一个**跨应用的契约**——它进 `packages/contracts` 还是留在 `device-registry`，是一个包边界问题
- **时延**：刷新间隔本身就是 A4 的答案（比如 30 秒）
- **多实例**：一致（都拉同一份）
- **代价**：全量拉取在万级设备下的体积；快照与 PG 之间需要保证「发布」的原子性（发布到一半不能让人拉到半份）；Redis 放哪个实例要先定
- **可撤回性**：改档案后要重新发布快照

### 4.3 服务：worker 调 server 的内部接口

server 暴露一个内部读接口（如 `GET /internal/iot/registry?since=...`），worker 定时拉或按需查。

- **它把什么定死**：server 成为运行期依赖——worker 的可启动性从此与 server 绑定（今天 worker 与 server 并列独立启停）
- **时延**：请求即时；但服务不可用时 worker 怎么办，是必须答的问题
- **多实例**：一致
- **代价**：多一跳网络；server 挂掉时 worker 的数据通路要不要停；接口的鉴权（内部接口 ≠ 公开接口，但仍在同一个 HTTP 端口上）
- **可撤回性**：改档案后立刻可读

## 5. 五处必须先答的子问题

1. **A4 的口径**：判据 A 的「不重启」，允许的时延上界是多少？负结果缓存（5 分钟）要不要一并改？
2. **三个读者是否同源**：消费环的查档、写入、降采样环的模型枚举，是否强制走同一个来源与同一次刷新？
3. **读不到档案时的行为**：丢弃并计数（今天的行为）、沿用上一次的值、还是停摆？三种形态下这个答案不同。
4. **失效与回退**：档案改错后怎么撤回？形态若带版本号，「回退到上一版」是回收旧快照还是重新发布。
5. **模型的读法与档案是否同一个通道**：S5 还要读模型声明（量程、聚合集、列类型）。若两者走不同的通道，就要维护两套刷新逻辑。

## 6. 与其他决策的接缝

- **与 D5（注销口径）**：档案被注销后，worker 什么时候停止接受该设备的数据？这取决于本决策选定的时延特征。
- **与 D3（审计只认 ACTIVE）**：三种形态都只应读到 `ACTIVE`，但「只认 ACTIVE」发生在 server 侧（发布时过滤）还是 worker 侧（拉取时过滤），决定了脏数据能不能漏进去。
- **与 S2 的 `DeviceRegistryRepository`**：它现在是 server 侧的只读仓储、异步。若选直连，worker 不该复用它（跨进程）；若选快照或服务，它的返回结构就是快照 / 接口形状的起点。

## 7. 三种形态对判据 A 的逐条对照

| | A1 看得到 | A2 查得到 | A3 降采样看得到 | A4 时延 |
| --- | --- | --- | --- | --- |
| 直连 | ✅ 改库即见 | ✅ | ✅ 同一查询 | 即时，受缓存影响 |
| 快照 | ✅ 下次刷新 | ✅ 同左 | ✅ 同左 | = 刷新间隔 |
| 服务 | ✅ 下次拉取 | ✅ 同左 | ✅ 同左 | = 轮询间隔 |

三种都能成立。差别不在「能不能」，在**代价落在谁身上**：直连把依赖压在 worker 与 schema 上，快照压在契约与体积上，服务压在可用性上。

## 8. 按轴自检（决策人先填，AI 后补）

### 8.1 先纠正轴集本身

原始出处是知识库 `iot-learning/增量1-验收复盘（MQTT 设备接入）` 第八节，那里是**两条判据 + 九条轴**，不是八条：

- **两条判据**（判该不该现在定）：① 会不会落到设备上 ② 定了之后有没有东西长在上面（历史数据 / 外部依赖 / 现场固化）
- **九条轴**（分四组，判还有哪些没意识到的决定）：数据面 3（数据生命周期、单位与量纲、幂等键）、容量成本 2（容量模型与失效点、成本曲线）、业务面 3（业务倒推、现场的「脏」是设计输入、数据可信度与责任边界）、交付面 1（上线与割接）

决策卡仪式里用的八条是压缩版：2 判据 + 6 轴，**压掉的是「现场的脏」「数据可信度」「上线与割接」**。对 D1 来说，被压掉的那三条里至少有一条比留下的三条更相关（见 8.3）。

### 8.2 逐条量 D1

| 轴 | 对 D1 是否咬人 | 落到哪个子问题 |
| --- | --- | --- |
| **判据一** 会不会落到设备上 | **否，而且是否得干净** | 设备只报 `localDeviceId`，平台侧标识从不下发（S0.5）。D1 全在平台内部代码里 |
| **判据二** 有没有东西长在上面 | **是，但形态弱** | 不长历史数据、不固化现场；长的是**一份跨应用契约**——快照格式或接口形状一旦定下，S5 与将来的告警、AI 特性都按它写 |
| 数据生命周期 | **不适用** | 档案是元数据，没有留存/降采样/删除问题。唯一沾边的是缓存条目 TTL 与淘汰，归到 ⑥ |
| 单位与量纲 | **不适用** | 已由 D2 §10 定（单位不可变、改单位=新建模型）。D1 只决定「从哪儿读」，不决定读到的内容怎么解释 |
| 幂等键 | **半适用，且要换问法** | 读本身天然幂等。真正要问的是**快照/响应的版本单调性**：worker 不能拿旧快照覆盖新快照。这是状态更新的幂等，不是数据重复 |
| 容量模型与失效点 | **最咬人的一条** | 万级设备下快照体积；`ResolveCache` 今天上限 10 万条、超了整体清空；第二个 PG 连接池的容量；Redis 挂在哪个实例（队列还是业务缓存） |
| 成本曲线 | **半适用** | 单机开发下成本都可忽略；有意义的是**边际成本随设备数怎么长**：直连 O(1)/次查询、快照 O(设备数)/次刷新、服务多一跳 |

### 8.3 建议补上的三条

| 轴 | 为什么对 D1 咬人 | 落到哪个子问题 |
| --- | --- | --- |
| **上线与割接**（原始九轴里有，压缩时被砍） | D1 要换掉 worker 的档案来源，这是**运行期切换**：怎么切、切到一半怎么办、怎么回滚。真实环境不允许停机部署，而 P1 现在没有割接设计 | 与 5.4「失效与回退」合并答 |
| **现场的「脏」**（原始九轴里有，压缩时被砍） | 档案读回来的可能是脏数据（S4 刚为 `deviceId` 加了 `checkDeviceId`）；设备会被换、会重注册。读法要能承受这些，而不是假设档案总是干净的 | 与 5.3「读不到档案时的行为」合并答 |
| **跨应用契约边界**（本仓特有，原始轴集没有） | 快照格式若跨应用流动，它进 `packages/contracts` 还是留在 `device-registry`，是一个包边界问题。`contracts.md` 明写「只放纯类型与常量，不放运行期逻辑」 | 决定形态的第一步就要答 |

### 8.4 一个结论：这次自检该快而浅

**判据一对 D1 给出的是「否」**——不落设备、全在平台代码里。按两条判据的逻辑，这意味 D1 是**可逆的、长期成本低的**决策：改错了重新发版就行，不像 D2 的列名那样一写进数据就收不回。

「该不该现在定」这个问题，D1 的答案是**由排期给的，不是由轴给的**——S5 就是接线，不先定就写不了。所以这次按轴自检的重点**不在「要不要现在定」，而在「运行期有哪些坑」**：容量、失效、割接、脏数据。

建议按这个顺序填：8.3 的三条 + ⑥ 容量与失效 → 得到四条必须现在答的；其余全部写「挂触发点」并给出触发条件。

## 9. 快照形态的推演（2026-11-07）

决策人提出的形态：worker 把常量化的物模型与档案全部改读持久化数据；server 在数据变更后刷新 Redis 全量快照；快照 Redis 与 BullMQ 队列分开实例；设备数与上报频率上来后考虑多级缓存。

即 §4.2 的快照形态，加一层本地全量缓存。方向成立。下面按会咬人的程度列尚未覆盖的点。

### 9.1 先纠正两处前提

**（1）worker 要读的不是「档案」，是三样东西。** 今天 `consumer.ts` / `detection.ts` / `writer.ts` / `downsample/*` 读五个常量，归成三类：

| 类别 | 常量 | 谁读 |
| --- | --- | --- |
| 档案映射 | `p1DeviceRegistry` | 消费环查档、降采样环枚举模型 |
| 模型属性集合与**绑定类型** | `RAW_METRICS` | detection 的已知测点集、writer 的 STMT 列绑定、降采样 query / rows / verify |
| 量程 | `DEFAULT_METRIC_RANGES` | detection 的越界丢弃 |

三者刷新频率差三个数量级：档案随设备注册，模型随版本发布，量程随模型。合成一份快照，意味着注册一台设备要重传全部模型声明与量程。

**（2）「每次从 Redis 拉取性能较差」这个前提在本形态下不成立。** 快照形态里 worker 不是每条报文查 Redis，而是本地持一份全量、定期比对版本号。Redis 单 GET 的吞吐（数万 QPS/实例）与本地 Map 的差别只在热路径多一次往返。**贵的不是「读几次」，是「每次读多少」**：一万台设备的档案 JSON 约 750 KB，加模型声明约 1 MB；每次刷新反序列化 1 MB 是几十毫秒，30 秒一次可忽略。

本地全量的理由不是吞吐，是 ① 报文处理路径不依赖 Redis 可用性；② 模型声明结构深、反序列化比档案映射贵得多，不宜逐条做。「多级缓存」若指「本地 LRU + Redis + PG」三层，对 P1 是过度设计；若指「本地全量 + 版本号轮询」，那就是正解——而它同时把 `ResolveCache` 取代掉了。

### 9.2 会让方案在当前形态下不成立的

| # | 缺口 | 后果 |
| --- | --- | --- |
| 1 | **绑定类型**：写入是 `INSERT INTO db.sub (a, b) VALUES (?, ?)`，按列名不按位置；但 `RAW_CODEC` 把每个测点硬编码成 `kind: 'float'`，而 `ColumnKind` 只有 `timestamp / float / double / bigint / varchar` | 布尔（BOOL）与枚举（INT）测点按 float 绑会写错或报错。快照必须携带每模型的**预推导列清单**（列名 + 绑定类型），由 server 推导、worker 只读 |
| 2 | **刷新失败没有兜底**：PG 提交成功、Redis 刷新失败 | 档案在库里 ACTIVE、worker 永远看不到，半生效且不自愈。须有定时全量重建（或刷新失败进重试） |
| 3 | **并发刷新会让快照回退**：两个请求各自全量重建 | 后写的可能读了更旧的 PG 快照。版本号必须单调递增，写入用条件更新（Lua / `WATCH`）拒绝旧版本 |
| 4 | **刷新与提交的先后** | 必须在 PG commit 之后、用新连接读；在事务内刷新会读到未提交数据，或刷新成功而事务回滚 |
| 5 | **冷启动**：worker 起来时快照不存在（首次部署、Redis flush、server 从未成功刷新过） | 今天是常量所以起得来。空转（丢弃全部报文）、起不来、还是降级，必须选一个 |

### 9.3 设计上会踩坑的

| # | 缺口 | 说明 |
| --- | --- | --- |
| 6 | **`ResolveCache` 去留** | 有了全量本地快照，`resolve` 就是一次 `Map.get`，TTL 层多余；但它今天还兼着负结果缓存。负结果要不要缓存、TTL 多长，属于 A4 口径 |
| 7 | **刷新挂在哪一层** | service 层还是接口层。D5 的注销、换型都会是新的写入口，挂错位置会漏刷 |
| 8 | **降采样环的模型集合** | `ring.ts` 构造时快照一次 `modelCodes`，注释明写「不要每 tick 重读——一次读取失败会变成静默停摆」。快照刷新后环要不要换集合？两个选择：重建调度，或每 tick 读**本地**快照（本地读不会失败，原顾虑随之消失） |
| 9 | **多实例下的降采样一致性** | 消费环一个 job 只被一个实例消费，不冲突；降采样环每个实例都跑，两个实例的本地快照版本不同 ⇒ 同一窗口算出不同模型集合，后写覆盖先写 |
| 10 | **快照格式的包边界与演进** | server ↔ worker 的契约，进 `packages/contracts` 还是留 `device-registry`；server 升级后老 worker 读到新结构怎么办（版本字段 + 不兼容即拒用） |
| 11 | **读不到时的三种情形要分开定** | 快照为空 / 设备不在快照里 / 快照过期，今天都归到 `unknown-device` 丢弃并计数 |

### 9.4 可以挂触发点的

- 快照体积超阈值时改按模型分片——触发点：单份超过一个量级（约 10 MB）
- 用 Pub/Sub 替代版本号轮询——触发点：A4 口径要求亚秒级可见
- 快照格式的向后兼容层——触发点：server 与 worker 不再同版本发布

### 9.5 现在必须答的四条

1. **内容边界**：一份全量，还是档案 / 模型两份（或三份：档案 / 模型声明 / 量程）
2. **A4 口径**：注册成功到 worker 可见，允许多久；负结果缓存怎么算
3. **刷新兜底**：定时重建的间隔，或失败重试策略
4. **`ResolveCache`**：删掉，还是保留作为负结果层

其余按 §9.4 写触发点。这四条答完，§8.5 的十一行即可一次性填完——它们决定 ② ⑤ ⑥ ⑨ ⑩ 的取值。
