# D5 前置材料 · 注销口径与遗产清理

- **用途**：[D5 决策卡](2026-11-01-scope-and-task-map.md) 的项级背景。只给约束与候选空间，**不替决策人选题**
- **日期**：2026-11-07
- **上承**：范围定稿 §3——D5 锁「注销后的删除路径」与「同毫秒冲突」，必须在 **S6 开工前**定
- **不重开**：D1（快照口径与按 ts 判定）、D2 §11（版本快照、列只增不减）、D3（注册原子性、失败清理只删本次建的表）、D4（时间戳边界与拒收）

## 1. 问题是什么

注销（以及同一族的改期、撤销、换型号）要同时回答四件事：

1. **档案上留什么**：状态位、usage 右边界，还是删行
2. **数据与表留不留**：原始子表、降采样子表、已写入的行
3. **设备再回来怎么办**：返修、换新机、改挂型号
4. **快照里怎么表达**：D1 之后消费、降采样、审计三条链路**只读快照**，注销若不在快照里表达，另外三处就只能靠猜

前三件在增量 2 就有雏形，第四件是 D1 带来的新约束——今天没有任何一处按"档案被注销"分支。

## 2. 本仓的八个事实

| # | 事实 | 位置 | 对 D5 的含义 |
| --- | --- | --- | --- |
| 1 | 设备状态只有 `PENDING` / `ACTIVE`，枚举注释明写「没有退役语义」 | `apps/nestjs-server/prisma/schema.prisma:100-104` | 注销要么加第三态，要么复用 `PENDING`，要么不动状态只关区间 |
| 2 | 判定口径由 usage 区间 `[fromAt, toAt)` 推出，`toAt` 已存在且被三处读取 | `snapshot.builder.ts:84-92`、`apps/iot-worker/src/resolve.ts:31-37`、`apps/iot-worker/src/subtables/audit.ts:26-40` | **关右边界就是「从此刻起不再接收」的天然表达**；但今天没有任何写路径会设置 `toAt` |
| 3 | 快照只收 `status='ACTIVE'` 的设备，且带其**全部** usage（含历史） | `snapshot.builder.ts:64-67` | 设备一旦不再是 `ACTIVE`，就从快照**整体消失**——消费记 `unknown-device`，审计期望集同时减少 |
| 4 | 审计期望集 = 快照 `devices[]` 展开的子表；任一桶非空退出 1，**工具本身无删除路径** | `audit.ts:26-40`、`apps/iot-worker/scripts/subtable-audit.ts:80-99` | 注销后若保留数据与表，审计必须仍把它们算作「已注册」，否则以后每次审计都红 |
| 5 | 降采样读原始超表 `PARTITION BY tbname`，**不查注册表**；写目标子表由 tbname 推 | `apps/iot-worker/src/downsample/query.ts:31-37`、`rows.ts:124-142` | 原始子表在、对应降采样子表缺失 ⇒ **该级整次重算失败**，爆炸半径是全级设备 |
| 6 | 注册失败清理已有删除原语：按清单**逆序** `DROP`、单表重试 3 次、仍失败留给审计 | `apps/nestjs-server/src/modules/iot/schema/execute.ts:25-55` | 注销删表可复用它；但它是**尽力而为**，不构成跨表原子 |
| 7 | 注册只有一个入口：`localDeviceId` 唯一、`deviceId` 永不复用；档案存在但不是 `ACTIVE` 时报 `device-not-active` | `apps/nestjs-server/src/modules/iot/devices/devices.service.ts:90-100`、`schema.prisma:140-141` | 注销后同一台设备回来必须有明确出口，否则现场只能换 `localDeviceId` |
| 8 | 批内同键是 **last-wins 静默**，只有 `duplicateInBatch` 计数 | `apps/iot-worker/src/consumer.ts:282-283`、`:349-355` | 「最后一条胜」由 `(子表, ts)` 覆盖语义决定；D5 只需定要不要把它升级为告警 |

补两条不占表格的：

- **模型永不删除**：没有删除模型的接口，降采样环按快照里的全部模型逐个重算。所有设备都注销后，模型、超表、空窗口重算都还在
- **DS 保留期是原始的约三倍**：原始 1095 天、降采样 3650 天。等自然过期意味着子表与降采样扫描面要背三年

## 3. 行业参照：Type 1 / Type 2

| 形态 | 机制 | 本仓对应 |
| --- | --- | --- |
| **Type 2**（保留历史版本） | 每段状态一行，区间表达起止 | `IotDeviceModelUsage` 已是这个形状；换型号产生第二行 |
| **Type 1**（就地覆盖） | 直接改字段，历史不可追溯 | 只适合**改正错误**，不适合表达「从此不再使用」 |

推论（【AI 判断】）：注销是**给 Type 2 行闭合右边界**，不是删行。这样「某时刻这台设备属于哪个模型」永远有答案，D1 的按 ts 判定也不需要额外的历史表。代价是行与表随历史增长，清理策略不能省。

## 4. 注销后会发生什么：逐链路推演

三种候选形态下，四条链路的表现：

| 形态 | PG | 快照 / 消费环 | 降采样 | 审计 |
| --- | --- | --- | --- | --- |
| **A. 加退役态 + 闭合 usage** | 设备行在，`status=RETIRED`，`usage.toAt=注销时刻` | 设备从快照整体消失 ⇒ 注销后的报文记 `unknown-device`；**注销前时段的晚到数据也一并被拒** | 表与数据在则照常算 | 全部子表进孤儿两桶（期望集不再含它） |
| **B. 不加状态，只闭合 usage** | 设备仍 `ACTIVE`，无 open usage | 设备仍在快照，区间闭合 ⇒ `ts ≥ toAt` 记 `out-of-range-ts`；`ts < toAt` 的晚到数据仍入库 | 同上 | 期望集不变，审计不红 |
| **C. 物理删档案与 usage** | 设备行、usage 删除 | 设备从快照消失 ⇒ `unknown-device` | 表若未删则可能整级失败（事实 5） | 表未删则孤儿 |

A 与 B 都能靠「额外把非 ACTIVE 设备也放进快照供审计」或「审计改读 PG」来消除审计红灯，但那分别是改 D1 的快照边界、或让审计重新依赖第二个数据源——**属于要一并表态的连带改动，不是免费的**。

### 4.1 晚到数据与注销时刻

按 D1 的口径，一条数据属于哪段区间只看**它自己的 `ts`**。于是 B 形态下，注销之后到达、但 `ts < toAt` 的报文**仍会入库**——它们是设备关闭前的合法历史。

这不是漏洞，是「按事件时间判定」的直接推论。若要连这类数据也拒，就得引入「到达时间」维度，那等于在热路径上把 D1 已经排除的处理时刻口径加回来。

【AI 判断】可选口径有两条，D5 要给一句：

- **封存历史**：`ts < toAt` 的数据永远接受，无论何时到达。语义干净，与 D1 一致；代价是注销后队列里残留的 job 仍会写进历史表
- **注销即断流**：注销后到达的一切都拒。需要「到达时间」或一个随快照下发的「已注销设备」集合，且要与 D1 的判定链路显式区分

## 5. 需要决策人回答的子问题

### 5.1 注销的形态

**要定什么**：加退役状态、只闭合 usage，还是物理删档案。

**只有你能答的部分**：注销后还需要在平台上**查到**这台设备吗（历史归属、对账、追责）？「`deviceId` 永不复用」这条已定约束，是否要求档案行永久存在作为凭据？如果注销的动机是「设备报废」，行留着只是多一条记录；如果动机是「数据合规要求删除」，行与数据都不能留。

### 5.2 数据与表的去留

**要定什么**：注销时删不删原始子表、降采样子表、已写入的行；不删的话留多久、谁来删。

候选（不排序）：

- **全部保留到 KEEP 自然过期**：原始 1095 天、DS 3650 天。审计口径要跟着改，且三年内降采样扫描面不缩小
- **注销即删**：审计归零、扫描面立刻收缩；代价是不可恢复，且删表是尽力而为（事实 6），中断会留半套
- **分级**：先关档停止接收，删表另给一条显式命令 / 接口，D5 只定顺序与安全边界

**只有你能答的部分**：注销的典型动机是「换机 / 报废」还是「合规删除」？前者可以不删，后者必须删。

### 5.3 删除的顺序与中断

**要定什么**：一套设备的 4 张表（原始 1 + 降采样 3）按什么顺序删；中断时残留成什么形状。

事实 5 是关键约束：**原始子表在、降采样子表缺**会让降采样整级失败——所以「先删原始、后删降采样」的中断态最危险；反过来「先删降采样、后删原始」的中断态同样会让降采样读到孤儿原始子表却写不进去。

三个可选口径（不排序）：

- 先删降采样、再删原始，残留表现为孤儿原始子表；要么清理脚本重试，要么让降采样读取侧按注册表裁剪（backlog 已记的候选）
- 先删原始、再删降采样，残留表现为孤儿降采样子表（审计能报，但降采样不会碰它）
- 只删到「审计能报」为止，物理删除交给单独脚本，用户确认名单后执行

### 5.4 再注册与换型号

**要定什么**：同一 `localDeviceId` 在注销后再注册，走哪条路。

候选（不排序）：

- **复活同一档案**：状态回 `ACTIVE`、重开 usage，沿用原 `deviceId` 与子表（表还在就直接用；表被删了就重建）
- **新建档案**：必须释放 `localDeviceId` 的唯一约束，或要求现场换标识；`deviceId` 重新签发
- **拒绝**：要求先人工处理，平台不提供自动路径

「换型号」是另一回事且已有既定口径：`deviceId` 不变、关闭旧 usage、开新 usage，旧模型子表合法保留（README §4 接缝 3）。D5 要定的只是**入口**——注册接口带不同 `modelCode` 时算换型，还是另开一个换型接口。

**只有你能答的部分**：现场「换新机」时 `localDeviceId` 会不会变？（它是设备自报编号，若写死在设备本体上，换机就变；若是贴在安装位置的编码，换机不变）

### 5.5 排期设备的改期与撤销

**要定什么**：`fromAt` 在未来、尚未生效的设备，能不能改期或整体撤销。

- **改期**：只在 `fromAt > now` 时允许；已生效的区间不能改（该时段的数据已按旧区间写入）
- **撤销**：子表已建、按区间定义不可能有数据 ⇒ 删表是安全的；删表失败残留成孤儿
- **入口**：直接改 usage 的 `fromAt`，还是「撤销 + 重发」（模型版本侧的既定做法）

**只有你能答的部分**：提前建单后「安装推迟」是否常见？若常见，改期要做得顺手；若罕见，撤销重发足够。

### 5.6 批内同键不同值

**要定什么**：同一 `(子表, ts)` 在**同一批**里出现两条不同值时，除了 last-wins 还要做什么。

今天的行为：静默保留最后一条，`duplicateInBatch` 计数 +1，不告警。语义依据是 TDengine 的 `(子表, ts)` 覆盖——无论应用层怎么处理，后写的都会覆盖先写的。

候选（不排序）：

- 维持现状：只计数，口径写成「同键覆盖是幂等语义」
- 计数 + 阈值告警：超过阈值说明设备固件在同一毫秒重复发不同值，值得看
- 只对「值不同」计数（现在是同键即去重，同值也计数）——能区分「重发」与「冲突」

**只有你能答的部分**：同一毫秒两个不同值在现场是固件 bug 还是正常重发？这决定它是需要人看的信号，还是可以忽略的噪声。

### 5.7 清理的执行者

**要定什么**：谁能发出「删除」这个动作。

既定：`subtable:audit` 保持只读、无删除路径。剩下的候选（不排序）：

- 删除只发生在注销 / 撤销接口内部
- 另给一条 dry-run 清理脚本（打印名单 → 人工确认 → 执行），审计工具仍只读
- 两者都要：接口负责按设备删，脚本负责清理历史残留（探针遗留、删表失败留下的孤儿）

**只有你能答的部分**：孤儿清理你希望「看到名单再决定」还是「自动跟随注销」？前者安全、要人；后者省事、会误删风险。

## 6. 定完之后，什么能证明定对了

1. 注销后该设备的上报不再入库，且落在一个**能区分原因**的桶里（不是与「设备不存在」混在一起）
2. 注销后 `subtable:audit` 的退出码符合所选口径（保留数据退出 0；删除数据后归零）
3. 同一台设备返修回来，不需要手工改库就能走通所选路径
4. 排期设备改期后按新区间判定，改期前已生效时段的数据不受影响
5. 删表中途中断，残留能被审计认领，且**不会让降采样某一级失败**
6. 批内同键冲突有可观测的量，且口径写明「最后一条胜」

### 8.2 轴外补充：注销与模型版本撤销的对称性

模型版本撤销（S5 已实现）与本页要定的设备注销是同一组动作的两个对象：

| 动作 | 模型版本（已定） | 设备（待定） |
| --- | --- | --- |
| 撤销的边界 | 只撤 `effectiveFrom > now` | 只撤 / 只改 `fromAt > now`？ |
| 撤销时回填前驱 | 前驱 `effectiveTo = null` 并恢复 `ACTIVE` | 设备没有"前驱"，只有「已注销」与「在册」 |
| 引用怎么处理 | 同事务把 `usage.version` 置空 | 无引用可置空 |
| 物理删除 | 只删版本行，不删列 | 删不删表是 5.2 的题 |

对称的部分（只撤未生效、事务内处理引用）建议直接沿用；不对称的部分（表删不删、档案留不留）是本页真正的决策面。
