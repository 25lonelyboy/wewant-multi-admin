## 0. 这个决策锁死什么

三样不可逆，且都必须在写第一行数据之前定：

| 不可逆项 | 定错的代价 |
| --- | --- |
| **列名**（属性 key 即列名） | 改列名 = 迁全部历史 + 改全部查询 |
| **列类型** | 改不动，只能加新列 |
| **超表划分** | 换划分要迁全部子表 |

判据 B（测点集合与类型来自模型）与判据 C（新类型无 diff）都依附这三样，所以 D2 不定，S1 / S3 / S4 都不开工。

## 1. 已定的前提（不是选项）

来自 L1 判据与 S0 已落地的事实，本卡不重开：

1. 子表命名 `{deviceId}_{pointKey}` 折小写；**子表名库内全局唯一**（`1565`）
2. 一个采集点建 1 张原始子表 + 3 张降采样子表（1m / 1h / 1d）
3. 降采样列**必须由模型推导**——否则新增属性后降采样环缺 `sum_xxx` 列，整级失败（判据 C 后半句）
4. 属性 key 不得以 `_unit` 结尾，且大小写不敏感唯一（[第 2 讲 §6]，由 `apps/iot-worker/src/schema.ts` 的列生成方式推出）
5. 超表列数上限 4096，按 6 列/属性估约 680 属性/类型，不构成实际约束
6. 本增量只实现属性通路；service / event 留结构、留 channel

## 2. 需要你回答的六个子问题

每项只给"要定什么"与"只有你能答的部分"，不给候选。

### 2.1 属性挂在哪一层

模型的属性，挂在**设备类型**上，还是挂在**采集点**上？

行业口径：阿里云、SiteWise 的测量属性都挂在类型 / 资产模型上，没有"采集点"这一层。本仓现状有 `pointKey` 这一层，且它是子表名的一半。

只有你能答的：一台设备会不会有多个采集点，多点的测点集合是否相同。

### 2.2 超表划分粒度

单超表 / 一类型一超表 / 一测点一超表。矩阵与逐格代价见 [行业输入 §3](2026-11-01-thing-model-industry-input.md)。

只有你能答的：**设备会不会换型**；**跨类型联合查询是不是主路径**。

无论选哪个都要接受的代价：(a) 一类型一超表 ⇒ 换型 = 换 `deviceId`；(b) 单超表 ⇒ 类型在存储层不可见、宽表吃全平台属性并集。

### 2.3 列集合怎么从模型推导

今天只做标量时，一属性 → 一列，是映射。要能长大到 array / struct 时，一属性 → 多列，规则要变成展开算法。

只有你能答的：这个增量之后，**下一个要接的真实设备类型**大概什么形状——有没有波形、有没有嵌套参数组。

### 2.4 类型档位表

模型的 dataType → TDengine 列类型的映射。要覆盖：数值分几档、字符串限长、枚举怎么存（INT + 取值表）、array / struct 的拒绝码。

只有你能答的：字符串长度上限——这个数一旦定死，以后只能加新列。

### 2.5 降采样列的推导规则

每属性固定四聚合，还是**按类型分档**（BOOL 只留 `count_` / `max_`）。前者简单，后者才说得通——`sum_bool` 没有语义。

只有你能答的：BOOL 类测点你要看什么聚合——运行时长？窗口内是否运行过？

### 2.6 属性 key 的命名空间规则

分隔符、组件前缀、长度上限、保留词（`ts` / `deviceId` / `_unit` 后缀）。

只有你能答的：将来组件化时，`组件_属性` 这个形态能不能接受。
