## 0. 这个决策锁死什么

三样不可逆，且都必须在写第一行数据之前定：

| 不可逆项 | 定错的代价 |
| --- | --- |
| **列名**（属性 key 即列名） | 改列名 = 迁全部历史 + 改全部查询 |
| **列类型** | 改不动，只能加新列 |
| **超表划分** | 换划分要迁全部子表 |

判据 B（测点集合与类型来自模型）与判据 C（新类型无 diff）都依附这三样，所以 D2 不定，S1 / S3 / S4 都不开工。

## 1. 已定的前提（不是选项）

来自 L1 判据与 S0 已落地的事实，本卡不重开：

1. 超表命名 `{模型编码}`、子表命名 `{模型编码}_{deviceId}`，均折小写；子表名库内全局唯一（`1565`）；**模型编码须是合法标识符**——小写字母开头，只含字母、数字、下划线，不含 `-` / `.` / `:`；**长度 `模型编码 ≤ 172`**（表名上限 192，预留 `_{deviceId}` 17 字符与降采样级后缀 3 字符）；去掉采集点层由 S0.5 落地
2. 一台设备建 1 张原始子表；**降采样 3 张（1m / 1h / 1d）仅在聚合集非空时**
3. 降采样列**必须由模型推导**——否则新增属性后降采样环缺 `sum_xxx` 列，整级失败（判据 C 后半句）
4. 属性 key 大小写不敏感唯一；`_unit` 后缀降为**保留词**——单位列已取消，重名冲突不复存在，保留只为将来回退时不用改数据
5. 超表列数上限 4096；去掉单位列后每属性 = 1 个值列 + 4 个降采样列 = 5 列，单表约 819 属性，不构成实际约束
6. 本增量只实现属性通路；service / event 留结构、留 channel
7. **单位在模型内不可变**——要改单位等于新建模型类型，随之新超表、新子表名（`deviceId` 不变）（2026-11-03 定，见 §10）

## 2. 需要你回答的六个子问题

每项只给"要定什么"与"只有你能答的部分"，不给候选。

### 2.1 属性挂在哪一层 —— 已定（2026-11-03）

**结论**：属性挂**设备**，单设备单采集点。多采集点属过渡设计，不采用。

**推论**：子表名从 `{deviceId}_{pointKey}` 改为 `{模型编码}_{deviceId}`；载荷删 `localPointId`；档案删采集点层。落地为子任务 **S0.5**，排在 D2 定稿之后、S1 之前（见 [范围定稿](2026-11-01-scope-and-task-map.md) §1）。

**被否决的候选**：一台设备多个采集点——它要求在档案里维护点层、在载荷里加 `localPointId`、在子表名里加一段，而这层信息在四家行业实现里都不存在。

**代价**：一台网关挂多路、且各路测点集不同时，只能用"多台设备"登记，物理上的一台会显示成多台。

**复查触发点**：出现一台网关需挂多路异构测点、而"多台设备"登记不成立（如共用一张证书、共用一条连接）时。

### 2.2 超表划分粒度 —— 已定（2026-11-03）

**结论**：一类型一超表，**版本不进物理命名**。超表 `{模型编码}`，子表 `{模型编码}_{deviceId}`。

- 模型内演进（加属性、减属性、改类型、改量程）靠 `ALTER STABLE ADD COLUMN` 与元数据变更完成，**不建新表、不换 `deviceId`、数据不散落**
- 换模型（设备换型号）→ 换 `deviceId`，认作新设备；物理连续性留给将来的资产层

**依据**：① 类型量级为几十到百级，单超表的降采样列在约 1023 个属性处撞 4096 上限，2000+ 属性装不下；② "加装传感器"主要是同型号加属性（情形 A），不是换型号（情形 B）；③ 阿里云、腾讯云的存储均按产品分表，不按模型版本分表。

**被否决的候选**：`{模型编码}_{版本}_{deviceId}` 版本分表——它把一台设备的数据按**每一个版本**切开，让"按设备查"的次数随版本数增长，而未带来查询收益（三家云的历史接口本身就是逐属性查询）。

**代价**：(a) 换型号时子表名随之改变，一台设备的数据落在两个子表里，跨型号查询要枚举子表（`deviceId` 保持不变）；**审计的期望集随之变化**——从"每设备一张子表"变成"每设备 × 用过的模型各一张"，旧模型子表是合法的，不能判成孤儿；(b) 超表列集合是模型内所有历史属性的并集，废弃属性永久占列。

**换型号的处理（2026-11-03 定）**：`deviceId` **保持不变**。设备换到新模型时，在新模型下建新子表，旧模型的子表连同历史数据保留。因此档案必须记录**模型变更历史**（设备 × 用过的模型 × 起止），审计的期望集据此展开；只记"当前模型"不足以区分合法旧子表与孤儿。

**前置实测（2026-11-03 通过）**：`ALTER STABLE ADD COLUMN` 后已有子表**立刻获得该列**，旧行读出新列为 NULL（本机 3.4.2.8 实测）。

**复查触发点**：① 单类型累计属性数 × 6 > 4000；② 换型号发生频率高于预期，且资产层无法补足物理连续性。

### 2.3 列集合怎么从模型推导 —— 已定（2026-11-03）

**结论**：模型允许**结构体**属性，但存储上仍是**一属性一列**——结构体序列化后存进一个变长字符串列。列集合规则永久是"一属性一列"，不需要展开算法。

- 属性 key 一旦保存即固化；**改 key 等于新建模型类型**（见下方「改 key 的处理」）
- 序列化格式由**平台**定义（不是设备），保证同一属性每次写法一致
- 校验在序列化**之前**对对象做：设备发对象，平台按模型的子字段声明校验后再序列化
- 字符串列用 **VARCHAR（变长）**，不用 NCHAR（定长）——序列化后的 JSON 长度不定

**被否决的候选**：模型只允许标量、由建模者自行拆成 `父_子` 多个属性——表达力等价，但建模者要手工拆，分组语义也会丢。

**代价**：(a) 结构体内部字段**不可查询、不可聚合**，只能整体读出来在应用层解析；(b) **降采样不做值聚合**——`sum` / `min` / `max` 对 JSON 无意义，只允许 `count`；选哪几类由建模人在定义时决定（见 2.5）；(c) 变长字符串列的长度上限一旦定死不可改，序列化 JSON 却是变长的，超长只能拒收。

**口径（2026-11-03 定）**：本增量按**结构体内部字段不需要被筛选或聚合**设计。

**复查触发点**：出现按结构体内部字段过滤或聚合的查询时——届时只能加新属性（拆成标量），旧列因列名固化而无法改造；该场景已登记 backlog。

**改 key 的处理（2026-11-04 定）**：不允许原地改名，也**不在同一模型内"删旧加新"**——改 key 等于**新建模型类型**。

- **依据**：列名不可改（物理上只能新增列）；而设备侧 key 一旦变更，旧模型已与设备对不上，"同一模型"这个前提本身就不成立
- **落地**：新模型 → 新超表 → 设备在新模型下建新子表，`deviceId` 不变（见 2.2）
- **与 2.2「版本不进物理命名」不矛盾**：进命名的是**模型编码**，不是版本号。改量程、改服务定义、改描述、**加属性、减属性**都在同一模型内完成——版本号递增，不新建模型；只有**改 key**（与 §10 的改单位）才新建模型。判据不是"动了列集合"，而是**旧结构还能不能解释新数据**，见 §11
- **代价**：(a) 模型数量随**改 key / 改单位**的次数增长——十型号 × 两次改 key = 30 个模型、每个 4 张超表；(b) 模型编码须能表达同型号的代次（`st100` → `st100b`），代次因此进入子表名
- **行业参照**：阿里云明文禁止修改已添加功能的标识符，只允许删除后再添加（台账 #204）。它能"同模型内删加"是因为存储不绑列；我们必须绑列

**被否决的候选**：同一模型内"删旧 key + 加新 key"、旧列停写。阿里云走这条路，但它的落地层不绑列；我们照做会让一个模型里长期并存两套语义重复的列，也与"key 固化"的表述冲突。

### 2.4 类型档位表 —— 已定（2026-11-03）

**结论**：类型档位、长度、精度都由**物模型在定义时声明**，不写死在代码里。

- 数值：`FLOAT` / `DOUBLE` 二选一（按量程与有效位数选）
- 整数：`INT` / `BIGINT` 二选一（累计量必须 `BIGINT`）
- 布尔：`BOOL`
- 枚举：`INT` + 取值表
- 字符串：`VARCHAR(N)`，**N 由模型声明**
- 结构体：`VARCHAR(N)`，存平台序列化后的 JSON，**N 由模型声明**
- 数组：拒绝（本增量不做）；后续若要，走二进制列或解析侧降维

**代价**：长度与档位一旦定死不可改，模型定义时必须给足余量；超长一律拒收，不截断。

**长度上界（2026-11-04 实测）**：`VARCHAR(N)` 的 N ≤ **65517** 字节；裸 `VARCHAR`（不写长度）是语法错误，N 必须显式给出。注册时按此校验。单个结构体属性的容量因此约 64 KB。

**开口**：无。精度即**档位选择**——`FLOAT` 或 `DOUBLE`，由模型声明。小数位数属校验与展示层，可存在模型里用于拒收超位数值，不影响存储。TDengine 没有 `DECIMAL`；将来金额、电量读数这类需要精确十进制的量，只能用 `BIGINT` 存最小单位，本增量不做。

### 2.5 降采样列的推导规则 —— 已定（2026-11-03）

**结论**：**聚合集由模型按属性声明**，不是固定四聚合。

- 每个属性声明自己需要哪几类聚合（`sum` / `count` / `min` / `max` 的子集，可为空）
- 聚合集为空的属性**不产生降采样列**，也不进入降采样 SQL——否则 `SUM(varchar)` 会让整条查询失败、整个级别停摆
- 类型与聚合的允许组合：`sum` 仅数值；`min` / `max` 数值、布尔、枚举；`count` 任意类型；字符串与结构体只允许 `count`
- **拦截点在注册接口**：建模时每个属性可自由声明聚合集，保存前由物模型定义接口把可选项收窄到上表——存储层只回答"这个组合能不能算出列类型"，不判策略
- 非法组合（如 `sum` 配 `BOOL`）在注册时拒绝，给明确错误码
- 自定义聚合留位：将来以表达式扩展，本增量不做

**全空聚合的模型（2026-11-03 定）**：**不建降采样超表，也不建降采样子表**——该模型的设备只有一张原始子表。降采样环与对账脚本必须跳过这类模型；审计的期望集要按模型的聚合配置推导，不能再假设"每设备恒定 1 原始 + 3 降采样"。

**代价**：(a) 聚合集变更也是列集合变更，靠 `ADD COLUMN`（加）与停写（减）处理；(b) 某属性后来才加聚合时，只能从新窗口开始积累——降采样环只重算最近 K 个窗口，历史原始数据不会自动回填。

### 2.6 属性 key 的命名空间规则 —— 已定（2026-11-03）

**结论**：

- **字符集**：小写字母开头，只含小写字母、数字、下划线。模型里允许写大写，平台归一化为小写；仅大小写不同的两个 key 直接拒绝
- **长度**：**key ≤ 58**——本机实测列名上限 64 字符，而降采样列名是 `<聚合>_<key>`，最长的聚合前缀 `count_` 占 6 字符
- **保留词**：`ts`、`deviceId` 必须禁；聚合前缀 `sum_` / `count_` / `min_` / `max_` **不需要禁**——`<聚合>_<key>` 的拼接是单射，四个聚合名互不为前缀；`_unit` 后缀已无冲突
- **组件分组**：**不进列名**，作为模型元数据（`group` 字段）存在，列名永远扁平
- **唯一性**：key 在模型内唯一，不是全平台唯一
- **改 key**：不允许原地改名，也不在同一模型内删旧加新——**改 key 等于新建模型类型**（见 §2.3）

**被否决的候选**：分组进 key（`组件_属性`）——`_` 会同时承担分组边界与普通分词两种含义，`location_lat` 是"location 组的 lat"还是"一个叫 `location_lat` 的属性"无法区分，而列名固化后歧义永存。

**代价**：同名属性落在不同分组时，要自己起不同的 key（`feed_temp` / `discharge_temp`）。

**复查触发点**：组件化需要跨模型复用同一份属性定义时。

## 6. 定完之后，什么能证明定对了

1. 写出一张完整的类型档位表，且 array / struct 有明确拒绝码
2. 降采样列能由属性列表**算出来**，不需要人再加一行常量
3. 拿 P1 三测点走一遍：新规则推导出的列集合与现有 `telemetry` 超表一致，或明确说明哪里有意不同
4. 属性 key 撞保留词、撞大小写、以 `_unit` 结尾——三种都有拒绝码
5. ✅ `ALTER STABLE ADD COLUMN` 后**已有子表自动获得该列**，旧行读出新列为 NULL（本机 3.4.2.8 实测，2026-11-03）
6. ✅ **列名上限 64 字符**（64 通过、65 拒绝）；**表名上限 192**（192 通过、193 拒绝）。⇒ 属性 key ≤ 58、模型编码 ≤ 172
7. ⚠️ 超长表名在特定序列下会报 `index already exists in db [0x80000483]` 而不是长度错误——**注册时必须主动校验长度**，不能指望错误信息自解释
8. ✅ **`VARCHAR(N)` 上限 65517 字节**、`NCHAR(N)` 上限 16379 字符；裸 `VARCHAR` 是语法错误（本机实测 2026-11-04）。注册时按 65517 校验 N

| TDengine 4096 列上限、类型族 | 🟡 官方 v3.0 口径，本机 3.4.2.8 未实测（#193 / #194） |
| 属性 key 不得以 `_unit` 结尾、大小写不敏感 | ✅ 本仓代码推导（`apps/iot-worker/src/schema.ts`） |
| `ADD COLUMN` 传播到已有子表；列名上限 64；表名上限 192 | ✅ 本机 3.4.2.8 实测（2026-11-03，台账 #200–#201） |

## 10. 单位（2026-11-03 定）

**结论**：单位在模型内**不可变**。要改单位，新建模型类型——随之新超表、新子表名（`deviceId` 不变）。

**依据**：单位变更必然伴随设备改造或固件升级、期间停机。把它当结构变更而非参数变更，与"列类型不可逆"是同一条纪律。

**推论**：

1. 同一属性的"应该是什么"与"当时是什么"恒等 ⇒ L1 §2 的两级单位塌成一级
2. 写入侧拒绝与模型声明不符的单位；不符即是错误，不是警告
3. 降采样窗口不可能跨单位变更 ⇒ 1h / 1d 边界的混单位问题不存在

**代价**：单位变更按整批设备计——一个型号 100 台全部换到新模型的子表，历史断成两段（`deviceId` 不变，但子表名变）。单位变更因此归入 2.2 的"情形 B"频率档。

**必须区分**：**存储单位**改了才是模型变更；**展示单位**改了只是读取时换算（PI 的 `EngUnits` 是标签，换算在 AF 层），不动模型。

**已定（2026-11-03）：去掉单位列。** 原始超表与降采样超表都不再有 `<metric>_unit`；单位只存在于模型声明里，由写入侧校验（载荷仍带 `unit`，与声明不符即拒绝，不落行）。取证价值从"行内留证"转为"拒绝日志"。

## 11. 版本与版本快照（2026-11-04 定）

**结论**：模型**物理一份、逻辑多版**——列在超表里就地演进，每个版本另存一份不可变的**声明快照**。

### 11.1 什么操作算什么

| 操作 | 物理动作 | 版本 | 模型 |
| --- | --- | --- | --- |
| 改量程 / 改服务定义 / 改描述 | 无 | 递增 | 不变 |
| 加属性 | 原始超表与三级降采样超表 `ADD COLUMN`（已实测传播到全部子表，§6 第 5 条） | 递增 | 不变 |
| 减属性 | 停写（列不删） | 递增 | 不变 |
| **改 key** | 新超表 + 新子表名 | — | **新建** |
| **改单位** | 无（单位不落列） | — | **新建** |

**判据不是"动不动列集合"**：加属性动列集合却不新建模型，改单位不动列集合却新建模型。真正的判据是**旧结构还能不能解释新数据**：

- **叠加型**（加 / 减属性、改量程、改服务、改描述）——旧结构仍能解释，缺失由 `NULL` 加快照共同表达
- **覆盖型**（改 key、改单位）——同一列在时间轴上会承载两种语义，旧结构解释不了，只能分表

### 11.2 快照存什么

一个版本一条记录：版本号、所属模型编码、起止时间、状态（`PENDING` / `ACTIVE` / `FAILED`），以及该版本**声明的属性集**——每个属性的 key、列类型与长度、单位、量程、聚合集、分组。

### 11.3 快照解决什么

超表列集合是历史属性的并集、只增不减（§2.2 代价 b）。没有快照时，某属性在某窗口读出 `NULL`，分不清是"当时还没定义这个测点"还是"定义了但当时没上报"；有快照时按时间取当时的声明即可判定。

### 11.4 「版本不可变」指什么

不可变的是**快照**，不是物理列集合。列集合随版本单调增长、永不收缩，废弃属性永久占列。

### 11.5 代价

- 查询侧多一次快照读取（内存查表，不是多一次扫描）
- 每次加属性要同步 `ALTER`：1 张原始超表 + 3 张降采样超表，其全部子表随之获得新列
- 版本数随变更次数增长，快照需要有保留策略

### 11.6 与 §2.2 的关系

§2.2 定的「一类型一超表、版本不进物理命名」不变——版本的物理载体就是**同一张超表的列**，版本号只活在快照里。加属性因此不会让设备换子表、也不会让跨时间段的查询变成多表 `UNION`。
