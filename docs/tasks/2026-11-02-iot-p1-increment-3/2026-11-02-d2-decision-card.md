## 0. 这个决策锁死什么

| 不可逆项 | 定错的代价 |

## 1. 已定的前提（不是选项）

来自 L1 判据与 S0 已落地的事实，本卡不重开：

1. 超表命名 `{模型编码}`、子表命名 `{模型编码}_{deviceId}`，均折小写；子表名库内全局唯一（`1565`）；**模型编码须是合法标识符**——小写字母开头，只含字母、数字、下划线，不含 `-` / `.` / `:`；去掉采集点层由 S0.5 落地
2. 一台设备建 1 张原始子表 + 3 张降采样子表（1m / 1h / 1d）
3. 降采样列**必须由模型推导**——否则新增属性后降采样环缺 `sum_xxx` 列，整级失败（判据 C 后半句）
4. 属性 key 大小写不敏感唯一；`_unit` 后缀降为**保留词**——单位列已取消，重名冲突不复存在，保留只为将来回退时不用改数据
5. 超表列数上限 4096；去掉单位列后每属性 = 1 个值列 + 4 个降采样列 = 5 列，单表约 819 属性，不构成实际约束
6. 本增量只实现属性通路；service / event 留结构、留 channel
7. **单位在模型内不可变**——要改单位等于新建模型类型，随之新超表、新子表名（`deviceId` 不变）（2026-11-03 定，见 §10）

## 2. 需要你回答的六个子问题

每项只给"要定什么"与"只有你能答的部分"，不给候选。

### 2.1 属性挂在哪一层 —— 已定（2026-11-03）

**结论**：属性挂**设备**，单设备单采集点。多采集点属过渡设计，不采用。

**推论**：子表名从 `{deviceId}_{pointKey}` 改为 `{模型编码}_{deviceId}`；载荷删 `localPointId`；档案删采集点层。落地为子任务 **S0.5**，排在 D2 定稿之后、S1 之前（见 [范围定稿](2026-11-01-scope-and-task-map.md) §1）。

**被否决的候选**：一台设备多个采集点——它要求在档案里维护点层、在载荷里加 `localPointId`、在子表名里加一段，而这层信息在四家行业实现里都不存在。

**代价**：一台网关挂多路、且各路测点集不同时，只能用"多台设备"登记，物理上的一台会显示成多台。

**复查触发点**：出现一台网关需挂多路异构测点、而"多台设备"登记不成立（如共用一张证书、共用一条连接）时。

### 2.2 超表划分粒度 —— 已定（2026-11-03）

**结论**：一类型一超表，**版本不进物理命名**。超表 `{模型编码}`，子表 `{模型编码}_{deviceId}`。

- 模型内演进（加属性、减属性、改类型、改量程）靠 `ALTER STABLE ADD COLUMN` 与元数据变更完成，**不建新表、不换 `deviceId`、数据不散落**
- 换模型（设备换型号）→ 换 `deviceId`，认作新设备；物理连续性留给将来的资产层

**依据**：① 类型量级为几十到百级，单超表的降采样列在约 1023 个属性处撞 4096 上限，2000+ 属性装不下；② "加装传感器"主要是同型号加属性（情形 A），不是换型号（情形 B）；③ 阿里云、腾讯云的存储均按产品分表，不按模型版本分表。

**被否决的候选**：`{模型编码}_{版本}_{deviceId}` 版本分表——它把一台设备的数据按**每一个版本**切开，让"按设备查"的次数随版本数增长，而未带来查询收益（三家云的历史接口本身就是逐属性查询）。

**代价**：(a) 换型号时子表名随之改变，一台设备的数据落在两个子表里，跨型号查询要枚举子表（`deviceId` 保持不变）；**审计的期望集随之变化**——从"每设备一张子表"变成"每设备 × 用过的模型各一张"，旧模型子表是合法的，不能判成孤儿；(b) 超表列集合是模型内所有历史属性的并集，废弃属性永久占列。

**换型号的处理（2026-11-03 定）**：`deviceId` **保持不变**。设备换到新模型时，在新模型下建新子表，旧模型的子表连同历史数据保留。因此档案必须记录**模型变更历史**（设备 × 用过的模型 × 起止），审计的期望集据此展开；只记"当前模型"不足以区分合法旧子表与孤儿。

**前置实测**：`ALTER STABLE ADD COLUMN` 后已有子表是否自动获得该列（本机 3.4.2.8）。不通过则退回按结构代次分表。

**复查触发点**：① 单类型累计属性数 × 6 > 4000；② 换型号发生频率高于预期，且资产层无法补足物理连续性。

### 2.3 列集合怎么从模型推导

今天只做标量时，一属性 → 一列，是映射。要能长大到 array / struct 时，一属性 → 多列，规则要变成展开算法。

只有你能答的：这个增量之后，**下一个要接的真实设备类型**大概什么形状——有没有波形、有没有嵌套参数组。

### 2.4 类型档位表

模型的 dataType → TDengine 列类型的映射。要覆盖：数值分几档、字符串限长、枚举怎么存（INT + 取值表）、array / struct 的拒绝码。

只有你能答的：字符串长度上限——这个数一旦定死，以后只能加新列。

### 2.5 降采样列的推导规则

每属性固定四聚合，还是**按类型分档**（BOOL 只留 `count_` / `max_`）。前者简单，后者才说得通——`sum_bool` 没有语义。

只有你能答的：BOOL 类测点你要看什么聚合——运行时长？窗口内是否运行过？

### 2.6 属性 key 的命名空间规则

分隔符、组件前缀、长度上限、保留词（`ts` / `deviceId` / `_unit` 后缀）。

只有你能答的：将来组件化时，`组件_属性` 这个形态能不能接受。

## 10. 单位（2026-11-03 定）

**结论**：单位在模型内**不可变**。要改单位，新建模型类型——随之新超表、新 `deviceId`。

**依据**：单位变更必然伴随设备改造或固件升级、期间停机。把它当结构变更而非参数变更，与"列类型不可逆"是同一条纪律。

**推论**：

1. 同一属性的"应该是什么"与"当时是什么"恒等 ⇒ L1 §2 的两级单位塌成一级
2. 写入侧拒绝与模型声明不符的单位；不符即是错误，不是警告
3. 降采样窗口不可能跨单位变更 ⇒ 1h / 1d 边界的混单位问题不存在

**代价**：单位变更按整批设备计——一个型号 100 台全部换到新模型的子表，历史断成两段（`deviceId` 不变，但子表名变）。单位变更因此归入 2.2 的"情形 B"频率档。

**必须区分**：**存储单位**改了才是模型变更；**展示单位**改了只是读取时换算（PI 的 `EngUnits` 是标签，换算在 AF 层），不动模型。

**已定（2026-11-03）：去掉单位列。** 原始超表与降采样超表都不再有 `<metric>_unit`；单位只存在于模型声明里，由写入侧校验（载荷仍带 `unit`，与声明不符即拒绝，不落行）。取证价值从"行内留证"转为"拒绝日志"。
