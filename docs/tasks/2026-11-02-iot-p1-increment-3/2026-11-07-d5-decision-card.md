## 0. 这个决策锁死什么

| 项 | 定错的代价 |
| --- | --- |
| 注销在档案上的表达 | 定错会让审计把退役设备的子表永久判成孤儿，或让消费分不清「已注销」与「从未注册」 |
| 数据与表的去留 | 删了不可恢复；留着则子表与快照永久增长，审计口径必须跟着改 |
| 设备再回来 | 定错则返修设备只能换标识或人工改库，现场无法自服务 |
| 排期设备的改与撤 | 定错会让未生效设备的上报在撤销后仍被接受，或留下无归属的数据 |
| 删除能力放在哪 | 放进只读审计会让「看一眼」变成「删一次」；没有删除路径则测试 / 生产环境无法回收孤儿 |

## 1. 已定的前提（不重开）

1. **数据与表不随注销删除**，保留到自然过期（本次决策）
2. **注销不物理删除档案**；动机是设备报废，不是合规删除（本次决策）
3. `deviceId` 永不复用；`localDeviceId` 唯一（D3 / README 接缝 3）
4. 判定按数据自己的 `ts`、区间半开 `[from, to)`（D1 §2.3）
5. 列只增不减，物理列是所有版本的并集（D2 §11.4）
6. 审计只读，期望集来自快照（S0 / D1）
7. 注册失败只删本次建的表（D3 §2.4）
8. `(子表, ts)` 最后一条胜（增量 2）

## 2. 七个子问题与结论

### 2.1 形态：加 `RETIRED` 状态 + 闭合 usage

**结论**：`IotDeviceStatus` 增加第三态 `RETIRED`。注销在**一个 PG 事务**里完成：

```text
锁设备行（SELECT … FOR UPDATE）
→ status = RETIRED、statusChangedAt = now
→ 关闭 open usage：toAt = max(now, usage.fromAt)
→ 提交后 INCR iot:registry:rev
```

- **`toAt = max(now, fromAt)`** 同时覆盖两种场景：已生效设备 `toAt = now`；已排期未生效设备 `fromAt > now` ⇒ `toAt = fromAt`，得到**零长区间** `[fromAt, fromAt)`，一条数据都不覆盖（撤销，见 §2.5）
- **不预约注销**：`toAt` 不会取晚于 `now` 的时刻，除非是撤销未生效设备。需要「到期自动注销」时另立触发点
- **幂等**：对已 `RETIRED` 的设备重复调用返回 200 与当前状态，不重复改 `toAt`
- **不动 TDengine**：不删表、不删行
- **入口**：沿用 HTTP + JWT（D3）；注销与撤销共用 `DELETE /api/v1/iot/devices/:localDeviceId`

**不变式**：`status = RETIRED` 的设备**没有 open usage**。注册、注销、复活三个写路径都必须维持它。

### 2.2 数据与表：保留，数据按 KEEP 过期，表永久

**结论**：注销不删任何表与行。

- 原始数据按 `KEEP 1095 天`、降采样数据按 `KEEP 3650 天` 自然过期；**过期的是数据，不是表**
- 子表与降采样子表**永久保留**，降采样 `PARTITION BY tbname` 的扫描面不随注销收缩
- 因此「表存在 ⇔ 曾注册」这条不变量继续成立，退役设备的表**必须仍在审计期望集里**

**快照必须纳入退役设备**（连带修订 D1）：

- `snapshot.builder.ts` 的设备查询从 `status = 'ACTIVE'` 改为 `status IN ('ACTIVE','RETIRED')`
- D1 决策卡中「全部 ACTIVE 档案」统一改为「全部在册档案（`ACTIVE` + `RETIRED`）」
- worker 侧**不需要读状态**：退役设备的 usage 已闭合，`ts ≥ toAt` 由区间判定拒为 `out-of-range-ts`；`ts < toAt` 的历史数据仍接受

⚠️ **封存历史口径**：注销后到达、但 `ts < toAt` 的晚到数据**仍会入库**。这是按事件时间判定的直接推论，不是漏洞——注销表达的是「设备从此不再产生新数据」，不是「拒绝它的历史」。要让这类数据也拒，只能把「到达时间」加回热路径，与 D1 冲突，不做。

**计数语义变化**：注销后的上报不再落 `unknown-device`（设备仍在快照），而是落 `out-of-range-ts`。现场排障口径与告警阈值要同步。

### 2.3 删除路径：只剩孤儿清理脚本

**结论**：注销与撤销都**不删表**。本增量新增的删除能力只有一个：`subtable:cleanup`。

- **审计保持只读**，`subtable:audit` 不加删除参数
- `subtable:cleanup` 默认 dry-run：打印 `orphanRaw` / `orphanDs` 名单与总数；`--apply` 才执行删除
- **安全闸**（三条，缺一拒绝执行）：
  - 快照不存在 ⇒ 拒绝（与审计同一口径）
  - 期望集为空 ⇒ 拒绝（否则全库判孤儿）
  - 快照不新鲜（`builtAt` 超过 10 分钟，或 `rev ≠ built`）⇒ 拒绝——**防止拿滞后快照把刚注册的表删掉**
- **删除顺序：原始子表优先，降采样子表随后**。中断时残留为孤儿降采样子表——它不会被降采样读取，是惰性的；反过来先删降采样，会让降采样读到孤儿原始子表却写不进目标表，**整级重算失败**
- 单表删除失败重试 3 次、仍失败记 error 并继续，残留由下一次审计重新认领（与 `dropCreatedTables` 同一纪律）
- 只删名单里的名字，不按前缀匹配、不做「看起来像我们建的」推断

**为什么不能只靠开发环境重建库**：测试 / 生产不允许重建库（硬约束），孤儿必须有一条不依赖重建的回收路径。

### 2.4 再注册：仅同型号复活

**结论**：`POST /api/v1/iot/devices` 对 `status = RETIRED`、**模型相同**的设备执行复活：

```text
校验 fromAt（默认 now）≥ 模型最早版本，且不与任何非空历史 usage 重叠
→ status = ACTIVE、statusChangedAt = now
→ 新开 usage（modelCode 不变、version = fromAt 时刻生效的版本）
→ 提交后 INCR rev
```

- **沿用原 `deviceId` 与子表名**，不重新签发、不新建表
- 复活前校验应有子表齐全；缺一张即 `schema-mismatch`，**不自动补**（与现有幂等路径一致，修复归审计与人工）
- **不同 `modelCode` 仍返回 409 `registered-to-other-model`**：换型号本增量不支持
- 重叠约束：新 `fromAt` 不得早于最后一个**非空** usage 的 `toAt`；被撤销设备留下的零长 usage 不参与重叠判定
- 已 `ACTIVE` 且模型相同的重复注册，行为不变（幂等返回首次结果）

⚠️ **换型留后续增量**。触发点：第一台现场改型设备，或前端需要「改挂模型」入口。

### 2.5 排期：支持改期，撤销同注销

**结论**：已排期未生效（`open usage.fromAt > now`）的设备可改期；撤销与注销共用一个入口。

**改期** `PATCH /api/v1/iot/devices/:localDeviceId`，body 只接受 `fromAt`：

- 只允许作用于 `fromAt > now` 的设备；**目标 `fromAt` 必须仍在未来**
- 仍受「不早于模型最早版本」约束；按新 `fromAt` 重算 `usage.version`
- 已生效（`fromAt ≤ now`）的设备改期 ⇒ 409——该时段的数据已按旧区间解释，改期会制造不可追溯的口径
- 要立即生效，走「撤销 + 重新注册」（注册允许 `fromAt` 早于 `now`）
- 幂等：同一 `fromAt` 重复提交返回相同结果

**撤销**：走 `DELETE`，与注销同一事务；`toAt = max(now, fromAt) = fromAt`，得到零长区间。

- **保留 usage 行与子表**：删 usage 会让审计失去该子表的期望，空表立刻变孤儿；零长区间同样一条数据不覆盖，语义更干净
- 撤销后上报全部落 `out-of-range-ts`
- 审计仍退出 0（表在期望集里）
- 被撤销设备可被同型号复活；复活不要求 `fromAt ≥ 零长 usage` 的 `toAt`（见 §2.4 重叠约束）

### 2.6 批内同键：维持 last-wins

**结论**：`(子表, ts)` 同一批内出现多条时保留最后一条，口径写进文档：

> 同一 `(子表, ts)` 的最后一条胜出，是幂等语义，与 TDengine 的覆盖语义一致。

- `duplicateInBatch` 计数保留，作为可观测的量
- **不新增告警**：告警接收方目前缺位（D4 §7），且 P1 无真实设备
- 计数不区分「同值重发」与「不同值冲突」；需要区分时另立触发点

### 2.7 快照与连带修订

**结论**：本次决策对既有文档与查询的改动是一次性的对齐清单：

| 位置 | 改动 |
| --- | --- |
| `snapshot.builder.ts` 设备查询 | `ACTIVE` → `ACTIVE` + `RETIRED` |
| `schema.prisma` 的 `IotDeviceStatus` 注释 | 「没有退役语义」改为三态说明 |
| D1 决策卡 §2.1 / §2.2 | 「全部 ACTIVE 档案」→「全部在册档案（`ACTIVE` + `RETIRED`）」 |
| D1 决策卡 §7 第 2 条 | 旧快照窗口的口径改为「封存历史」：`ts < toAt` 仍收、`ts ≥ toAt` 拒 |
| 注册路径的冲突码 | 拆分 `device-not-active`：`RETIRED` 走复活、其余非 `ACTIVE` 报 `device-not-active` |
| `DeviceRegistryRepository.listSubtablesOfRegisteredDevices` | 过滤条件与审计同口径纳入 `RETIRED`，避免两套期望集 |

## 3. 定完之后，什么能证明定对了

| 验收 | 怎么证明 |
| --- | --- |
| 注销生效 | 注销后 `status = RETIRED`、无 open usage、`toAt` 已闭合；重复注销 200 且 `toAt` 不变 |
| 注销后上报 | `ts ≥ toAt` 落 `out-of-range-ts`；`ts < toAt` 的晚到数据仍入库 |
| 审计不红 | 注销后 `subtable:audit` 退出 0，退役设备的子表仍在期望集里 |
| 快照可见 | 注销后不重启 worker，快照仍含该设备；`worker-version` 在 2 秒内前进 |
| 返修复活 | 同型号注册 → `ACTIVE` + 新 usage，`deviceId` 与子表名不变；不同型号 409 |
| 复活不补表 | 手工删掉一张子表后复活 → `schema-mismatch`，PG 不留半条 |
| 改期 | 未来设备改 `fromAt` 成功且 `usage.version` 按新区间重算；已生效设备改期 409；改到模型最早版本之前 409 |
| 撤销 | 未生效设备撤销 → `RETIRED` + 零长 usage、审计 0、上报全部 `out-of-range-ts` |
| 批内同键 | 同一 `(子表, ts)` 两条不同值 → 落库为最后一条，`duplicateInBatch` 计数 +1 |
| 清理一致 | dry-run 名单与 `--apply` 实际删除逐名一致；快照缺失 / 空 / 陈旧时拒绝执行 |
| 清理顺序 | 中断后残留为孤儿降采样子表；降采样三级仍正常重算 |

## 4. 复查触发点

| 触发点 | 要复查什么 |
| --- | --- |
| 出现合规要求删除设备数据 | 「保留到自然过期」需要改为显式删除，注销形态与审计口径重开 |
| 子表数接近万级 / 快照超过 10 MB | 退役设备只增不减；快照保留策略与子表回收（D1 §4 同一触发点） |
| 第一台现场改型设备 | 换型路径（现为 409），以及 `deviceId` 不变、新旧 usage 的衔接 |
| 需要「到期自动注销」 | 预约注销：`toAt` 取未来时刻，零长区间规则要重新推演 |
| `duplicateInBatch` 持续非零 | 区分同值重发与不同值冲突，并接告警 |
| 告警接收方落地 | `out-of-range-ts` 因注销而上升，需要独立的注销后上报指标 |

## 5. 本卡不含

- 换型号（改挂模型）→ 触发点见 §4
- 模型超表的物理删除（模型永不删除）
- 预约注销 / 到期自动退役
- 数据归档到冷存储
- 注销的批量入口（一次注销多台）
- 设备列表 / 查询接口（本增量只做写路径）

## 6. 被否决的候选与理由

| 候选 | 否决理由 |
| --- | --- |
| **物理删除档案与 usage** | 与「`deviceId` 永不复用」冲突；审计失去历史凭据；设备报废场景没有删除必要 |
| **注销即删子表与数据** | 动机是报废不是合规；删了不可恢复，且跨表删除无原子，中断态会让降采样整级失败 |
| **只闭合 usage、不加状态** | 分不清「换型事务间隙」与「已注销」；运维查询只能靠推断 |
| **退役设备不进快照** | 审计期望集随之减少，全部子表永久进孤儿桶 |
| **让审计改读 PG** | worker 不碰 PG 是 D1 的依赖边界；审计脚本在 worker 里 |
| **返修新建档案** | `localDeviceId` 唯一且不物理删除，新档案无处可建；释放唯一约束等于物理删 |
| **复活时自动补缺表** | 与 D3 §2.4「缺表报结构不一致、不自动补」冲突；自动补会掩盖命名或建表逻辑的 bug |
| **撤销时删 usage 行** | 审计失去该子表的期望，空表立刻变孤儿 |
| **撤销时 `toAt = now`（`fromAt` 在未来）** | 区间 `[fromAt, now)` 起点晚于终点，语义为负；零长区间更好解释 |
| **改期允许把 `fromAt` 改到过去** | 已生效时段的数据已按旧区间写入，改期制造不可追溯口径；立即生效走撤销 + 重注册 |
| **批内同键告警** | 告警接收方缺位；同值重发与不同值冲突未区分前，告警只会制造噪声 |
| **审计工具内置删除参数** | 「看一眼」与「删一次」必须分开；dry-run 脚本单独存在 |

## 7. 代价与已知未解

| # | 项 | 状态 |
| --- | --- | --- |
| 1 | **子表永久增长**：注销不回收，DS 数据留 10 年、表永久 | 已接受。触发点见 §4 |
| 2 | **快照随退役设备永久增长** | 与 D1 §7 第 4、7 条同源，触发点共用 |
| 3 | **封存历史**：注销后 `ts < toAt` 的晚到数据仍入库 | 已接受，按事件时间判定的必然结果 |
| 4 | **预约生效设备在生效前收到未来 `ts` 的数据**：撤销后这段数据落在任何 usage 之外，留在表里但无区间归属 | 极窄；D4 允许 `ts` 前推 24 小时，记录为已知边界 |
| 5 | **换型不支持**：现场改型只能人工处理 | 触发点见 §4 |
| 6 | **撤销留下零长 usage 与空子表**：永久占位，审计绿但子表数不减 | 与第 1 条同源 |
| 7 | **`out-of-range-ts` 混装两种原因**：排期前上报、注销后上报 | 告警接收方落地时拆分计数 |
| 8 | **清理脚本依赖快照新鲜度**：10 分钟闸只能降低误删风险，不能消除 | dry-run + 人工确认是第二道闸 |
| 9 | **注销与复活并发**：靠行锁串行化，未做跨进程幂等键 | 单实例管理面，触发点：多操作者 |

## 8. 来源等级

| 结论 | 等级 |
| --- | --- |
| 设备状态两态、`localDeviceId` 唯一、`deviceId` 永不复用 | ✅ 本仓 `schema.prisma` |
| 快照只收 ACTIVE、审计期望集来自快照、降采样 `PARTITION BY tbname` 不查注册表 | ✅ 本仓 `snapshot.builder.ts` / `audit.ts` / `downsample/query.ts` |
| 注销 = 闭合 Type 2 行的右边界 | 【AI 判断】按维度建模通例推得，本仓无既有实现 |
| 先删原始、后删降采样可避免整级失败 | 【AI 判断】依赖「降采样只读原始超表」这一代码事实，S6 需用例证明 |
| 零长区间可让撤销设备一条数据都不覆盖 | 【AI 判断】依赖半开区间的 `find` 语义，S6 需用例证明 |
