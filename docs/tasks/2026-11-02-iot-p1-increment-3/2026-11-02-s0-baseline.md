## 2. 为什么跳过 `docker compose down -v`

S0 计划原本把「重建开发库卷」列为 T1，前提是库里存在 12,353 张存量表（历史探针与旧版测试遗留）。本次在 Docker 环境启动后先取数：`SHOW wewant_iot.TABLES` 为 100 行、`SHOW wewant_iot_ds.TABLES` 为 300 行，`subtable:audit` 四桶全空——**本机库里没有那批存量，基线本来就是干净的**。`down -v` 会一并清掉 PG / 两个 Redis / EMQX / TDengine 的全部卷且不可逆，在没有待清理对象时没有收益，故未执行。

因此本记录的准确表述是「**基线核验为干净，未做清库**」，不是「已清理 12,353 张」。清理路径本身仍然成立：只读审计负责发现；开发环境清库走重建卷；正式删除随注销状态机。

**健康检查能红**

```text
$ docker compose start worker
t=20s status=healthy

$ docker kill --signal=SIGSTOP wewant-multi-admin-worker-1
t=6s status=healthy
…
t=77s status=unhealthy        # ≤ 90 s

$ docker kill --signal=SIGCONT wewant-multi-admin-worker-1
t=6s status=unhealthy
…
t=28s status=healthy
```

心跳键 TTL 30 s、每 10 s 刷新；进程被挂起后键过期，compose healthcheck（interval 30s / timeout 5s / retries 2）在 77 s 内把容器标成 unhealthy，恢复后回到 healthy。compose 不会因 unhealthy 自动重启，这是可见信号，并为 K8s liveness 铺路。
