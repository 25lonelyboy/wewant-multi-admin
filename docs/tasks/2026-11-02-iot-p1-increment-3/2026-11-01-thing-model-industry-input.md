## 1. 四家各一句话（只用得上这一层）

| 家 | 形状 | 对我们最有用的一条 |
| --- | --- | --- |
| 阿里云 | 产品 × 物模型，属性/事件/服务三元组，9 类 dataType 带 min/max/unit | **模型即校验器**：不合格上报被过滤并回错误码 |
| ThingsBoard | Device Profile 管传输/规则链/队列/告警/计算字段 | **告警与派生量挂类型**，不挂单台设备 |
| Azure | DTDL 接口，模型 ID 自带版本 `…;1` | 模型是**可寻址的一等对象** |
| AWS SiteWise | 资产模型 + 四类属性 + 层级/组件/接口 | **latest / active 双版本 + ACTIVE/FAILED 状态机** |

一条反面教材：Azure 的 DTDL 文档页现已移入 `previous-versions` 且声明不再常规更新；阿里云该产品文档页标注"文档停止维护"。【AI 判断】选一个还在现役演进的形态作参照（SiteWise），比抄一个正在退场的更稳。

## 2. 对三条接缝的直接含义

| 接缝 | 行业做法给的答案 | 我们的落法 |
| --- | --- | --- |
| 档案 ↔ 子表预建 | SiteWise：定义先落 latest，校验通过才 propagate 为 active，失败进 FAILED，下游继续用上一 active | **状态机替代补偿事务**：档案 `PENDING → ACTIVE / FAILED`，消费者只认 ACTIVE。跨库无事务的问题从"写入时一致"挪到"读取时过滤" |
| 物模型 ↔ 单位 | PI 两级单位：归档层只描述、换算在上层；**属性上写"应该是什么"，行内 `_unit` 写"当时是什么"** | 不新决策，与增量 2 已定的口径同构；单位变更 = 新属性（新列） |
| 设备注销 ↔ 子表清理 | 三家都不做物理删，只做状态与保留策略 | 软注销 + `deviceId` 永不复用 |

## 3. D2 的二维矩阵（超表划分 × 新属性怎么落）

**维度一：存储划分**——A 单超表（现状 `telemetry`）｜B 一类型一超表｜C 一测点一超表（窄表）

**维度二：新属性加入时的动作**——① 给已有超表加列｜② 新建超表｜③ 无需改结构

| | ① 加列 | ② 新建超表 | ③ 无需改 |
| --- | --- | --- | --- |
| **A 单超表** | ✅ 可行。`ADD COLUMN` 是元数据操作（与数据量无关，台账 #92）。失败行为：列名重复 / 改类型被拒；错误码 `not support alter column with option except compress`（台账 #92）。代价：列集合 = **全平台属性并集**，宽表随类型增多变宽；加列补不出历史 | 不适用（单表不需要） | ⛔ 不成立：TDengine 列必须预定义 |
| **B 一类型一超表** | ✅ 可行，语义最干净。失败行为：**同一设备换型时子表名跨超表冲突**（子表名库内全局唯一，`1565`）；错误码 `Table already exists in other stables`（台账 #181）。代价：跨类型查询要 `UNION ALL`；换型必须换 `deviceId` | ✅ 可行，是"注册即建表"的自然形态。失败行为：建表成功而档案未落 → 孤儿超表；错误码 `1565`（叶子名冲突）。代价：超表数 = 类型数，建表与建子表必须同一条注册流程 | ⛔ 不成立：新类型必然是新列集合 |
| **C 一测点一超表** | ⛔ 不成立（窄表列固定为 ts/value/unit） | ✅ 技术上可行。代价极大：**与现有降采样设计不兼容**（DS 是宽表四聚合，按测点算 sum/count/min/max 语义不同）；查询需大量 JOIN/转置 | ⛔ 不成立：新测点必须是新超表 |

**两个维度之外的两条硬约束**：① 无论选哪个，注册一个采集点要建 **1 张原始子表 + 3 张降采样子表**，且子表名 `{deviceId}_{pointKey}` 库内唯一；② **降采样列必须由模型推导**——否则新增属性后降采样环缺列，整级失败（判据 C 的后半句）。

## 4. 【AI 判断】倾向与理由（不是结论）

**成本结构以核验时的真实规模为准**：此前把"存量 12,353 张子表"当作选 A 的理由。核验时本机库是 `wewant_iot` 100 张 + `wewant_iot_ds` 300 张，那批存量在当前环境并不存在；按 100 台 ×（原始 1 + 降采样 3）计，任何方案的迁移面都远小于当初的假设。**A 与 B 因此是真正开放的选择**；若某个环境确存上万张残留，先重建库再评估，不要用残留规模去论证方案。

| | A 单超表 + 加列 | B 一类型一超表 + 新建超表 |
| --- | --- | --- |
| 判据 C 的形态 | 靠"加列"，新属性会改动**所有类型共享**的表 | 新类型 = 新超表 + 新降采样超表，**不触碰既有表** |
| 不可逆范围 | 列名与列类型的影响面是**全平台** | 影响面限制在**单一类型**内 |
| 类型在存储层 | 不可见，只能靠标签或档案 | 天然可见（超表即类型） |
| 跨类型查询 | 直接查 | 需 `UNION ALL` |
| 设备换型 | 加列即可 | **不可行**，须新 `deviceId`（子表名跨超表冲突 `1565`） |
| 宽表增长 | 属性并集，随类型数增长 | 每表只含本类型属性 |

**倾向改为 B + ②（一类型一超表 + 新建超表）**，理由三条：

1. 判据 C 在 B 下是**自然形态**：新类型不动既有表，注册流程只有一条路径
2. **两处不可逆（列名、列类型）的影响面被限制在单一类型内**——A 下任一类型的属性定义都在放大全平台的宽表
3. 清理后迁移成本已不构成否决理由

**必须同时接受的代价**：跨类型查询要 `UNION ALL`；同一设备不能换型（换型 = 换 `deviceId`，等于换一台设备）；超表数量随类型增长。

**反方（仍选 A + ①）的成立条件**：如果 D2 讨论中你认为"设备会频繁换型"或"跨类型联合查询是主路径"，A 更合适——但那意味着接受"类型边界在存储层不可见"。

⚠️ 无论 A 还是 B，**降采样列、列类型、属性 key 三样都必须在写第一行数据前定死**。

## 5. 决策人的两处担心（2026-11-01 原话要点）

1. **怕被前序遗留绑住**：为了迁就已有结构做成"四不像"，同时又给后面留新债，最终大量返工或做不出能用的东西。
2. **怕做成玩具**：和可落地的产品差距太大，生产上不了。

这两条各自有可核的落点，不用停留在感觉上：

| 担心 | 落到哪里核 | 本增量已表态的处置 |
| --- | --- | --- |
| 迁就与返工 | D2 矩阵的每一格都标了"代价"；定稿时逐条写"这条是迁就过去的约束，还是现在付代价换自由" | 契约 `value: number`、三测点全 `FLOAT`、降采样列写死 → **改正**；子表存量 → **只读审计已落地，清库走开发环境重建（核验时 100/300）**；"worker 不碰 PG" → **重估为目标而非约束**。详见 [L1 §2](README.md) |
| 玩具 vs 产品 | 单独一张"离生产还差什么"表，与判据分开记——**判据通过 ≠ 生产可用** | 无认证 / 无 TLS、无备份自动化、单实例、无指标出口、无物模型迁移 → 列为本增量**接受代价**并挂触发点；下行 → 留模型与主题位置，实现排后续增量 |

**判据与生产可用是两件事**：本增量的判据只要求"注册即可接入、不改代码"，它能被满足而产品仍然不是生产级。两张表并存，不用判据掩盖第二条。
