## 0. 这个决策锁死什么

| 项 | 定错的后果 |
| --- | --- |
| 时间戳边界 | "数据缺失"与"设备没上报"分不清；错钟数据污染查询；K 之外的数据永远不被聚合且不报错 |
| 报文上限 | 热路径内存没有上界；一条超大报文能把队列 Redis 撑爆 |
| 单位换算 | 已大半定，剩读侧怎么表达 |

## 1. 已定的前提（不重开）

1. 单位在模型内不可变；写入侧拒绝与声明不符的单位；单位列已取消
2. 载荷 `ts` 是**设备事件时间**，毫秒；主键等价于 `(deviceId, ts)`
3. 降采样环只重算最近 K 个已闭合窗口（默认 K=3）
4. 同一 `(设备, ts)` 的第二条不同读数会被静默覆盖（增量 2 已登记）

## 2. 4.1 时间戳边界

### 现状

`apps/iot-worker/src/detection.ts:110` 只校验 `isFiniteNumber(ts)`——不设任何上下界。

三个已知后果：

- 错钟设备（时钟快）发来的远期 `ts` 会污染按时间范围的查询
- 落在降采样 K 之外的 `ts` **永远不会被聚合**，且不报错
- 事后无法区分"这段没数据"是因为没上报、被丢弃，还是落在 K 之外

### 业界参照

阿里云 IoT：属性上报时间**仅支持未来 24 小时内**；不传 `time` 则云端生成（台账 #182）。这是"拒未来、放过去"的形态。

### 需要定的三件事

**(a) 未来上界**：`ts` 允许超前多少？候选空间：不设 / 分钟级（如 +5 min）/ 小时级（如 +24 h）

**(b) 过去下界**：`ts` 允许回溯多久？候选空间：不设 / 天级 / 与原始数据保留期同量级

- 补传是**合法场景**（设备断网后补几天数据），所以过去的硬边界不是"数据合不合法"，而是"聚合会不会漏"
- 与 K 的关系：超过 `K × 窗口` 的数据必然聚合不到，设不设过去下界它都不会被聚合

**(c) 超界处置**：拒收 / 收下并打标 / 用平台时间替代

| 处置 | 失败行为 | 代价 |
| --- | --- | --- |
| 拒收 | 错钟设备的全部数据被挡在门外——**一次时钟错误等于一台设备长期失联** | 最严格，但故障面大 |
| 拒收 + 计数告警 | 同上，但运维能看到 | 需要告警接收方（当前没有，见 backlog） |
| 收下并打标 | 数据进库，但标记"时间可疑" | 需要一列或一张旁表；列名固化后不可加 |
| 用平台时间替代 | 不丢数据 | 事件时间被替换，与"设备事件时间"的语义冲突，且掩盖了设备错钟 |

## 3. 4.2 报文大小上限

### 现状

`apps/nestjs-server/src/modules/iot/telemetry/telemetry-producer.ts:113` 的 `send(raw)` 直接 `queue.add`，**不校验字节数**。进队列的最大报文由 EMQX 的报文上限决定，本仓未显式配置，取值未核实。

后果：单条超大报文会进入 BullMQ 的 job，占用队列 Redis 内存；解析时还要整体 `JSON.parse`。「本地缓冲」路径按字节计，也会被一条大报文顶到上限。

### 需要定的两件事

**(a) 上限值**：平台自己设多大？（候选：64 KB / 256 KB / 1 MB——按"一条报文要装多少测点"反推）

**(b) 超限处置**：拒收并计数 / 拒收并断开连接 / 只记日志放行

- 断开连接是 MQTT 层的手段，能挡住恶意客户端；但对正常误配置的设备过于激烈
- 拒收并计数不打断连接，与现有"未知设备丢弃 + 计数"的形态一致

## 4. 4.3 单位换算口径（收尾）

已定：**写时不转换**，载荷单位与模型声明不符即拒绝；单位列已取消；展示单位在读取层换算。

剩下一条要表态：**读侧接口是否返回单位**。建议返回（从模型读），否则前端要自己维护一份单位表。

⚠️ 一条要同时作废的旧方向：增量 2 轴 4 记的是"采集上来要做一次**归一化转换**"。单位不可变之后，一列之内单位恒定，**没有可归一化的东西**——该方向作废。

## 5. 定完之后，什么能证明定对了

1. 错钟设备（`ts` 超前超过上界）的数据被拒，且有可数的计数
2. 合法的补传数据（在 K 之内）不被误拒
3. 超大报文在**入队之前**被拒，队列 Redis 内存不随报文大小增长
4. 单位不符的报文被拒且不落行；读接口返回的单位来自模型

## 6. 复查触发点

| 条件 | 复查什么 |
| --- | --- |
| 接入第一台真实设备并出现时钟漂移 | 未来上界是否过紧 |
| 出现大规模补传（断网数天后一次性上传） | 过去下界与 K 的关系 |
| 队列 Redis 内存出现异常增长 | 报文上限是否缺失或过大 |
