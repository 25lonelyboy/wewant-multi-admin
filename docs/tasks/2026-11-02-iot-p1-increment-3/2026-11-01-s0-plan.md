# S0 · 债务清理与护栏：设计与实施计划

- **日期**：2026-11-01｜上承 [范围定稿](2026-11-01-scope-and-task-map.md) S0
- **出口**：① 开发库回到"表存在 ⇔ 已注册"的干净基线；② 库与代码的漂移能被只读审计发现；③ 对账脚本空跑必红；④ e2e 不再留下行；⑤ worker 卡死可被 `docker ps` 看出来
- **不依赖任何 D 决策**——这是它排在第一步的原因

## 1. 形状

| # | 任务 | 性质 |
| --- | --- | --- |
| T1 | 重建开发库卷 | 一次性清库：`down -v` → `ops:env-up` → `tdengine:init`，得到 400 张表基线（100 台 × 原始 1 + 降采样 3） |
| T2 | 只读子表审计 | 长期守卫：四桶、退出码，**不提供任何删除入口** |
| T3 | 对账脚本空过护栏 | 判据防伪 |
| T4 | e2e `finally` 删行 | 停止制造新残留 |
| T5 | worker 健康检查 | 可见信号 |
| T6 | 文档 | 事实源同步 |

**为什么审计不带删除能力**：删除路径以后会有第二条——D3 的注销流程。两套删除机制并存时，最容易出现「一套删了、另一套以为还在」。开发环境的清库交给 T1，正式流程的删除由状态机统一决定。

**两条事实前提**：

- 现有 e2e **不建表**（`apps/iot-worker/test/*.ts` 里除 `schema.test.ts` 的字符串断言外无 `CREATE TABLE`），用例只写行 ⇒ e2e 清理只需管行
- 阶段地图记的存量 12,353 张表是历史探针与旧版测试遗留，来源无法从现有代码确认；**核验时本机为原始 100 / 降采样 300**（见 [验收记录](2026-11-02-s0-baseline.md)），那批存量在当前环境不存在

## 2. 设计

### 2.1 重建开发库（T1）

`docker compose down -v` → `pnpm ops:env-up` → `pnpm --filter @multi-admin/iot-worker run tdengine:init`。

- 会一并清掉 PG / TDengine / EMQX / 两个 Redis 的卷；PG 由 migrate + seed 重建
- 执行前记录当前表数与库大小，执行后核对表数 = 400
- 若重建后发现表数不等于 400，先查注册表与建表脚本的差，不要继续往下做

### 2.2 只读子表审计（T2）

入口：`pnpm --filter @multi-admin/iot-worker run subtable:audit [--json] [--list-all]`

**期望集**：注入的 `expectedProvider: () => SubtableRef[]`，当前返回 `p1DeviceRegistry.allSubtables()`（折小写）+ `dsSubtableName()` 推三级；D3 之后换成 PG 里的 ACTIVE 档案，脚本主体不动。审计主体写成 `auditSubtables(sql, provider)`，供单测注入空集或少量表。

**四桶**：

| 桶 | 含义 | 报告里的处置建议 |
| --- | --- | --- |
| 孤儿原始子表 | 表在、注册表里没有 | 开发环境重置库；正式流程走注销 |
| 缺失原始子表 | 注册了、表不在 | 重跑建表；不自动补 |
| 孤儿降采样子表 | 三级别同上 | 同上 |
| 缺失降采样子表 | 同上 | 同上 |

**行为**：

- 任一桶非空 → 退出码 1
- 默认打印四桶计数 + 每桶前 20 个名字；`--list-all` 打全量；`--json` 供将来接 CI 或监控
- **空期望闸**：注册表读出 0 台设备时直接报错退出，不做判定——否则一次加载失败会把全库判成孤儿

**数据来源**：`information_schema.ins_tables`，按 `db_name` + `stable_name` 区分原始（`telemetry`）与降采样（`telemetry_1m` / `_1h` / `_1d`）。实现前先 `DESCRIBE information_schema.ins_tables` 核列名；不可用时退回 `SHOW <db>.TABLES`，但那样拿不到父超表，需重新设计。

### 2.3 对账护栏（T3）

`apps/iot-worker/src/downsample/verify.ts` 加纯函数 `emptySideFailures(result)`：`expectedCount === 0` 或 `actualCount === 0` 各返回一条失败描述；脚本把它计入 `failed`。

- 提示语给动作：按数据最后时间戳用 `--now` 取窗口，或先起流量
- **不加 `--allow-empty`**：要观察空库就别跑这个脚本；加了开关，下一次空过又会有人打开它
- 单测进 `downsample-verify.test.ts`，注入假查询，不需要容器

### 2.4 e2e 清理（T4）

`apps/iot-worker/test/consumer.e2e.ts` 两个用例的 `finally` 补删除，按既有惯例（`DELETE … WHERE ts >= X AND ts < Y`）：

- 降采样行先删：同一区间覆盖到的 **1m / 1h / 1d 三级窗口**（另一个开着降采样环的 worker 会把同一段算成三级各一行；只删 1m 会留下 1h/1d 的残留）
- 原始行后删：子表名由 `p1DeviceRegistry.resolve('sim-001', …)` 得 `deviceId` 后拼 `{deviceId}_001` 折小写

顺序不能反：先删原始行的话，环可能在两步之间把窗口算出来、留下一条孤立的聚合行。

### 2.5 worker 健康检查（T5）

**心跳**（新 `apps/iot-worker/src/heartbeat.ts`）

- 键 `${TELEMETRY_QUEUE_PREFIX}:worker:hb:${os.hostname()}`，值 `{pid, ts}`，**TTL 30 s，每 10 s 刷新**
- 带主机名：多实例时不会被另一个健康实例顶掉
- TTL：进程卡死时键自己过期
- Redis 封装在 `src/redis-store.ts`（`RedisLike` 接口 + `createRedis`），心跳与探针共用；连接独立、`enableOfflineQueue:false`、失败只记一次 warn
- 定时器与存储都可注入 ⇒ 单测覆盖刷新、失败只记一次、`stop` 清定时器并删键，不需要真 Redis
- 接进 `src/index.ts`；`shutdown` 里先 `clearInterval` 再 `process.exit`，否则定时器吊住事件环

**探针**（新 `apps/iot-worker/src/healthcheck.ts`，编译为 `dist/healthcheck.js`）

- 读 `QUEUE_REDIS_URL` 与容器主机名（`os.hostname()` 与进程写键时同源），`GET` 心跳键，无值退出 1
- 用编译入口而不是 `node -e require('ioredis')`：镜像 `WORKDIR /repo/apps/iot-worker` 能解析，但依赖 pnpm 的链接结构，编译产物更稳
- compose：`interval 30s / timeout 5s / retries 2 / start_period 30s`

**它测什么、不测什么**（同时写进代码注释与文档）

- 测：**事件环停摆**、**队列 Redis 不可达**
- 不测：**消费卡住但事件环正常**（单个 promise 永远 pending）——那要指标，归增量 6
- ⚠️ compose 不会因 unhealthy 自动重启；这是可见信号，也为将来 K8s 的 liveness 铺路

## 3. 顺序与验收

```text
T1（确认后）→ T2 → T3 → T4 → T5 → T6
```

| 验收 | 怎么证明它真的能红 |
| --- | --- |
| 干净基线 | T1 后审计退出 0、表数 = 400 |
| 审计能红 | 手工建一张 `probe_x` 子表 → 退出 1 且点出名字 → 删掉恢复 0 |
| 空期望闸 | 单测：`auditSubtables` 传空 provider → 抛错，不打印四桶 |
| 护栏能红 | 无流量时跑 `downsample:verify` → 退出 1，文案提示用 `--now` 或起流量 |
| e2e 不留行 | 连跑两次，`sim-001` 子表行数前后一致 |
| 健康检查能红 | healthy → `kill -STOP` 主进程 → **≤90 s** 变 unhealthy（键过期 ≤40 s + 两次探测）→ `kill -CONT` 恢复 healthy |
| 文档 | `pnpm doc:lint` 全绿 |

## 4. 危险动作

| 动作 | 影响 | 闸 |
| --- | --- | --- |
| `docker compose down -v` | 清掉 PG / TDengine / EMQX / 两个 Redis 的全部卷 | 只在本地开发环境；执行前单独确认，并记录当前表数与库大小 |
| `kill -STOP` 测健康检查 | 临时挂起 worker 进程 | 测完 `kill -CONT` |

## 5. 不做

- 审计脚本的删除能力（删除归 T1 的重置与 D3/D5 的注销流程）
- 自动重启（compose 不因 unhealthy 重启；留 K8s 阶段）
- 专用测试库隔离（属测试基建，单独立项）
- 消费进度指标（队列积压、写入速率）——增量 6
- 降采样读取侧按注册表裁剪（属 D3）

## 6. 环境前置

T1–T5 都需要 `pnpm ops:env-up`（postgres / redis / redis-queue / emqx / tdengine）。本机 docker 当前未启动，T1 起跑前先起环境。
