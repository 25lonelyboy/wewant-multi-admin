## 0. 这个决策锁死什么

| 项 | 定错的代价 |
| --- | --- |
| 建表归属 | DDL 与命名的来源分裂后，同一张表会有两个名字；改一次要动两处，且不会报错 |
| 注册幂等 | 客户端重试与"真失败"不可区分，运维只能靠人眼分辨 |
| 状态机边界 | 半成品表无人认领，审计口径与注册行为互相打架 |
| 重建库的边界 | 一旦测试/生产有了真实档案，重建 = 丢用户录入的数据 |

## 1. 已定的前提（不重开）

1. 两库无共同事务——「注册成功」只能是**某个可见状态**，不是"两处都写成功"
2. `PENDING → ACTIVE`；注册失败时整体回滚、档案不落库，没有失败态（D2 §11）
3. 消费者只认 `ACTIVE`
4. 审计四桶只读、无删除路径
5. 判据：「注册一台新类型设备，仓库无 diff」

## 2. 六个子问题与结论

### 2.1 入口形态

**结论**：物模型与设备档案注册走 **HTTP 接口**（`nestjs-server`，`api/v1` 下）。**本增量不做前端界面**——调用方是 curl / Postman 或脚本。

- 判据只要求"不改代码"，没要求界面；先出接口，界面随增量 4 的 iot 视图域一起做
- **鉴权复用现有的 JWT + RBAC**：注册能建 TDengine 表，不能挂在无鉴权的路由上。具体路由与权限点命名归 S4

**代价**：没有界面时，注册新类型设备要人肉拼 JSON；模型结构的复杂度（八档、结构体子字段）在命令行下容易写错。

### 2.2 谁来建表

**结论**：**server 建表**。DDL 语句写在 `nestjs-server` 内，**不进共享包**；`iot-worker` 与外部脚本此后不再执行 DDL。

**连带结论（本卡一并定）**：**命名函数进包**。

表名不是 DDL，是命名规则。现在 `rawStableName` / `dsStableName` / `dsLevelSuffix` / `dsSubtableName` 四个函数在 `apps/iot-worker/src/schema.ts`，而 `subtableName` 已在 `packages/device-registry`。server 接管 DDL 后，若不把四个函数一并移进 `packages/device-registry`（与 `subtableName` 同处），两个应用就会各定义一套表名——改了不报错，只是表建到别处去。

- `packages/device-registry`：新增四个命名函数（或与 `subtableName` 合成一个 `naming` 模块），成为表名的唯一出处
- `apps/iot-worker`：`schema.ts` 只留常量与库级配置，命名改为从包 import
- `apps/nestjs-server`：DDL 语句 + 执行，名字全部从包取

**代价**：server 多一个 TDengine 依赖（taosAdapter），与 worker 并列；两处都持连接池，容量模型要在 S4 里重新算。

### 2.3 状态机粒度

**结论**：**物模型与设备档案各一套状态机**。新建设备档案引用**已存在的物模型是常态**，不是例外。

一次"新模型 + 第一台设备"的注册，两条状态机联动，顺序被锁死：

```text
模型 PENDING → 建原始超表 + 三张降采样超表 → 模型 ACTIVE
档案 PENDING → 建原始子表 + 三张降采样子表 → 档案 ACTIVE
```

- 设备档案引用模型时，模型必须已 `ACTIVE`（范围定稿 §5 的拒绝项：引用非 ACTIVE 模型 → 明确错误码）
- 同一模型注册第二台设备时，模型那条不动，只走档案那条

### 2.4 注册幂等

**结论**：**已 ACTIVE 即成功**——提交前先查：档案已 `ACTIVE` 且四张子表齐，直接返回首次的结果，不重复建表。

- 这是**结果幂等**，不是请求幂等：不需要 requestId，也不需要额外的请求表
- 客户端超时重试天然安全
- **边界**：档案 `ACTIVE` 但表缺一张（被人误删）**不算"已注册"**——报「结构不一致」，不自动补。自动补属于修复路径，归审计与人工，不在注册流程里悄悄做

### 2.5 审计口径与失败清理

**结论**：审计的「已注册」**只认 ACTIVE**；注册过程失败时**删除本次创建的表**，**档案信息不落库**——整个注册过程失败。

- **没有失败态**：状态机只有「未注册 / 已注册」，`PENDING` 是流程内的中间态，不落库。档案表里只会出现 `ACTIVE` 行
- **超表不删**：它属于模型。若本次注册是"新模型 + 第一台设备"，模型已 ACTIVE，超表不能跟着回滚
- 所以注册流程必须记录**本次创建了哪些表**，删除只针对这份清单
- **删除本身失败**（TDengine 不可用）是极少数情况：先重试；仍失败则记录并告警，留在库里的表由审计报 `orphanRaw` / `orphanDs` 认领——审计只读、无删除路径，正好兜住这一层
- 审计的期望集 = 由 `ACTIVE` 档案推导

**代价**：注册失败在库里不留任何档案痕迹，排查只能靠应用日志；残留表由审计认领，但认不出属于哪一次注册。

### 2.6 设备上电与注册的先后

**结论**：正常流程是**先注册、后通电**。先通电未注册时，报文照现在的行为处理——**查档失败、丢弃、计入 `rejected`**。

- 异常通知与消息落档**本增量不做**，后续规划；届时给出人工重新处理的途径
- 现场违规序时，现象与设备掉线相同（D4 的时钟偏差也是同一类：不同原因、同一现象），排查时要先看 `rejected` 计数

## 3. 重建库的边界（本次一并定）

补齐脚本保留，但**它只是开发阶段的权宜之计**。

| 环境 | 能否重建库 | 演进方式 |
| --- | --- | --- |
| 本地开发 | 能（`down -v` + `ops:env-up` 的补齐脚本） | 随便 |
| 测试 / 生产 | **不能**——档案里已有用户录入的数据 | 表结构只能就地演进：`ADD COLUMN`、停写，不重建 |

由此推出三条硬约束：

1. **表结构变更只走 `ADD COLUMN`**（D2 §11 已定），不靠重建
2. **e2e 不得假设可以清库**：每个用例自清理自己写入的数据（S0 已落地的 `finally` 删除），新建的表要能被审计识别或自己删掉
3. **补齐脚本的定位**：开发环境把"档案有、表没有"补回来；它不构成测试/生产的恢复手段

这条已登记 backlog，作为 e2e 与迁移路径的长期约束。

## 4. 定完之后，什么能证明定对了

1. 建表中途失败 ⇒ 档案不存在，查档不成功——不出现"查到了却写不进去"
2. 同一份注册请求重复提交 ⇒ 返回成功且不重复建表
3. 注册中断后重跑 ⇒ 不产生第二套表，也不把已存在的表判成错误
4. `FAILED` 留下的残留表由审计报 `orphan`，不需要人工翻库
5. 注册一台新类型设备全程不需要人工执行 DDL
6. 未登录调用注册接口被拒（401），有权限的账号可以注册
7. 档案 `ACTIVE` 但表被误删 ⇒ 报「结构不一致」，不静默重建

## 5. 复查触发点

| 条件 | 复查什么 |
| --- | --- |
| 出现第二个操作者 / 需要权限分级 | 是否要从"有 JWT 即可"细化到权限点 |
| 单次注册耗时超过数秒，或需要批量导入 | 是否要异步化、要不要批量接口 |
| 测试环境首次需要在线变更表结构 | `ADD COLUMN` 在大表上的锁与耗时（未实测） |
