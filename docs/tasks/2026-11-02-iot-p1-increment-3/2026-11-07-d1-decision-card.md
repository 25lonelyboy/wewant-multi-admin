# D1 决策卡 · 档案承载与 worker 读取

- **状态**：已定稿（2026-11-07），八个子问题全部收口
- **日期**：2026-11-07
- **落点**：S5（消费与降采样接线）开工前
- **前置材料**：[D1 前置材料](2026-11-06-d1-input.md)（四个本仓事实、三种形态、判据 A 的四条可验条件、按轴自检）
- **不重开**：D2 §11（版本快照与 tri-state）、D3（注册原子性）、D4（时间戳与报文上限）。本卡只定 **worker 从哪里、以什么形态读到档案与模型**，以及由此推出的生效口径

## 0. 这个决策锁死什么

| 项 | 定错的代价 |
| --- | --- |
| worker 的进程依赖 | 定了直连就多一个 PG 连接池与 schema 依赖，两个应用对同一张表各有一份理解，改表时不会报错 |
| 「生效」的口径 | 判据 A 只说「不重启」，没说多久；没定口径，验收时无法判定通过与否 |
| 多实例的一致性 | worker 可多实例；形态若带进程内状态，实例间会答出不同结果 |
| 数据口径的时间边界 | 定错会让模型演进期间的数据按错误声明解释，且事后无从分辨——本卡最主要的目的就是消除这一类不可追溯错误 |
| 失效与回退 | 档案改错时怎么撤回；读不到档案时的行为 |

## 1. 已定的前提（不重开）

1. **判据 A**：注册一条档案 + 一个物模型（纯数据），不重启 worker 即可查档成功、落库到新子表
2. **平台侧标识不下发设备**（S0.5）：设备只报 `localDeviceId`，`deviceId` 由平台签发
3. **队列 Redis 与业务缓存是两个实例**（ADR-010 D4）：BullMQ 要求 `noeviction`，是实例级配置
4. **D2 §11 的版本快照已含 `effectiveFrom` / `effectiveTo`**，且 §11.3 的原意就是「按时间取当时的声明即可判定」
5. **注册失败整体回滚、档案不落库**（D3 §2.5）：PG 里没有失败态行
6. **列集合只增不减**（D2 §11.4）：`ADD COLUMN` 传播到已有子表，废弃属性永久占列

## 2. 八个子问题与结论

### 2.1 形态：快照 + 本地全量

**结论**：server 把「全部 ACTIVE 档案 + 全部版本声明」写成一份**带单调版本号的全量快照**，放进**业务 Redis**；worker 本地持一份全量，按版本号轮询更新。

否决的两种形态见 §6。选择快照的理由不是性能，是两条：

- **报文处理路径不依赖外部服务可用性**。本地全量之后，热路径上一次查档就是 `Map.get`，不产生网络往返
- **模型声明的反序列化成本远高于档案映射**，不宜逐条做

⚠️ 「性能」不是主要理由。一万台设备的快照约 750 KB、加模型声明约 1 MB；每 500 毫秒 GET 一个几字节的版本号，相对 BullMQ 自身的 Redis 操作量是 1% 量级。**贵的不是读几次，是每次读多少。**

### 2.2 快照的内容边界：一份全量，三合一

**结论**：档案、模型声明、量程**合成一份**。形状：

```ts
interface RegistrySnapshot {
  version: number;                    // 单调递增，来自 iot:registry:rev
  builtAt: string;                    // ISO
  models: Array<{
    modelCode: string;
    versions: Array<{
      version: number;
      effectiveFrom: string;          // 非空
      effectiveTo: string | null;     // null = 无后继
      properties: PropertyDecl[];     // 有序，含 kind / unit / range / aggregates / varcharLength
    }>;
  }>;
  devices: Array<{
    localDeviceId: string;            // 已 normalizeLocalId
    deviceId: string;
    modelCode: string;
    fromAt: string;
    toAt: string | null;
  }>;
}
```

**为什么不分三份**：

- 量程本来就是 `PropertyDecl.range`，随属性走。拆出去要维护两套刷新
- 档案与模型必须**同时**替换。分开刷新必然出现「档案已新、模型还旧」的窗口——正是本卡要消除的那类错配
- 列绑定要求「最新的列序 + 按 ts 选出的值」，两者必须来自同一份快照

**连带结论**：`DEFAULT_METRIC_RANGES` 删除。它按 P1 三个 key 写死，对新模型无意义；判据 B 也要求量程来自物模型，不来自这个常量。

⚠️ **随之而来的后果**：`PropertyDecl.range` 是可选的。模型没声明量程 ⇒ **不校验**。若要求数值档位必须有量程，那是改 S3 的校验器把 `range` 变成必填，不属本卡。

### 2.3 口径：按数据的时间戳，不按处理的时刻

**结论**：一条数据属于哪个模型、哪个版本，由**它自己的 `ts`** 决定，与 worker 何时处理它无关。

判定链路：

```text
localDeviceId + ts
  → 命中哪条 usage（fromAt ≤ ts < coalesce(toAt, ∞)）→ deviceId / modelCode / 子表名
  → 命中哪个版本（effectiveFrom ≤ ts < coalesce(effectiveTo, ∞)）→ 该时刻的声明
  → 列绑定用「当前超表的列集合」（= 最新版本的列集合，因为 ADD COLUMN 只追加）
    值取「该版本声明里有、且报文带了的属性」，其余 NULL
```

**列序与口径必须分开**：STMT 按位置绑定列。超表当前列序是所有版本列的并集，v1 的列序只是它的前缀；一条 v1 时期的晚到数据若按 v1 列序绑定，整行错位且不报错。**绑定用最新列序，值按 ts 选版本。**

这条同时消除了三类不可追溯错误：晚到数据、BullMQ 重试（退避可达分钟级）、多实例不同步。

**边界与兜底**：

- 区间取半开 `[from, to)`
- `ts` 早于该模型最早版本 → 丢弃 + 计数
- `ts` 时刻设备没有 open usage → 丢弃 + 计数
- 两类计数分开：`unknown-device`（设备不在快照）与 `out-of-range-ts`（在快照、但 ts 不落在任何区间）

⚠️ 这条建立在 **`ts` 可信**上。D4 已接受「错钟设备的全部数据会被拒」，本卡不改该代价，只是把它延伸到口径判定。

### 2.4 版本区间与排期

**结论**：`ACTIVE` 只描述**发布流程**，**「此刻生效的是哪一版」一律由区间推出**。不设 `SCHEDULED` 状态，不设状态推进器。

- 发布 v2（`effectiveFrom` 可在未来）的同一事务里：v1 → `SUPERSEDED`、`effectiveTo = v2.effectiveFrom`；v2 → `ACTIVE`
- `SUPERSEDED` 的含义是「已被后续版本排期覆盖」，**不代表已失效**
- 「同一模型至多一个 ACTIVE」的 partial unique index 因此**保留不动**

**允许指定未来的生效时刻**。由它带出的五条约束：

1. 新版本的 `effectiveFrom` 必须**严格大于**当前最新版本的 `effectiveFrom`。不做回溯——回溯会改写历史数据的解释
2. **不做连锁推移**。改期若与后继版本重叠，拒绝，由操作者按顺序处理
3. **改期同时改前驱的 `effectiveTo`**（`v1 [t0,t3)` 中 v2 从 t3 改到 t5 ⇒ v1 变 `[t0,t5)`）。这段区间在未来、尚无数据，安全
4. **撤销只删版本行，不删列**（D2 §11.4）。撤销「唯一且未生效」的版本会让模型变成没有版本的空壳——**允许**，否则会形成「想撤销必须先发新版」的死循环
5. **版本号不复用**。撤销 v2 后再发布就是 v3，`max(version)+1` 天然跳号
6. 改期与撤销都**只能作用于 `effectiveFrom > now` 的版本**

**档案也支持排期，同一套机制**：

- 子表立即建（物理提前、逻辑延后，与模型一致）
- `IotDevice.status` 立即 `ACTIVE`
- `IotDeviceModelUsage.fromAt` = 指定时刻；worker 按 `[fromAt, toAt)` 判定
- **已排期未生效的设备算「已注册」**：同一 `localDeviceId` 再提交走幂等返回，不新建
- 设备的改期与撤销**归 D5**，与注销共用一套语义

### 2.5 A4 时延口径与负结果缓存

**结论**：A4 定义为

> 注册或发布接口返回 200，到**所有** worker 实例的本地快照 `version ≥ 该次变更的 rev`，**P99 ≤ 2 秒**。

「所有实例」不是保守：降采样环每个实例都跑，消费环上一条报文落到哪个实例是随机的。

实现与预算：

| 环节 | 预算 |
| --- | --- |
| 变更 → 重建写快照 | ≤ 1.0 秒（重建节拍 500ms + 重建约 100ms） |
| 重建 → worker 拉到并应用 | ≤ 0.7 秒（轮询 500ms + 拉取应用 200ms） |

**worker 轮询间隔定 500ms**（每实例 2 QPS，成本可忽略）。1 秒轮询会让最坏值逼近 2.5 秒，验收踩线。

**怎么测**：worker 把自己当前的 `snapshot.version` 写到 `iot:registry:worker-version:{instanceId}`（TTL 30 秒）。验收脚本轮询这些 key，取「全部实例都 ≥ 目标版本」的耗时分布。不写死测法，A4 到了验收会各说各话。

**负结果缓存删除**。快照本身就是缓存——「设备不存在」是快照的一个正常状态，随快照刷新自然消失。保留一个 5 分钟 TTL 的负结果层，等于给 A4 加一个 5 分钟的下界。

### 2.6 刷新与兜底

**写路径**（任意 iot 写入口，PG 事务提交之后）：

```text
INCR iot:registry:rev
→ 接口立即返回，不做任何重建
```

批量导入 100 台 ⇒ 100 次 `INCR`（微秒级），不是 100 次扫 PG。

**重建器**（server 侧一个 provider，每 500ms 一轮）：

```text
snapshot key 不存在          → 重建
GET rev > 已知已建版本        → 重建
否则                          → 空转
```

- **节流，不是 trailing debounce**：每 500ms 最多一次、持续脏就持续重建。只在「最后一次变更后 X 毫秒」重建会让一次跑 30 秒的批量导入期间新设备全都不可见
- **条件写**：Lua 比较版本再写，版本永不倒退。这一步保证正确性
- **锁**：`SET rebuild-lock NX PX 2000`，只有持有者重建。锁只降低重复劳动（多实例各建一遍 = 多倍 PG 读），不承担正确性——条件写兜住了
- **检查 key 是否存在**，而不只是版本：Redis 被 flush 或 key 被淘汰时 `rev` 与快照一起消失，只比版本会永远推不动
- 重建失败：不推进「已知已建版本」，下一轮重试；连续失败记 error

**worker 侧**：

- 每 500ms `GET iot:registry:version`，大于本地版本才拉全量
- **拉取失败 → 保留旧快照继续跑**，记 error。可用性优先；滞后由下一次成功刷新纠正
- 需要一条告警阈值：「旧快照已容忍 N 秒」
- **冷启动拉不到 → 不启动消费者**，退避重试。用空快照跑会把全部数据当 `unknown-device` 丢掉，且计数看起来像设备故障。队列 Redis 与业务 Redis 是两个实例，业务 Redis 挂了队列还在——此时积压比静默丢数据好

### 2.7 降采样一致性：单写者

**结论**：降采样环**选主执行**，同一时刻只有一个实例在写。消费环不受影响，仍可多实例并行。

理由：降采样无并行收益（每级每 tick 一次、重算 K 个窗口，低频低量），而多实例并行的代价是三类不一致——模型集合不同、同一模型声明版本不同、重叠窗口乱序覆盖。单写者同时消除三者。

- 锁放**队列 Redis**（降采样的调度本来就在 BullMQ 上），不放业务 Redis
- 用「实例 id + 原子比较删除」防误删他人锁；续期失败立刻停止调度，不带着可能失效的锁继续写
- 一致性口径是**同一窗口只有一种口径**，不是「所有实例同时看到新模型」。leader 也可能在 A4 窗口内用旧集合跑一轮，但那只是滞后一个 tick，由 K 窗口重算自愈

⚠️ 今天的「一致」是**隐含前提**：所有实例的 `modelCodes` 都是同一个编译期常量，算出的值必然相同，互相覆盖无害。本卡之后该前提消失，故必须显式化成单写者。

将来降采样成为瓶颈时按 `modelCode` 哈希分片：**每个模型仍然只有一个写者**，一致性约束不变。

### 2.8 包边界

**结论**：快照类型新增到 `packages/device-registry`，**不加新包、不动 `packages/contracts`**。

- 快照由 `PropertyDecl`、`DsLevel`、表名规则拼成，全是该包的词汇；它又是**同版本发布的编译期共享类型**，不是需要版本协商的运行期契约。contracts 承载的是跨边界 wire format（前端、设备）与跨进程常量，两者性质不同
- `device-registry` 的定位收窄为：**决定「数据长什么样、叫什么、落到哪一列」的知识**。决定「什么时候写、怎么写、写到哪」的，留在应用里
- 该包**不装**：DDL 语句（server）、档案读写（server）、报文解析与写入（worker）、HTTP 与队列形状（contracts）

**连带结论**：`p1.ts` / `p1-model.ts` / `registry.ts` / 部分 `types.ts` 是编译期档案的过渡物，S5 完成后删除。物模型的声明 / 校验 / 推导（`model-validate` / `model-derive` / `column-type` / `identifier`）当前只有 server 消费，**S5 收口后挪回 `apps/nestjs-server`**。届时包内只剩命名、设备标识、快照类型三块。

## 3. 定完之后，什么能证明定对了

| 验收 | 怎么证明 |
| --- | --- |
| 判据 A | 注册一台新设备与一个新模型，**不重启 worker**，设备上报能落到新建的子表 |
| 快照一致 | 所有 worker 实例的 `iot:registry:worker-version:*` 在注册返回后 2 秒内达到目标版本 |
| 批量合并不放大 | 连续注册 100 台，重建次数 ≤ 变更时长 / 500ms + 2，不是 100 次 |
| 口径按 ts | 在模型 v2 生效后，构造一条 `ts` 落在 v1 区间的晚到报文，落库值符合 v1 声明、列序符合最新超表 |
| 档案排期 | 注册一台 `effectiveFrom` 在未来的设备，其子表已建；排期前的上报被计为 `out-of-range-ts`；到点后正常入库 |
| 降采样单写者 | 起两个 worker 实例，只有一个在跑降采样环；杀掉 leader 后由另一个接管 |
| 版本不倒退 | 并发触发两次重建，最终快照版本等于 rev，且不会出现旧版本覆盖新版本 |

## 4. 复查触发点

| 触发点 | 要复查什么 |
| --- | --- |
| 单份快照超过 10 MB | 改为按模型分片拉取；届时分片必须保持「档案与模型同一版本」 |
| 实测 P99 超过 2 秒 | 考虑加通知通道（Pub/Sub 或 Streams）把轮询压掉；**不要只删轮询** |
| server 与 worker 不再同版本发布 | 快照格式需要版本字段与兼容策略；今天不需要 |
| 单个模型版本数超过 100 | 快照随版本数单调增长，需要版本保留策略 |
| 降采样成为瓶颈 | 按 `modelCode` 哈希分片，每模型仍单写者 |
| 物模型声明被 server 之外的第二个消费者使用 | `model-validate` / `model-derive` 是否要挪回共享包 |

## 5. 本卡不含

- 设备注销、改期、撤销的语义 → D5（S6）
- 降采样跨版本窗口的算法定型 → S5 的实测（见 §7）
- 快照的 HTTP 调试接口 → 不做，排障靠 Redis 直读
- worker 内部快照索引的具体数据结构（`Map` 的键设计）→ S5 的实施细节
- 通知 / 订阅通道 → 挂 §4 的触发点，本增量不做

## 6. 被否决的候选与理由

| 候选 | 否决理由 |
| --- | --- |
| **直连 PG** | worker 对 PG schema 产生编译期发现不了的依赖；加一列要跟着改 SQL 字符串；worker 部署多一个迁移时序耦合 |
| **调 server 内部接口** | worker 的可启动性从此绑定 server，而今天两者并列独立启停；多一跳网络且服务不可用时的行为难定义 |
| **只发通知、不做轮询** | Redis Pub/Sub 不持久化、不 ack、不重放。worker 重启或网络抖动期间的通知永久丢失，之后若无变更就永久停在旧快照 |
| **快照拆成档案 / 模型两份** | 分开刷新必然出现「档案已新、模型还旧」的中间态 |
| **按处理时刻判口径** | 晚到数据、BullMQ 重试、多实例不同步都会被放大成不可追溯的口径错误 |
| **`SCHEDULED` 状态 + 推进器** | 推进器没跑或跑失败 ⇒ 数据按旧口径处理，正是本卡要消除的失效模式 |
| **同步重建（请求内）** | 批量导入 N 次变更 = N 次扫 PG |
| **多实例并行降采样** | 口径不同时同一窗口的结果不收敛；而降采样没有并行收益 |
| **快照类型放 `contracts`** | 快照由存储侧词汇构成，contracts 不含这些；且它是同版本发布的编译期共享类型，与 wire format 不同性质 |
| **保留 `ResolveCache`** | 5 分钟 TTL 与 A4 的 2 秒直接冲突；全量快照之后 `resolve` 就是一次 `Map.get` |
| **保留 `DEFAULT_METRIC_RANGES`** | 按 P1 三个 key 写死，对新模型无意义；判据 B 要求量程来自物模型 |

## 8. 来源等级
