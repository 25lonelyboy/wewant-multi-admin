# D3 前置材料 · 注册原子性、入口形态、状态机与孤儿处置

- **用途**：[D3 决策卡](2026-11-01-scope-and-task-map.md) 的项级背景。只给约束与候选空间，**不替决策人选题**
- **日期**：2026-11-05
- **上承**：范围定稿 §3——D3 锁「跨库一致性」与「谁来建表」，必须在 **S2 / S4 开工前**定
- **不重开**：D2 §11 已定版本快照与 `PENDING / ACTIVE / FAILED` 三态；本页只问**谁来驱动迁移、失败时谁收拾**

## 1. 问题是什么

一条注册要同时落两处：

- **PG**：档案（设备 ↔ `deviceId` ↔ 模型）、模型声明、版本快照
- **TDengine**：超表（新模型）、降采样超表、原始子表、降采样子表

**两库没有共同事务**。所以"注册成功"不能定义成"两处都写成功"——那件事做不到——只能定义成某个**可见状态**：下游在什么条件下承认这台设备、这些表。

## 2. 本仓的四个事实

| # | 事实 | 位置 | 对 D3 的含义 |
| --- | --- | --- | --- |
| 1 | **DDL 全在 worker 应用**，唯一调用方是建表脚本 | [schema.ts](../../../apps/iot-worker/src/schema.ts)、[tdengine-init.ts](../../../apps/iot-worker/scripts/tdengine-init.ts) | 注册路径在 server 侧。server 要建表，得先把 DDL 搬进共享包；否则只能让 worker 代建 |
| 2 | **审计四桶、只读、无删除路径** | [audit.ts](../../../apps/iot-worker/src/subtables/audit.ts) → `orphanRaw` / `missingRaw` / `orphanDs` / `missingDs` | 判据是「表存在 ⇔ 已注册」。**PENDING / FAILED 的档案算不算"已注册"，直接决定注册中途失败的表会被判成孤儿还是缺失** |
| 3 | **消费者只认 ACTIVE**（设计口径，S2 落地） | D2 §11、范围定稿 S2 | 顺序被锁死：先建表、后置 ACTIVE。反过来会出现"查档成功但写入必然失败" |
| 4 | **档案现在是编译期常量** | [p1.ts](../../../packages/device-registry/src/p1.ts) | S2 换成 PG 之后，worker 读档案要穿过 PG——那是 D1 的题目，但 D3 定的状态机决定了 D1 要读到什么 |

## 3. 行业参照：SiteWise 的 latest / active

三条事实（来源等级见 §7）：

- 定义先落 **latest**，校验通过才 propagate 为 **active**
- 失败进 **FAILED**，**下游继续用上一 active**——不是停摆
- latest 与 active 是**同一对象的两态**，不是两份数据

对本仓的含义：**状态机替代补偿事务**——把一致性从「写入时刻」挪到「读取时刻」。写入侧允许中途失败，读取侧只认 ACTIVE，于是"半成品"天然不可见。

⚠️ 与本仓的差异：SiteWise 的 active 是**模型**层的；本仓有**两个对象**要管状态——档案（设备）与模型版本（D3 要定这两个状态机是一个还是两个）。

## 4. 三种失败形态

| 失败点 | 现象 | 谁能发现 | 今天能不能发现 |
| --- | --- | --- | --- |
| 档案写了、表没建 | 查档成功，写入必然 `Table does not exist` | 写入报错（B 类，进 failed 集合） | ✅ 能 |
| 表建了、档案没置 ACTIVE | 表存在但无人认领 | 审计判孤儿 | ⚠️ 取决于 §2 第 2 条的口径 |
| 超表建了、子表建了一半 | 同上，且降采样整级可能失败 | 审计 + 降采样对账 | ⚠️ 同上 |

## 5. 需要决策人回答的子问题

每项只给"要定什么"与"只有你能答的部分"。

### 5.1 入口形态

**要定什么**：注册是一条 HTTP 接口、一个运维脚本，还是两者都要？

**只有你能答的部分**：P1 阶段谁在注册设备——只有你自己，还是要有界面？如果只有脚本，状态机可以简单得多（失败就重跑），但 S4 的"注册一台新类型设备，仓库无 diff"这条判据是否要求"不经代码"？判据原文没说是脚本还是接口。

### 5.2 谁来建表

**要定什么**：TDengine DDL 由谁执行。

候选空间（不排序）：

- server 直连 TDengine 建表 → **DDL 必须从 worker 搬进共享包**，且 server 多一个下游依赖
- worker 代建（server 投一条建表 job）→ DDL 不动，但**注册依赖 worker 在跑**，且注册变成异步
- 保持外部脚本（`ops:tdengine-init`）→ 注册流程不建表，靠脚本补；与"注册即接入、不改代码"的判据冲突

### 5.3 状态机的粒度

**要定什么**：档案（设备）与模型版本各有一套 `PENDING → ACTIVE / FAILED`，还是合成一套？

**只有你能答的部分**：一台设备注册时，模型可能是**已存在的**（复用别人用过的模型）。这时是"模型版本 ACTIVE + 档案 PENDING → 建子表 → 档案 ACTIVE"，还是"一个注册事务同时驱动两者"？

### 5.4 审计对 PENDING / FAILED 的口径

**要定什么**：审计的"已注册"集合包含哪些状态的档案。

- 只含 ACTIVE → 中途失败建出来的表被判孤儿，**注册失败每次都要人工清表**
- 含 PENDING 与 ACTIVE → 中途失败的表不算孤儿，但"表存在 ⇔ 已注册"这条不变量被放宽成"⇔ 曾尝试注册"
- 只含 ACTIVE，且 FAILED 时自动清理表 → 审计口径不变，但注册流程多一条删除路径（而审计工具本身是无删除路径的）

### 5.5 重试语义

**要定什么**：注册失败后重跑，遇到"表已存在"怎么办。

`CREATE ... IF NOT EXISTS` 让建表天然幂等；但**加列**（模型内演进）不是——重复 `ADD COLUMN` 会报列已存在。这条与 D2 §11 的"加属性走 ALTER"直接相关。

## 6. 定完之后，什么能证明定对了

1. 建表中途失败时，**查档不会成功**，或成功但写入被拒——不出现"查到了却写不进去"
2. 注册中断后重跑，不产生第二套表、也不把已存在的表判成错误
3. 审计对注册中途失败留下的表有明确口径，不需要每次人工清库
4. 注册一台新类型设备全程不需要人工执行 DDL
5. 失败原因能落到具体某一步（建超表 / 建子表 / 置状态），而不是笼统的"注册失败"

### 8.2 轴外补充一条：设备上电与注册的先后

八条轴里没有问"操作顺序"，但它是 ① 的直接后果，且**今天就会遇到**：

设备先上电、档案后注册时，那段时间的报文全部走「查档失败 → 丢弃 + `rejected` 计数」。现象与设备掉线完全相同（D4 的时钟偏差也有同样的问题：现象相同、原因不同）。

三个可选口径（不排序）：

- **要求先注册后上电**：运维纪律，平台不做任何事。代价：现场顺序错了没人知道，只能从 `rejected` 计数倒推
- **允许先上报、丢弃并计数**：与现在行为一致，把"注册前丢多少"变成可观测的量
- **缓冲未注册设备的报文**：注册后补投。代价：缓冲有界、过期即丢，且要多一条"未注册设备"的旁路

这条不改 D3 的骨架，但要在 D3 定稿时给出一句口径——否则 S4 落地后，"设备装了没数据"会被当成接入链路故障排查。
