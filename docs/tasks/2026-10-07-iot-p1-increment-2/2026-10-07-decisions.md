## 1. 背景

**要做什么**：把遥测数据**可靠地存下来**（增量 1 只做到"看得见日志"，没存）

**现状（增量 1 之后）**：

```text
设备/模拟器 → EMQX →（iot 域通配订阅）→ 解析校验（不合法丢弃并计数）→ 每秒汇总打印日志
```

⭐ **数据到这里就没了**——只在日志里，**没有落库**。

**改完之后**：

```text
设备/模拟器 → EMQX →（iot 域订阅）→ BullMQ 队列 → 消费者 → TDengine
                                                          （状态数据留 PG）
```

**为什么现在做**：

- **M1（10/19）的 ① 项就靠它**
- 它是增量 3–5 的地基——**没有历史数据，物模型、实时监控、告警全是空谈**

**不做的后果**：数据看完就丢，**平台的"数据资产"根本不存在**。

### 4.1 TDengine 的建模模型【已核实：docs.tdengine.com，2026-10-07】

**核心建模理念：「一个数据采集点一张表」（table-per-device）**

| 概念 | 含义 |
| --- | --- |
| **指标（Metric）** | 被采集的物理量（电流、电压、温度、速度……） |
| **标签（Tag）** | **静态属性**（设备型号、位置、分组）——不随时间变化 |
| **采集点（DCP）** | 负责采集指标的硬件或软件单元 |
| **表（Table）** | **每个采集点一张表** |
| **超级表（STable）** | 一类采集点的**模板**：定义"有哪些指标列 + 哪些标签" |
| **子表（Subtable）** | 某个具体采集点的表，继承超表结构、填自己的标签值 |

**建超表**（官方示例）：

```sql
CREATE STABLE meters (
    ts timestamp, current float, voltage int, phase float
) TAGS (location varchar(64), group_id int);
```

- **第一列必须是 timestamp**
- 其余列是**测量列**
- `TAGS` 定义标签；**标签名不能与测量列同名**

**建子表**：

```sql
CREATE TABLE d1001 USING meters (location, group_id) TAGS ('California.SanFrancisco', 2);
```

**官方给出的"一设备一表"四条好处**：

1. 每个采集点数据源唯一 → **单写者 → 无锁写入**
2. 数据按时序产生 → **append-only**
3. 同一采集点的数据**块内连续存放** → 查询某时段时**减少随机读**
4. 块内**列式存储 + 按数据类型选压缩算法** → **压缩比更高**

**官方在"智能制造最佳实践"里的表述**：

> Device model: **One table per device and supertable tags create a relationship model centered on physical assets.**

（一设备一表 + 超表标签 = **以物理资产为中心的关系模型**）

⭐ **与增量 3（物模型）的关系**：这里说的"device model"是**存储层**的模型；增量 3 要做的物模型是**应用层**的模型。两者需要对齐——**这是本卡要看的第一个连接点**。

### 4.2 TDengine 提供的写入机制【已核实：同源】

| 机制 | 说明 |
| --- | --- |
| **普通 INSERT** | `INSERT INTO tb VALUES(...)`；**一次可写多行、多表** |
| **自动建表** | `INSERT INTO tb USING stb TAGS(...) VALUES(...)`——子表不存在则自动创建 |
| **参数绑定** | `STMT` / `STMT2` 预处理写入，官方标注用于**高吞吐场景** |
| **Schemaless** | 支持 InfluxDB / OpenTSDB 行协议，**自动创建超表与子表** |
| **FILE 导入** | 从 CSV 批量写入 |

⭐ 具体到本项目，写入走 `@tdengine/websocket`（ADR-009 已定）提供的接口。

### 4.3 关键行为：同一时间戳【已核实：同源】

⭐⭐ **同一子表、同一时间戳重复写入 = 覆盖。** 官方原文：

> When inserting multiple rows at once, do not set every first-column timestamp to NOW. Otherwise multiple rows in the same statement share one timestamp and **may overwrite each other**.

**其他相关行为**：

- **主键列值必须指定，不能为 NULL**
- 允许的最新时间戳 = **当前时间 + 100 年**；最旧由 `KEEP` 决定；越界报 `Timestamp out of range`
- ⭐ 超表支持 **`COMPOSITE KEY`（复合主键）**——**说明主键不限于单一时间戳**
- ⭐ **覆盖的单位是"整行"，不是"整表里某一个测点列"**：**列清单里没写到的列按 `NONE` 处理、保留旧值**，只有显式写 `NULL` 才清空（见 §4.5 第 1 条实测）

### 4.4 数据生命周期：`KEEP`【已核实：同源】

**建库语句里就有它**：

```sql
CREATE DATABASE power PRECISION 'ms' KEEP 3650 DURATION 10 BUFFER 16;
```

| 参数 | 含义 |
| --- | --- |
| `PRECISION 'ms'` | 时间戳精度 |
| **`KEEP 3650`** | **数据保留 3650 天，超期自动删除** |
| `DURATION 10` | 每 10 天一个数据文件 |
| `BUFFER 16` | 写入内存池大小 |

**另**：

- **超级表层也可设 `KEEP`**，但有两条额外规则：**必须小于库级 `KEEP`**；**不立即生效**——要先 flush 再 compact
- **社区版不支持多级存储**，只能一个 KEEP 值（多配也只取最大值；企业版可 `KEEP 100h,100d,3650d` 分层）
- **RSMA（按时间窗降采样存储）属企业版**；**流计算（`CREATE STREAM`）社区版可用**——本机实测端到端跑通（见[第 4 项材料](2026-10-08-decision-4-lifecycle.md) §4.4）；`TSMA` 建在流计算之上，但**全集群上限 10 个**、每个占一个流

⭐ **所以数据生命周期不是"以后再说"**——**建库时就要给一个值**，不给就用默认。

### 4.5 TDengine 的关键行为（**本机实测**，2026-10-07）

**实测环境**：容器 `tdengine/tsdb:latest` = **`3.4.2.8.community`**（digest `sha256:44f58e6f…`），经 taosAdapter 的 REST 接口；脚本为 `scripts/probe/tdengine-semantics.mjs`。**四条结论直接改变本卡第 1、2 项的前提**：

| # | 结论 | 影响 |
| --- | --- | --- |
| 1 | **省略列＝`NONE`（保留旧值）；只有显式写 `NULL` 才覆盖。** 同一 `ts` 分两条报文写入，两列都在（实测 `v1=1, v2=2`） | #1 / #2——窄表**不需要**在消费者侧攒批凑齐一行 |
| 2 | **`ADD COLUMN` / `ADD TAG` 是元数据操作**：小库 1×1000 行 5 ms / 大库 100×2000 行 4 ms（行数差 200 倍） | #1——"一旦入库即固化"要打折，**加列很便宜** |
| 3 | **子表不能单独 `ALTER`**、**主键列不能删**、**非变长列不能改类型**（变长只能扩长）。三条均按文档拒绝 | #1——真正不可逆的是**主键、类型、子表边界**，不是"列集合" |
| 4 | **虚拟表在社区版可用**：`BASE ON` 继承 + **非叶 VST 查询自动展开为后代 `UNION ALL`**；只读；**不支持查询订阅**；**父 VST 一旦有子，schema 冻结** | #1——"不同设备指标不同但要在一个列表里看"有**声明式**解法 |

另两条与本卡对接的硬事实：

- **镜像**：社区版为 `tdengine/tsdb`（自 3.3.7.0 起改名）。⚠️ **不要用 GitHub releases 的 tag 推断社区版可用版本**——该仓库最新 release 只到 `ver-3.4.1.6`，而实际拉到的是 `3.4.2.8.community`。落地按 **digest pin**。
- **查询返回顺序**：超表查询**不带 `ORDER BY` 时按子表分段返回**，列表混排必须显式排序。

（出处与逐条证据见知识库《增量 2 第 1 讲》§1.8 / §3.8 / §5 与附录 B；查证台账 #89–#96。）

### 4.6 `mqtt.js` 的 MQTT 5.0 支持【部分核实：本机依赖实测，2026-10-07】

**实测 `mqtt@5.16.0` 的 `IClientOptions` 类型定义**：

| 选项 | 存在 | 说明 |
| --- | --- | --- |
| `protocolVersion?` | ✅ | 类型为 `IConnectPacket['protocolVersion']`；**默认值是 4（即 3.1.1）** |
| `clean?` | ✅ | ⭐ **只有 `clean`，没有 `cleanStart`**——mqtt.js 用一个选项同时服务 3.1.1 的 Clean Session 与 5.0 的 Clean Start |
| `properties?` | ✅ | 支持 **CONNECT / PUBLISH / SUBSCRIBE / UNSUBSCRIBE 四处的 properties**（5.0 特性） |

⭐ **结论**：**连接器本身支持 5.0**，切换成本不是"换库"。

**三处待核实（本卡需补）**：

1. **`clean` 在 5.0 下的语义变化**——5.0 的会话生命周期由 **Session Expiry Interval**（走 properties）控制，`clean` 只表达 Clean Start
2. **EMQX 侧是否需改配置**——默认监听器通常同时支持 3.1.1 与 5.0，但**未核实**本项目配置
3. **契约是否需新增字段**——【AI 判断】**大概率不需要**：主题结构与载荷格式都是**应用层**的，与 MQTT 协议版本无关；但需确认 5.0 特性（如 User Properties 传 trace 上下文）是否要进契约
