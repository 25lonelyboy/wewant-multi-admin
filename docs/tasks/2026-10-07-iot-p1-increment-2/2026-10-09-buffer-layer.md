## 2. 队列形态（已定三项）

### 2.1 队列命名

```text
iot:telemetry:ingest
```

**理由**：带上**域与用途**两段——将来告警、AI 各自的队列并列时不会混，也便于按前缀做通配管理。

### 2.2 worker 部署形态：独立入口

**形态**：同一个代码库里的**第二个入口**（与 HTTP 的 `main.ts` 并列），部署为**独立进程 / 独立 compose 服务**。

⭐ **要拿到的三个性质**：
- **可独立启停**——重启消费者不重启 HTTP 服务
- **可多实例**——每实例一个 Worker 连同一队列，堆积时加、完了减
- **可独立扩缩**——不受 HTTP 服务的资源与实例数牵制

**依据 / 连带**：

| 项 | 说明 |
| --- | --- |
| ⭐ **我们消费者是无状态的** | 攒批各攒各的；幂等靠 `(子表, ts)`（第 2 项 §9）⇒ **可安全水平扩** |
| ⚠️ **扩的连带** | 每实例各开自己的 **TDengine 连接**（第 2 项 §9 定的是"每进程 2~4 条"，要**乘以实例数**），而 TDengine 有会话上限（实测 `0x80000022 rpc too many session`） |
| **官方侧（stalled）** | Node 单线程下，CPU 密集的处理器会阻塞事件循环、来不及续锁 ⇒ job 被判 `Stalled` 并重新入队。BullMQ 官方给的缓解是 **sandboxed processor**（processor 跑独立进程） |
| ⭐ **官方侧（停机）** | `SIGINT`/`SIGTERM` + `worker.close()` 优雅停机；**否则 job 变 stalled，约 30 s 后由新 worker 处理**——⭐ **这正是验收判据"强杀消费者 → 重投不产重复"的机制**（第 2 项 §9 的"先入库再 ack + 幂等"正是为它准备） |

### 2.3 保留策略

⚠️ 官方：*"By default, all jobs processed by BullMQ will be either completed, or failed and **kept forever**"* ⇒ **必须配**，否则 Redis 会被涨爆。

| 项 | 值 | 理由 |
| --- | --- | --- |
| `removeOnComplete` | `true`（或只留最近一小批） | 完成的 job 没有留着人工看的理由；留一小批仅供排障时看一眼 |
| `removeOnFail` | **保留较多**（如 `{ count: 5000 }`） | ⭐ 第 2 项 §9 定了"**B 类错误耗尽重试后进 failed 集合 + 人工处理**"——**failed 集合就是"待人工看"的那个队列**，删太快人工就看不到了 |

## 3. 待定两项

### 3.1 遥测消息信封：job 里放什么

**要决定的是「入队时机」**——它决定增量 1 的订阅端要改多少：

| | 入队时机 | 增量 1 的订阅端 | 代价 |
| --- | --- | --- | --- |
| **(i) 原始报文** | **解析之前** | ⚠️ **要改**——现在它解析 + 校验 + 计数，改成"直接投队列" | 解析移到消费者，**每次重试都要重解析**（便宜）；⚠️ **坏消息也进队列**，消费者要处理 |
| **(ii) 解析后的结构** | **解析之后** | ✅ **基本不改**（增量 1 的解析逻辑保留） | 结构化数据入队，契约变更与队列存量解耦；⚠️ 但**重试时无法重新校验** |

⭐ **一个判据**：第 2 项 §9 定了"**整批重投**" ⇒ 重投要重新解析 ⇒ **(i) 更顺**（重投 = 原样重投）。
⚠️ 但 **(ii) 保住了增量 1 的"解析失败丢弃 + 计数"**——那是它当时的可见性成果。

### 3.2 Redis 挂时，订阅端投不进队列怎么办

⚠️ **先分清两种故障**（它们不是一回事）：

| 故障 | 现象 | 已被什么覆盖 |
| --- | --- | --- |
| **A. 订阅端进程挂** | MQTT 连接断 ⇒ 消息丢 | ✅ **已由第 3 项 §9 覆盖**——持久会话攒住，重连后投递 |
| **B. Redis 挂**（订阅端还在） | 收得到，**投不进** | ⛔ **本项要处理的** |

| | 做法 | 代价 |
| --- | --- | --- |
| **(a) 订阅端落本地磁盘** | 投不进就写本地，恢复后补投 | **要写新代码** |
| **(b) 借"不 ack"做背压** | 投不进就不回 PUBACK ⇒ Broker 会留着并重发；`Receive Maximum` 给它在途上限 | ⚠️ **与 ADR-010 D3 冲突**——那里把"**接入层不被下游拖慢**"列为做缓冲的理由之一；且"不 ack 与 `Receive Maximum` 的交互"**【AI 判断】，未实测** |
| **(c) 接受** | P1 本地单机，Redis 与订阅端本来就同生共死 | 挂触发点，生产上重估 |
