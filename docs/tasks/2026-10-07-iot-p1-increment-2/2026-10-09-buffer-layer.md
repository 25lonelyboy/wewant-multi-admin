## 1. Redis 形态（已定）

**独立 Redis 实例**——结论与理由写在 [ADR-010 D4](../../decisions/ADR-010-ingest-buffer-bullmq.md)：BullMQ 要求 `maxmemory-policy = noeviction`，而该配置是**实例级**，限流缓存恰好希望有淘汰 ⇒ 只能分实例。

**落地时一并的三条**：开 **AOF**；**两类连接的配置不同**（Queue 快速失败 / Worker 无限等待 + `maxRetriesPerRequest: null`）；compose 加服务 ⇒ `ops/check-digests.sh` 预期 pin 数 **10 → 11**。

## 2. 队列形态（已定三项）

### 2.1 队列命名

```text
iot-telemetry-ingest
```

**理由**：带上**域与用途**两段——将来告警、AI 各自的队列并列时不会混，也便于按前缀做通配管理。⚠️ 分隔符用 `-` 不用 `:`——**BullMQ 用 `:` 作 Redis 键分隔符，队列名含冒号构造即抛**。

### 2.2 worker 部署形态：独立入口

**形态**：同一个代码库里的**第二个入口**（与 HTTP 的 `main.ts` 并列），部署为**独立进程 / 独立 compose 服务**。

⭐ **要拿到的三个性质**：
- **可独立启停**——重启消费者不重启 HTTP 服务
- **可多实例**——每实例一个 Worker 连同一队列，堆积时加、完了减
- **可独立扩缩**——不受 HTTP 服务的资源与实例数牵制

**依据 / 连带**：

| 项 | 说明 |
| --- | --- |
| ⭐ **我们消费者是无状态的** | 攒批各攒各的；幂等靠 `(子表, ts)`（第 2 项 §9）⇒ **可安全水平扩** |
| ⚠️ **扩的连带** | 每实例各开自己的 **TDengine 连接**（第 2 项 §9 定的是"每进程 2~4 条"，要**乘以实例数**），而 TDengine 有会话上限（实测 `0x80000022 rpc too many session`） |
| **官方侧（stalled）** | Node 单线程下，CPU 密集的处理器会阻塞事件循环、来不及续锁 ⇒ job 被判 `Stalled` 并重新入队。BullMQ 官方给的缓解是 **sandboxed processor**（processor 跑独立进程） |
| ⭐ **官方侧（停机）** | `SIGINT`/`SIGTERM` + `worker.close()` 优雅停机；**否则 job 变 stalled，约 30 s 后由新 worker 处理**——⭐ **这正是验收判据"强杀消费者 → 重投不丢"的机制**（第 2 项 §9 的"先入库再 ack + 幂等"正是为它准备） |

### 2.3 保留策略

⚠️ 官方：*"By default, all jobs processed by BullMQ will be either completed, or failed and **kept forever**"* ⇒ **必须配**，否则 Redis 会被涨爆。

| 项 | 值 | 理由 |
| --- | --- | --- |
| `removeOnComplete` | `true`（或只留最近一小批） | 完成的 job 没有留着人工看的理由；留一小批仅供排障时看一眼 |
| `removeOnFail` | **保留较多**（如 `{ count: 5000 }`） | ⭐ 第 2 项 §9 定了"**B 类错误耗尽重试后进 failed 集合 + 人工处理**"——**failed 集合就是"待人工看"的那个队列**，删太快人工就看不到了 |

## 3. 消息信封与 Redis 挂时的处置（已定）

### 3.1 消息信封：原始报文

**入队在解析之前**——job 里放**设备上行的原始载荷**；⭐ **信封不带主题**（贴近生产的环境下主题不参与身份判定，不依赖它的可用性）。

| 得到什么 | 代价 |
| --- | --- |
| ⭐ 第 2 项 §9 定了"**整批重投**" ⇒ **重投 = 原样重投**，不用重建中间状态 | ⚠️ **增量 1 的订阅端要改**：它现在做"完整解析 + 校验 + 计数"，改成"**简单解析**（只取 `localDeviceId`）+ 投队列" |
| 契约变更与队列里的存量解耦 | ⚠️ **坏报文也进队列**——`JSON.parse` 失败**原样入队**，完整的解析与丢弃改由消费者做，**增量 1 的"解析失败计数"随之移到消费者** |

⭐ **订阅端保留的那一次"简单解析"服务两件事**，都不是完整校验：

| 用途 | 说明 |
| --- | --- |
| `seenDevices` | 增量 4 的设备在线视图以它为底。它要的是"**哪个设备在发**"，不是"报文是否合法" |
| ⭐ **身份校验** | **主题段 ≠ 载荷 `localDeviceId` ⇒ 丢弃 + 计数 + 告警**。主题是**路由与将来 ACL 的授权单位**，而身份以载荷为准 ⇒ 不拦的话，一个已授权设备可以在**自己的主题**上发别人的编号，数据落进**别人的子表** |

⇒ ⚠️ **"丢弃"因此分两类、归属不同**：`JSON.parse` 失败归**消费者**（原样入队）；**身份不一致归订阅端**（不入队）。

### 3.2 Redis 挂时：订阅端落本地

**投不进队列 ⇒ 写本地磁盘；Redis 恢复后按序补投。**

⭐ **与 ADR-010 D3 同向**：写本地很快，**接入层不被下游拖慢**——正是那里要的性质。

**落地要点（随实施计划定）**：

| # | 要点 | 说明 |
| --- | --- | --- |
| 1 | **落什么** | **原始报文**（与 3.1 一致），按它的自然边界成批 |
| 2 | **落哪** | 可配的本地目录 ⇒ ⚠️ **compose 必须挂卷**，否则容器一重建，本地缓冲白做 |
| 3 | **补投顺序** | FIFO；⭐ **投成功才删本地文件**——重复投是安全的（幂等），反过来会丢 |
| 4 | ⚠️ **本地缓冲要有上限** | 无上限 ⇒ 磁盘写满 ⇒ **连日志都写不了**，比丢数据更糟。超限的处置（丢最老 / 停订阅并告警）**要在实施时定** |
| 5 | ⚠️ **写本地失败要告警** | 磁盘满、权限错 ⇒ 那时**真的会丢**，必须响亮 |

⚠️ **这个方案有它自己的失败模式**（磁盘满、容器重建、补投积压）——**不是"落本地就安全了"**，第 4、5 两条就是为它们准备的。
