## 1. 背景：这一项要决定什么

**要做什么**：把队列里的遥测数据，**可靠、可观测地**写进 TDengine。第 1 项定了"数据长什么样"（schema），这一项定"**怎么把它送进去**"。

**现状**（增量 1 与第 1 项之后）：

```text
设备/模拟器 → EMQX →（iot 域订阅）→ 【BullMQ 队列】→ 【消费者】→ 【TDengine】
                                          ↑ 未实现        ↑ 本项          ↑ schema 已定
```

增量 1 只做到"订阅 + 每秒汇总打印"；**队列与消费者尚未存在**。

**改完之后**：数据落库，且**写失败这件事有明确的处置路径**（知道、可重试、可对账）。

**为什么现在做**：M1 的交付判据是"**落库可见**"（10/19）；它是增量 3–5 的地基。

**不做的后果**：链路断了最后一跳，前面所有工作都停在"看得见"。

## 4. 项级背景

### 4.1 一条数据从队列到落库，要经过哪几段【AI 判断：环节划分，非官方】

```text
① 出队 → ② 解析 + 校验（已知测点？值合法？）→ ③ 组装成行（见 §4.4）
  → ④ 按子表分组攒批 → ⑤ 生成子表名 → ⑥ 写入 → ⑦ 核对结果 → ⑧ 确认/重试
```

⭐ **②③④⑤ 是第 1 项的 schema 直接带出来的新工作**，不是"把数据丢给驱动"就完事。本项的实质工作量在这里。

### 4.2 官方给的写入路径与效率排序【已核实】

| 路径 | 形态 |
| --- | --- |
| **普通 INSERT** | `INSERT INTO tb VALUES (...)`；一条语句可写**多行、多表** |
| **自动建表** | `INSERT INTO tb USING stb TAGS(...) VALUES(...)` |
| **参数绑定（STMT）** | 预处理写入，官方标注用于高吞吐场景 |
| **Schemaless** | InfluxDB / OpenTSDB 行协议 |
| **FILE 导入** | CSV |

**官方给的效率排序**（原文）：**参数绑定 > 裸 SQL（无自动建表）> SQL（含自动建表）> Schemaless**。

**官方同时给出的四条关键因素**：

| 因素 | 官方口径 |
| --- | --- |
| 批量 | 尽可能把数据放进一条 SQL；**单条 SQL 默认上限约 4 MB**（`maxSQLLength` 可至 64 MB） |
| 预建表 | **提升写入性能**——省掉表存在性检查，且写入时可省略标签列 |
| 写局部性 | **每批尽量只写一张表（子表）** |
| 顺序 | **同一子表的数据必须按时间戳升序提交**；乱序触发服务端额外排序（性能劣化，非报错） |

**一个行为差异【已核实】**：**子表不存在时，STMT 返回错误，而 `taos` shell 会自动建表**。官方明说这是**防表名写错时误建表**。

### 4.3 连接器能力的边界【已核实】

**官方文档里的"高效写入"（自动建线程与队列、按子表分片缓存、达阈值或超时批量发送、可配重试与自动重连）——当前只覆盖 JDBC（Java）。** 全页出现 "node" 仅一处 `buffer` 参数说明。

⇒ **Node 侧没有这层**：批大小、攒批触发条件、重试策略、断线重连**都要在消费者侧自己写**。

**`@tdengine/websocket` 实际提供的能力**【已核实】：

| 能力 | 说明 |
| --- | --- |
| `exec(sql)` | 返回 `{ affectRows, timing, totalTime }` —— **`affectRows` 是核对写入的抓手** |
| `query(sql)` | 查询 |
| `stmtInit()` → `prepare` / `setTableName` / `setXxx` / `setTags` / `bind` / `batch` / `exec` / `getLastAffected` | 参数绑定族 |
| `schemalessInsert(...)` | 行协议 |
| 连接参数 | `retries`（默认 5）/ `retry_backoff_ms`（默认 200，指数退避至 `retry_backoff_max_ms` 默认 2000）/ `adapter_ha` |

**参考锚点（JDBC 版默认值，仅供量级参照，非我们的默认值）**：写线程 10、**批大小 1000 行**、缓存 10000 行、自动重连默认**关**。

### 4.4 ⭐ 一个必须做的组装步骤：窄 → 宽【AI 判断，依据第 1 项的 schema】

载荷是**窄表**（一条报文带 N 个测点）：

```json
{ "deviceId": "sim-001", "ts": 1759747200000, "metrics": [{ "key": "temperature", "value": 36.5, "unit": "℃" }, ...] }
```

而第 1 项定的是**多列模型**（一行多个测点，一个测点一列）：

```text
(ts, temperature, vibration, current, ...)
```

⇒ **消费者必须把 `metrics[]` 按 `key` 映射到列，组装成一行**。这一跳要做对四件事：

| # | 情况 | 处理 |
| --- | --- | --- |
| 1 | 某测点**缺失** | 该列**不写**（省略列＝`NONE`，保留旧值，实测已证） |
| 2 | 出现**列集合外的 `key`** | **未知测点策略**——检测清单第 3 条（§4.6） |
| 3 | **同一报文内出现重复 `key`** | 【待核实】会撞同一列，后者覆盖前者（静默）——要防御 |
| 4 | 报文里**出现多个 `pointId`** | 一行拆成**多行**，分别落到各自的子表（第 1 项已定 `pointId` 进载荷且可缺省） |

⭐ **第 4 条决定了**：**"一条报文 → 几行"不是固定的**；攒批的分组键是 `(deviceId, pointKey)`（经档案解析后的键），不是 `deviceId`。

### 4.5 写失败的形态：官方错误码表给出的三类【已核实，分类为 AI 判断】

官方错误码文档每一条都带"可能原因 + **建议用户动作**"。按**处置动作**归成三类：

| 类 | 代表错误码 | 官方描述 | 处置含义 |
| --- | --- | --- | --- |
| **A · 可重试**（连接/资源类） | `0x8000000B` 无法建立连接；`0x80000018` Conn is broken（网络抖动或请求超 900 秒被断开）；`0x80000019` Conn read timeout（请求过久 / 服务端过载 / 死锁）；`0x80000020` / `0x80000021` 部分 vnode/qnode/mnode 不可用或连接断开；`0x80000022` **rpc open too many session**（高并发把连接占满）；`0x80000309` 用户连接数过多；`0x80000102` OOM；`0x80000126` **rpc 队列内存到顶** | 多为网络与容量问题 | 官方建议调整配置参数、检查负载、重试 |
| **B · 重试无意义，要改数据或配置** | `0x80000127` 时间戳格式错误；`0x80000618` Table does not exist；`0x80000303` 权限不足；`0x8000030B` **Data expired**；`0x80000364` 标签过多；`0x80000365` 列过多 | 输入/配置/权限问题 | **重试多少次都一样** |
| **C · 需要人介入** | `0x80000104` **Data file corrupted**（官方建议联系支持）；`0x80000020`（全节点崩溃时） | 服务端故障 | 不能自动恢复 |

⭐ **两条最有设计含义的**：

1. **超时类（`0x80000019`）≠ 一定失败** —— 请求可能已经成功，只是响应丢了。**把它当"失败"而丢弃 = 丢数据**；当"成功"而不重试 = 可能没写进去。**这是幂等存在的最实际的理由**（第 1 项已证明重复写 `(子表, ts)` 是安全的）。
2. **`0x8000030B` Data expired** —— 写入**超出 `KEEP` 范围**的历史数据会报这个。**与"断网补传"直接相关**：设备离线很久后补传的数据，可能已经过期。

**另有一条与运维相关**【已核实】：`0x80000013` **Client and server's time is not synchronized**——"客户端与服务端时区不同，或**时差超过 900 秒**"。⚠️ 注意这是**平台侧客户端 vs 服务端**，与"设备时钟不可信"是两回事。

### 4.6 检测清单里属本项的 5 条【出自第 1 项 §6.6】

| # | 检测什么 | 现状 |
| --- | --- | --- |
| 1 | **重复 `ts`**（同一子表、同一 `ts` 被写多次） | ❌ —— 本套 schema 的**头号失败模式** |
| 2 | **时钟偏移**（设备 `ts` vs 平台接收时间） | ❌（连接收时间列都还没定，§5.3 B1） |
| 3 | **未知测点 `key`** | ❌ |
| 4 | 数值越界 / 非法值 | ❌ |
| 5 | **写入影响行数对账** | ❌（`exec` 的 `affectRows` 是抓手） |

> 检测清单的第 5、6 条（设备"该来没来"、解析失败）分别属增量 6 与增量 1。

### 4.7 与队列的重试语义会叠加【AI 判断，需决策人确认】

BullMQ 自带重试/退避（ADR-010 的理由之一），写入侧也可能重试——**两条重试链会叠加**：

```text
队列重试（消息级） ─┐
                    ├─→ 同一条数据可能被写多次
写入重试（请求级） ─┘
```

**重复写同一 `(子表, ts)` 是安全的**（第 1 项已证：覆盖，不产生重复行）——**所以这里不构成正确性风险**。但它有一个必须回答的连带问题：

> **"消费成功"什么时候算？** 是"写进 TDengine 了"，还是"队列 ack 了"？两者之间崩溃会怎样？

### 4.8 规模口径与实测锚点（**决策人已修正口径**）

> 【决策人】数据量级**不能按当前模拟的 100 台估算**——按**工厂内部自建 IoT、服务内部效率**、**产线级千到万级设备**来估。

**实测锚点**（本机 `3.4.2.8.community`；经 REST；单客户端串行；每批 2000 行；schema = `ts + 3×DOUBLE` + 1 标签）：

> **100,000 行 / 950 ms ≈ 10.5 万行/秒**

**目标规模下的推算**：

| 场景 | 行速率 | 占实测能力 |
| --- | --- | --- |
| 1 万设备 × 1 采集点 × 1 Hz | 10,000 行/秒 | ~10% |
| 1 万设备 × 3 采集点 × 1 Hz | 30,000 行/秒 | ~29% |
| 1 万设备 × 1 采集点 × 10 Hz | 100,000 行/秒 | ~95%（到顶） |

⭐ **结论一：TDengine 不是瓶颈。** 万级设备 @ 1 Hz 只用到实测能力的约 1/10。

⭐ **结论二：瓶颈在消费者（Node 单进程），而它主要由"批大小"决定。**

需要 10,000 行/秒时：

| 批大小 | 每秒请求数 | 每批时间预算 |
| --- | --- | --- |
| **2000 行** | 5 | **200 ms**（宽松） |
| 100 行 | 100 | 10 ms（可行但紧） |
| **逐条** | 10,000 | **Node + WebSocket 单连接做不到** |

⇒ **"批大小与攒批策略"从次要升为主要判据。**（这修正了本项初稿里"P1 量级小、吞吐不重要"的判断——那个判断基于 100 台，**已作废**。）

**子表数**：万级设备 → **1 万 ～ 3 万 子表**（按采集点数）。官方建议**每 VGROUP 表数 ≤ 1 万**（硬件充足时更佳）⇒ **建库时可能要显式设 `VGROUPS`**（这条反馈给第 1 项的建库语句）。

**存储量级**（**只有量级参考价值**）：行宽约 **32 字节**（`ts` 8 ＋ 3×`DOUBLE` 24）→ 1 万行/秒 ≈ **27 GB/天（未压缩）**；官方口径压缩约 1/10 → ~2.7 GB/天 ≈ **1 TB/年**。
⚠️ **本机算不出可信的压缩比**——测试数据是确定性线性序列，压缩比严重失真；**真实压缩比要等增量 6 用真实波动数据实测**。⇒ **`KEEP` 的取值确实需要容量依据**（这条反馈给第 4 项）。

**单批上限**：单条 SQL 默认**约 4 MB**。按 32 字节/行算，4 MB ≈ **13 万行/批**——**批上限在 P1 规模下不会先撞到**（先撞到的是攒批的时延与内存）。

## 5. 决策轴与决策人的答复

> 按第 1 项的形状：**候选方案由决策人先写**，材料方再补全与纠偏（补全与纠偏见 §6）。

| # | 问题 | 决策人的答复 |
| --- | --- | --- |
| 1 | **写入路径**——裸 SQL `exec`，还是参数绑定 STMT？ | ✅ **参数绑定 STMT**——官方效率排序的第一档，且与轴 4 的预建表正向配合（见 §6） |
| 2 | **逐条写还是攒批**？触发条件是条数、字节数、还是时间？ | ✅ **按业界推荐方式**（条数 或 时间，先到先 flush）：**批大小 500 条 或 `flush_interval = 2 s`**；**必须支持配置化调整**；**默认值贴合本项目实际** |
| 3 | **批多大**？每批一张子表还是多张？ | ✅ **约 500**（默认值，可配）；**每批多个子表**（理由见 §6——**这不是兼容性折中，是高基数下的唯一形态**）<br>理由：内部成效型项目，**1 万台已是大厂**；不能设太大，否则**入库延迟太久** |
| 4 | **子表谁来建**——预建还是自动建表？ | ✅ **预建**：**增量 2 先手动建表**（拟成可重复执行的脚本）；**增量 3 起由设备管理在注册时预建**。**不做自动建表** |
| 5 | **写失败怎么知道**——靠 `affectRows` 对账，还是靠异常？ | ✅ **优先以异常为第一判断，然后核对影响的行数** |
| 6 | **A 类错误（可重试）重试几次、退避多久、重试期间数据在哪**？ | ✅ **按 BullMQ 的指数退避 + 抖动定**（⚠️ 但 BullMQ **没有**"默认的指数退避 + 抖动"——必须显式配，见 §6） |
| 7 | **B 类错误（重试无意义）怎么办**——丢弃、死信、还是告警？ | ✅ **告警 + 人工处理**，人去了解实际情况再决定这一类怎么处置 |
| 8 | **"消费成功"的语义定在哪**？ | ✅ **入库成功，且队列正常 Ack**（两者都要） |
| 9 | **连接怎么管**——几条连接？断开怎么重连？ | ✅ **按"20 请求/秒"这个量级定**（⚠️ 但 20 请求/秒是**请求速率**、不是连接数——换算与默认值见 §6） |
| 10 | **§4.6 那 5 条检测落在哪一段**？ | ✅ **解析之后立刻判断**——例如**和设备管理里的信息核对设备编号、采集点编号、以及相应的指标** |

### 5.1 决策人的原话

> **第 2、3 条**：尽量按照业界的推荐方式来，但需要支持配置化调整，同时默认值要贴合我们的实际情况。在这种内部成效的 IoT 项目里面，其实 1 万台设备都已经是比较大的工厂了，也不能够把每批的数量设得太大，否则会导致数据不足、入库延迟太久。但是具体的数据我还是不知道怎么给出来，按每批 500 这样子去定，有没有问题呢。
>
> **第 2 条补充**：flush interval 默认值定 **2 秒**。
>
> **第 4 条（自动建表方案的立论）**：应该是要靠自动建表。可以容忍一定的慢，但是不太好接受每次上新设备都要手动去建表。一旦没有手动去建表，那数据丢失、系统报错，其实在生产环境下会更严重。
>
> **第 5 条**：优先以异常为第一判断，然后再核对影响的行数。
>
> **第 3 条（后半）**：我现在没办法知道设备侧实际会怎么申报。所以如果现在做选择的话，我会选择"**每批多个子表**"，以兼容设备侧汇总之后统一上报的情况。如果设备侧每个采集点单独申报，这也能够兼容，自然会回落到"每批一个子表"的情况。

> **第 7 条**：一类错误从事（重试）没有意义的情况下，能够接受的方案应该是告警，然后人为去处理，去了解实际的情况，看这一类要怎么再去做处理。
>
> **第 8 条**：消费成功肯定是要入库，然后队列能够正常 Ack。

> **第 9 条**：就按照 **20 请求/秒**这个定吧。
>
> **第 10 条**：对报文的检测应该在解析之后立刻去判断。例如，和设备管理里面的信息去核对设备编号、采集点编号以及相应的指标这些信息。
>
> **第 6 条**：A 类重试按 BullMQ 默认的指数退避加抖动来定。
>
> **第 4 条（最终）**：如果要和增量 3 的设备管理结合的话：① 增量 2 这里就不用做自动建表了，采用**预建**的方式，在设备管理那里去预建；增量 2 这里**先手动建表**就行了。② 对应的**第 1 条也不用受自动建表影响了**。
>
> **第 1 条**：就按**参数绑定 STMT** 定。

## 6. AI 补全与纠偏

### 轴 1 — 写入路径：**参数绑定 STMT**

**与官方效率排序一致**：**参数绑定 > 裸 SQL（无自动建表）> SQL（含自动建表）> Schemaless** ⇒ 选的是**第一档**。

**【AI 补全】它和轴 4 是正向配合，不是各管各的**

官方说预建表提升写入性能的两条理由之一是——**"写入时可以省略标签列（tag）数据"**。
⇒ **预建 + STMT = 连 tag 都不用绑**（子表已存在、标签值已定），少一组参数。**轴 4 改预建之后，轴 1 选 STMT 的收益比原来更大。**

**官方给的参数绑定推荐形态**：

```sql
INSERT INTO meters (tbname, ts, current, ...) VALUES (?, ?, ?, ...)
```

（子表已存在时**省略 tags** 可提升写入性能。）

**【AI 补全】⭐ 最关键的一条：STMT 怎么配"多子表批"（轴 3 后半的结论）**

Node 连接器的 STMT API 里有一个 `setTableName()`，**看起来是"一个 stmt 对象对应一张子表"**——若真如此，多子表批就要开 N 个 stmt 对象。

**但官方 Java 示例走的是另一条路**：用**超表语法**，把 **`tbname` 当成普通绑定参数**——

```java
String sql = "INSERT INTO power.meters (tbname, groupid, location, ts, current, voltage, phase) VALUES (?,?,?,?,?,?,?)";
// 循环里 setString(1, "d_bind_" + i)  ← 子表名也是参数
```

⇒ **这意味着一个 stmt 对象可以覆盖所有子表**，不必"每子表一个 stmt"。官方示例本身就是"循环生成多张子表与它们的行，再批量插入"。

⚠️ **但 Node 连接器的 API 同时提供了 `setTableName()`**，两者的关系未明确。**待实测**（§8 新增第 13 项）：**Node 侧用哪种写法、一个 stmt 句柄能否写多子表**。**这条直接决定实现的形态。**

**【AI 补全】其余四个要点**

| # | 要点 |
| --- | --- |
| 1 | **影响行数来自 `getLastAffected()`**，不是 `exec` 返回的 `affectRows` ⇒ **轴 5 的"行数核对"要用这个 API** |
| 2 | **类型映射**：`setFloat` / `setDouble` / `setInt` / `setBigint` / `setVarchar` / `setTimestamp`…… ⇒ **第 1 项的类型分档在这里落地**；注意 `ts` 是 epoch 毫秒数字，**怎么传给 `setTimestamp` 要确认** |
| 3 | **一次 `exec()` 能带多少行**（与批大小 500 的关系）—— 待实测 |
| 4 | **调试更难**：失败时看到的是绑定调用栈而不是 SQL 文本，**日志可读性比裸 SQL 差** |

**【AI 补全】它的代价要写清**：**实现复杂度最高、调试最难**。官方把参数绑定列为效率第一，但**这是用可读性换来的**。

### 轴 2 + 3 — 攒批与批大小（**先看这条：500 本身没问题，但光有它有问题**）

**方向对，而且"配置化 + 默认值贴实际"这个组合本身就是业界做法**（Telegraf 的默认值全部可配，且文档明写其默认值）。

**【AI 纠偏】"数据不足"这个担心的根因，不是"批太大"，是"缺时间兜底"。**

双触发的设计里，两个条件各自负责一段：

| 触发条件 | 它负责的 | 量纲 |
| --- | --- | --- |
| **条数**（500） | **高负载下的延迟上限** | 负载越高，越早命中 |
| **时间**（flush interval） | **低负载下的延迟上限** | 负载越低，越靠它 |

⇒ **没有时间触发，低速率下攒不满就一直挂着**——不是"延迟久"，是**永远不写**。
⇒ 所以"可配置"里，**`flush_interval` 不是可选项，是必需项**。

**【AI 补全】500 的算术**（延迟 ＝ min(500 ÷ 行速率, flush_interval)）：

| 行速率 | 攒满 500 需 | 请求速率 |
| --- | --- | --- |
| **100 行/秒**（P1 现状：100 台） | **5 s** | 0.2 /s |
| 1,000 行/秒 | 0.5 s | 2 /s |
| **10,000 行/秒**（万级设备 × 1 Hz） | **0.05 s** | 20 /s |
| 100,000 行/秒（万级 × 10 Hz） | 0.005 s | 200 /s |

⇒ **500 在目标规模下很轻松**：每秒 20 次请求，而本机实测**单批 2000 行只要约 19 ms**。

⭐ **一个反直觉的观察**：**在 P1 阶段（100 行/秒）"500 条"这个触发条件几乎永远不会命中**——攒满要 5 秒，时间触发早就亮了。**所以 P1 的实际批次是 `flush_interval × 100` 行，500 这个上界用不到。**
⇒ **500 合不合理，要到目标规模才检验得到**；而目标规模下它留了约 10 倍余量。

**【AI 补全】批大小的真正上界不是内存，是"失败影响面"**：

| 约束 | 数量级 |
| --- | --- |
| 内存 | 500 行 × 约 32 字节 ≈ **16 KB**（1 万行也才 320 KB）——**完全不是约束** |
| **失败影响面** | 一批 500 行失败 → 500 行重投；一批 1 万行失败 → **1 万行重投，且"ack 粒度"的问题被放大**（轴 8 的补全） |

⇒ **批大小 ＝「性能需要的最小值」与「失败影响面的可接受值」之间的折中**。500 在两边都很宽松。

**【AI 补全】"配置化"要写清三件事，否则它会变成一个空承诺**：

| # | 项 |
| --- | --- |
| 1 | **配在哪**（环境变量 / 配置文件 / 两者） |
| 2 | **哪些可配**（批大小 / flush 间隔 / 缓冲上限 / 并发或连接数 / 重试参数） |
| 3 | **默认值的依据**——⚠️ 最要紧：**没有依据的默认值，就是"选出一个谁都说不出理由的默认"**（这是决策人在增量 0 第 6 讲自己带进来的教训） |

**【决策人】`flush_interval` 默认值定 2 秒。**

**两个值合起来看，有一个明确的交接点**：

```text
交接速率 = 批大小 ÷ flush_interval = 500 ÷ 2 s = 250 行/秒
```

| 行速率 | 谁主导 | 实际批次 | 入库延迟 |
| --- | --- | --- | --- |
| **100 行/秒**（P1：100 台） | **时间触发** | ≈ **200 行**（＝2 s × 100） | **≤ 2 s** |
| **250 行/秒** | 正好交接 | 500 行 | 2 s |
| **10,000 行/秒**（万级 × 1 Hz） | **条数触发** | 500 行 | **≈ 0.05 s** |

⭐ **这条曲线是平滑的，两档之间没有断点**——低速率靠时间兜底，高速率靠条数兜底，交接点在 250 行/秒。
⭐ 也印证了上一节的观察：**P1 阶段（100 行/秒）远低于交接点，完全由时间触发主导，批次约 200 行，500 这个上界不生效。**

**依据成对写下来**（"配置化"第 3 条要求的）：

| 参数 | 默认值 | 依据 |
| --- | --- | --- |
| 批大小 | **500** | 按本机实测能力（10.5 万行/秒）留约 **10 倍余量**；同时限制**失败影响面** |
| `flush_interval` | **2 s** | 低负载下**可接受的入库延迟上限**；2 s 同时把额度留给队列与写入（端到端仍可压在数秒内） |

**【AI 补全】2 s 的一个连带影响，需要记下**：`flush_interval` 直接决定**入库延迟的下界**（P1 下 ≈ 2 s），而**端到端延迟 ＝ 攒批（≤2 s）＋ 队列 ＋ 写入（ms 级）**。
⇒ **这条会传导到增量 5（告警）的时效性**：若将来要求"秒级以内告警"，2 s 这个值要重估。**当下不是问题，但要把这条耦合写下来。**

**（对照）Telegraf 的 `flush_interval` 默认 10 s，而它的采集 `interval` 也是 10 s**——即"每采集一轮 flush 一轮"，两者同步。**我们的 2 s 与设备 1 s 的上报频率不同步**，这不是问题（会攒两轮），但说明：**`flush_interval` 不必等于上报频率**。

**【AI 补全】还有两个值属于同一组，建议一起定**：

- **缓冲上限**（Telegraf 的 `metric_buffer_limit = 10000` 是它的默认）——积压超过它怎么办
- **并发 / 连接数**（轴 9）——**批变小了，请求数就上去了**（10,000 行/秒 ÷ 500 ＝ 20 请求/秒），连接数要配得上

### 轴 3（后半）— 每批几个子表：**不是兼容性选择，是高基数下别无选择**

**【AI 纠偏】方向对，但"自然回落"这一句不成立——批的粒度不是设备形态决定的。**

攒批边界在消费者手里，而队列是**全局的**：

```text
P1：100 台设备 × 1 条/秒，每台 1 采集点
   → 100 行/秒 → flush 2 s → 批 ≈ 200 行
   → 这 200 行来自 ~100 个不同子表（每台一个）
```

⇒ **即使在"每采集点单独上报"的形态下，一个批里仍有约 100 个子表。** 设备形态决定的是"**一条报文 → 几行**"；"**一个批 → 几个子表**"由**队列与攒批边界**决定。

**【AI 补全】理由可以换成一个更硬的：这不是"兼容性折中"，是高基数下的唯一形态。**

| 场景 | 行/秒 | flush 2 s 后一批 | 该批涉及子表 | 若"每条 SQL 单子表" |
| --- | --- | --- | --- | --- |
| P1（100 台） | 100 | 200 行 | ~100 | 50 SQL/s（可行，但每条只有约 2 行） |
| **目标（1 万台）** | 10,000 | 20,000 行 | **约 10,000** | **5,000 SQL/s** ❌ |

目标规模下，"每条 SQL 单子表"会退化成"每条 SQL 只有约 2 行"——**请求数追上行数，不可行**。

**【AI 补全】"批"这个词要拆成两层**：

| 层 | 含义 | 是选择还是事实 |
| --- | --- | --- |
| **flush 周期** | 一个 2 秒窗口内攒到的行 | ⭐ **必然多子表——这是事实，不是选择** |
| **每条 SQL 的范围** | 一次 `exec` 里写多少个（子）表 | ⭐ **这才是选择** |

官方那句"**每批尽量只写一张表**"说的是**第二层**——而**它的隐含前提是"数据按子表聚集"**。

#### ⭐ 官方建议与我们冲突，而且原因可以解释

官方讲写局部性时举的实现手段是——**Kafka 里把同一张表的数据写进同一个 Topic 与 Partition**，目的是**提高数据邻接性**。也就是说，**官方假设"数据按子表聚集"**。

而我们的架构天然相反：

```text
官方假设：按子表聚集   ← 一个子表的数据攒成一批
我们的实际：按时间聚集 ← 全局队列 + 按时间/条数攒批 → 一批里全是不同设备
```

**这不是做错了，是两种数据聚集方式的差异**；而"按时间聚集"在高基数下不可避免（每子表 2 秒内只有约 2 行，攒不出"按子表聚集"的批）。

#### ⇒ 两个悬置点由此收口

**① `affectRows` 核对从"第二保险"变成"必需品"**（接轴 5）

| 批的形态 | "部分成功"发生在 | 谁抓得到 |
| --- | --- | --- |
| 每条 SQL 单子表 | SQL **之间** | 异常够用 |
| **一条 SQL 多子表** | SQL **内部**（跨 VNODE） | **只有 `affectRows` 抓得到** |

⇒ 既然多子表批是唯一可行形态，**轴 5 的"异常 + 行数核对"组合就是必需的**，必要性比原来更强。

**② ack 粒度只能是"整批"**（接轴 8）

⚠️ **一个必须知道的新难点**：**`affectRows` 是总数，不告诉你哪几行失败。** 500 行里 `affectRows = 498` → **不知道是哪 2 行**（TDengine 不给行级失败定位）。

⇒ 所以"部分成功"的处置**只能是整批重投**。
⇒ 而**整批重投是安全的**——幂等（`(子表, ts)` 覆盖）保证已成功的 498 行不会被重复写入。
⇒ 代价是**效率**：498 行好数据陪着 2 行一起重投。**但因为它安全，这个代价可接受。**

**一句话收口**：**"多子表批"不是兼容性选择，是高基数下的唯一形态；它使 `affectRows` 核对成为必需品，而"部分成功"的唯一正确处置是整批重投——靠幂等兜住。**

### 轴 4 — 子表谁来建：**预建**

**【决策人】不做自动建表**：增量 2 **先手动建表**；增量 3 起由**设备管理在注册时预建**。

**【AI 判断】这个修订把问题从"静默"改回了"响亮"，方向是对的。**

原顾虑是"漏建表 → 数据丢失 / 报错"，原解法是"自动建表（消除报错）"。**但更好的解法是"让它报错、并且告警"**：

| 方案 | 漏建表时 | 表名写错时 |
| --- | --- | --- |
| 自动建表 | 静默把表建出来（**看不出漏**） | **静默多一张表**——命中第 1 项头号失败模式（幂等破、重复行不报错） |
| **预建** | **报错**（表不存在）——可见、可修 | **报错** |

⇒ **"报错"不是问题，"静默"才是问题。** 与增量 0/1 反复得出的原则一致：**响亮失败优于静默失败**。

**【AI 补全】改这一条带来四个好处**：

| # | 好处 |
| --- | --- |
| 1 | **取回官方给的那层保护**——STMT 在子表不存在时报错，其动机原文就是"**防止表名写错时误建表**" |
| 2 | **消除轴 4 与轴 10 的方向冲突**——轴 10 要"先核对设备档案"，而自动建表是"没档案也照写"。**预建 ⇒ 表存在即已注册**，两者不再打架 |
| 3 | **轴 1 的约束解除**（见下） |
| 4 | **省掉"表存在性检查"的成本**——官方说自动建表需要 *frequent table existence checks* ⇒ §8 待实测第 6 项**作废** |

**【AI 补全】"增量 2 先手动建表"最好落成脚本，而不是人手敲 SQL**：

1. **子表名由 `(deviceId, pointKey)` 确定性生成**（第 1 项 §8 的冻结值）⇒ 脚本按同一规则生成表名，**顺带验证了命名规则的确定性**
2. **要可重复执行（幂等）**——增量 2 期间模拟器的设备规模可能调整（100 台 → 别的数），脚本要能重跑
3. ⭐ **它正好是增量 3"注册时建表"的原型**——将来把这套逻辑搬进设备注册即可。**增量 2 的脚本＝增量 3 的预演**

**【AI 补全】批量建子表有官方路径**（不必一台台建）：

- 单条语句批量建：**官方建议单语句控制在 1000–3000 张**
- 或从 CSV 批量建：`CREATE TABLE USING stb (tbname, tag...) FILE 'x.csv'`

⇒ 100 台（P1）与万级（目标规模）都在**一条语句的量级内**。

**【AI 补全】⚠️ 一个要写清归属的**：**增量 2 期间"建表"这个动作挂在谁身上？** P1 没有设备档案，所以只能是**平台侧一个初始化 / seed 步骤**（按模拟器的设备清单生成）。这条要写进实施计划，否则会变成"没人建表"——而**预建方案下漏建的表会直接报错**（比自动建表好，但仍要有人接这个报错）。

#### 连带影响：轴 1 的判据

**预建解除了轴 1 的一处约束**：自动建表属 SQL 系（`INSERT ... USING ... TAGS`），而**参数绑定在建表语义上是"报错"而非"自动建"**——两者在这一点上互斥。选了预建，这层互斥不再存在。

**【AI 补全】"参数绑定在表不存在时报错"这条，在预建前提下是优点**：

| 前提 | 这条的性质 |
| --- | --- |
| 自动建表 | **妨碍**——想要自动建就不能用它 |
| **预建** | **防线**——它是"漏建表 / 表名写错"的报警器 |

⇒ 轴 1 的判据：官方那四条（**效率排序 / 批量 / 局部性 / 顺序**）+ **实现复杂度与失败可读性**。

⚠️ **连带一条待实测要拆分**：§8 第 11 项（`exec` 对 SQL 错误的处理方式）**要拆成两条**——`exec(sql)` 的错误处理 vs **STMT 族（`prepare` / `bind` / `exec`）的错误处理**。轴 1 选哪条路，就依赖哪一条的实测结果。

### 轴 5 — 失败怎么知道：异常优先 + 行数核对

**顺序对，而且两道防线的分工是清晰的**：

| 防线 | 抓什么 | 抓不到什么 |
| --- | --- | --- |
| **异常** | **整体失败**：连接、超时、权限、格式、表不存在、数据过期 | **部分成功** |
| **`affectRows` 核对** | **部分成功**——官方明确说多子表跨 VNODE 会出现"部分数据写成功、部分失败" | —— |

⭐ **所以第二道防线不是"补充检查"，它是"部分成功"这一类唯一能被发现的路径。**

**【AI 纠偏】⚠️ 但 `affectRows` 的预期值不能直接等于"批内行数"——有一处会天然不符**

`(子表, ts)` 相同的两行会**互相覆盖**，而覆盖**只影响一行**。所以**批内若有重复 `(子表, ts)`，`affectRows` 天然小于"批内行数"**——若按"小于就是部分失败"判，会**误报**。

⇒ **必须在核对之前做批内去重**（同子表同 ts 只留一条；保留策略要写明，例如保留最后一条）。
⇒ ⭐ 而这**正好就是解码端检测清单的第 1 条（重复 `ts`）**——两项工作在同一个位置汇合。

**【AI 补全】"异常优先"有一个必须写清的前提**：**异常里有一类是"可能已成功"的**（读超时 `0x80000019`，§4.5）。

⇒ 所以异常的处理**必须是重试，不能是丢弃**——否则会把"已写成功但响应丢了"当成失败而丢数据。**这一条直接接到轴 6。**

**【已收口】"批的粒度"已由轴 3（后半）答复＝**每批多个子表**——详见「轴 3（后半）」一节。**结论是：多子表批是高基数下的唯一形态，因此 `affectRows` 核对是必需品，不是额外保险。**

**【待核实】一条会直接影响本轴实现的**：**`exec` 在 SQL 出错时是抛异常，还是返回错误码？** 连接器文档只写了"连接失败抛 `TDWebSocketClientError`"，**SQL 层错误的处理方式未核实**（已列入 §8）。

### 轴 6 — A 类重试：**BullMQ 没有"默认的指数退避 + 抖动"**

**【AI 纠偏】⚠️ 事实先纠正**（BullMQ 官方文档原文）：

| 以为的 | 实际的 |
| --- | --- |
| BullMQ 默认指数退避 | ❌ **默认不重试**——`attempts` 不设时，失败即进 **failed set** |
| 启用后会自动退避 | ❌ **不配 `backoff` 则"失败后尽快重试、无延迟"**（原文 *retried without delay as soon as they fail*） |
| 抖动是默认的 | ❌ **`jitter` 是 `backoff` 里的可选参数**，不配即 0 |

⇒ **"指数退避 + 抖动"必须显式配置**，而且延迟种子值也要自己给。

**要配的形态**：

```js
{ attempts: 5, backoff: { type: 'exponential', delay: 200, jitter: 0.5 } }
```

**三个参数的建议值与依据**（**供决策人确认，非替他定**）：

| 参数 | 建议 | 依据 |
| --- | --- | --- |
| `attempts` | **5** | 与连接器 `retries` 的默认值 **5** 同量级（"最多试 5 次"） |
| `delay` | **200 ms** | 与连接器 `retry_backoff_ms` 的默认值 **200** 同量级；⭐ 它同时是**最快重试间隔** |
| `jitter` | **0.5** | BullMQ 官方文档举例用的值；作用是**避免多个 job 的重试时刻同步**（重试风暴） |

按官方公式 `2^(attempts-1) × delay`，退避序列约 **200 → 400 → 800 → 1600 ms**，累计约 **3 秒**。
⚠️ **待核实**：官方文档在"attempts 如何计数"上自身不一致（举例说"重试 2 次"却列了 1 s / 2 s / 4 s 三个间隔）——**实际序列要以实测确认**（已列入 §8）。

#### ⭐ 但这一题真正的重点是它问的后半句："重试期间数据在哪"

这句话**藏着一个决定数据安全的设计点**：

| 重试方式 | 重试期间数据在哪 | 进程这时崩溃会怎样 |
| --- | --- | --- |
| **在消费者内部循环重试** | **内存里** | **丢数据** |
| **抛回队列、由 BullMQ 重试** | **Redis 里**（队列持久化） | **不丢**——消息还在，会被重新取到 |

⇒ **数据一旦要跨越"可能崩溃"的时长，就必须已经在持久化存储里。**

**【AI 补全】由此可以把轴 9 的"三层重试"简化成两层**：

```text
连接重连（连接器内建）  →  只负责把连接弄回来
队列重试（BullMQ）      →  所有写入失败都走这里，数据全程在 Redis
```

⭐ **中间那层"消费者自造的写入重试"可以去掉**——直接把异常抛出去，让消息回到队列，由 BullMQ 按指数退避重试。理由：

1. **数据安全**：全程在 Redis，崩溃不丢
2. **实现简单**：不在消费者里造两套重试逻辑
3. **代价可接受**：每次重试要重新解析整条消息，但**幂等（`(子表, ts)` 覆盖）保证安全**；且 `delay = 200 ms` 让首次重试也够快

⚠️ 由此 `delay` 的含义变了：**它同时是"最快重试间隔"**——所以不宜设大（200 ms 起合适）。

### 轴 7 — B 类错误告警 + 人工

**方向对**（重试无意义的事，重试只是浪费）。

**【AI 补全】必须说清"告警之后消息去哪"**，否则会变成"一直在重试"。三条路：

| 处置 | 后果 |
| --- | --- |
| 不 ack，耗尽重试次数 | 进入 BullMQ 的 **failed 集合** —— **正好对上"人工处理"** |
| 直接丢弃 | 静默丢数据（与轴 8 的选择自相矛盾） |
| 就地告警、不进队列 | 数据无痕 |

⭐ **BullMQ 自带重试计数与 failed 集合**（ADR-010 选它的理由之一）——**"耗尽重试 → failed 集合 + 告警"是现成机制**，不必自己造。

**【AI 补全】告警必须带错误码。** B 类里 `Table does not exist` 与 `Data expired` 的处置完全不同（前者像命名逻辑 bug，后者是补传数据超期）——**不带错误码的告警，人到了也不知道从哪查**。

**【AI 补全】B 类里有一条是"信号最强"的**：`Table does not exist`——**轴 4 改为预建之后，它在正常路径下不该出现**；一旦出现就只可能是两种情况：**① 建表遗漏**（该建的表没建）**② 命名逻辑有 bug**（生成的名字与建表时不一致）。**两者的告警级别都应高于其它 B 类**——因为它们是"平台侧自己错了"，不是"设备侧的数据有问题"。

### 轴 8 — 入库成功 + 队列 Ack

**方向对，而且顺序也对了**（"入库，然后 Ack"）。要把它写成一条**硬约束并说明理由**：

| 顺序 | 崩溃点 | 后果 |
| --- | --- | --- |
| **先入库成功 → 再 ack** | ack 之前崩溃 | **消息重投 → 重复写**（第 1 项已证 `(子表, ts)` 幂等 → **安全**） |
| 先 ack → 后入库 | 入库之前崩溃 | **数据永久丢失**（不可接受） |

⭐ **这就是第 1 项那个幂等设计的兑现点**——它不只是一个理论性质，而是**这条顺序约束成立的前提**。

**【已收口】"ack 粒度"由轴 3（后半）定下 = 整批**：

`affectRows` **只给总数、不给行级失败定位**（详见「轴 3（后半）」），所以"丢弃失败那行、ack 其余"这条路**在技术上做不到**。三个候选只剩一个可执行：

| 方向 | 判定 |
| --- | --- |
| **整批不 ack、全部重投** | ✅ **唯一可执行**——幂等（`(子表, ts)` 覆盖）保证已成功的行不会被重复写入，**安全**；代价是好数据陪着一起重投（效率损失，非正确性问题） |
| 拆成单条重投 | ❌ 做不到——无法定位是哪几行失败 |
| 整批进 failed | ❌ 与轴 7 的分工冲突：这是 **A 类（可重试）** 的场景，不该走人工；进 failed 会让好数据也停摆 |

⚠️ 注意区分：**"整批重投"适用 A 类（可重试）失败**；如果是 **B 类（重试无意义）**，仍按轴 7 的处置——**耗尽重试后进 failed 集合 + 告警**。

### 轴 9 — 连接管理：**"20 请求/秒"是请求速率，不是连接数**

**【AI 纠偏】两个概念要分开**：

| 量 | 值 / 状态 | 是什么 |
| --- | --- | --- |
| **请求速率** | **20 请求/秒** | 10,000 行/秒 ÷ 500 行/批 —— 单位时间的请求数 |
| **连接数** | **待换算** | 开几条 WebSocket 连接 —— **这才是轴 9 问的** |

⭐ **两者不是一回事**：20 请求/秒 **可以用 1 条连接串行做完**，也可以分到 4 条各做 5 次。

**由 20 请求/秒 能推出的**：

| 项 | 推算 |
| --- | --- |
| 单次往返预算 | 1 ÷ 20 = **50 ms** |
| 本机实测（REST，2000 行/批） | 约 **19 ms** ⇒ **单连接理论够用** |
| 串行 20 个请求的耗时 | 20 × 19 ms ≈ **380 ms** —— 仍在 2 s 窗口内 ✅ |

⇒ **20 请求/秒 不需要很多连接，1~2 条就够。**

**【AI 补全】但"够用"不等于"该只开一条"**，两个理由：

1. **故障隔离**：一条连接挂掉时全部写入停摆；多条连接则只有部分受影响
2. ⭐ **突发**：设备上报通常**整秒对齐**（模拟器就是每秒一条）→ 2 s 的 flush 会让**所有批几乎同时到期** → 瞬间并发约为平均值的一整倍（约 20 个请求同时到达）
   - 串行摊平需 380 ms；若要更快压平突发，就需要多连接

**【AI 判断】默认 2~4 条，且可配**（与轴 2 的"支持配置化"保持一致）。

⚠️ **连接数不是越大越好**——TDengine 有真实的会话上限（`0x80000022` rpc too many session、`0x80000309` 用户连接数过多）；且 `adapter_ha`（跨 taosAdapter 的负载均衡与故障转移）在**单节点部署下没有意义**。

**【AI 补全】轴 9 的后半问——"断开怎么重连"——有现成答案，但要先把三层重试的边界划清**

`@tdengine/websocket` 的连接参数里**内建了重连**：`retries`（默认 5）、`retry_backoff_ms`（默认 200，指数退避至 `retry_backoff_max_ms` 默认 2000）。⇒ **连接级重连不用自己写。**

但由此出现**三层重试**，职责必须划清（否则会互相叠加）：

| 层 | 谁负责 | 职责 | **不该做的事** |
| --- | --- | --- | --- |
| 1 **连接重连** | 连接器内建 | 把连接弄回来 | **不做数据级重投** |
| 2 **写入重试** | 消费者自己（轴 6） | 这一批没写成功 → 重试这一批 | 不要无限重试 |
| 3 **队列重试** | BullMQ（ADR-010） | 这条消息没处理完 | **不该被瞬时抖动刷爆** |

⭐ **分工判据**：**第 1+2 层要"吃掉"瞬时的连接类故障**；**只有持续失败才升级到第 3 层**。
⇒ 否则队列会被网络抖动刷爆，**failed 集合里全是本可自愈的消息**，把轴 7 的"人工处理"淹没掉。

**【已收口，见轴 6】上面的"三层"可简化成两层**——因为**写入层自造重试意味着"重试期间数据在内存里"，进程崩溃就丢**。轴 6 的结论是：**去掉中间那层，写入失败直接抛回队列**，由 BullMQ 重试，数据全程在 Redis。详见「轴 6」一节。

**这一条直接接到轴 6。**

### 轴 10 — 解析后立刻检测，与设备管理核对

**方向对**：越早检测越省——**错数据不该走到写入那一步**。

**【AI 纠偏】"和设备管理核对"藏着一个规模问题。** 按修正后的口径（万级设备），逐条报文查设备档案 = **1 万次/秒 的 PG 查询**，不可接受。
⇒ **必须走本地缓存 + 失效策略**。这与仓库 backlog 里「权限与动态路由 Redis 缓存」是同一类问题：**每请求实时查库在规模下不成立**。

**【AI 纠偏】设备档案属于增量 3，现在还不存在。** 第 1 项已定：设备档案在 PG，是**增量 3（物模型与设备注册）**的产物。所以"与设备管理核对"在增量 2 阶段**核不了**。

✅ **过渡形态已定**（2026-10-09，随第 1 项 §8 的 C 模型一并定）：**增量 2 用一份 seed 配置承载档案**——它既是"设备 / 采集点存在性"的核对依据，也是 **`localPointId → pointKey` 的映射来源**；**增量 3 把它换成真档案，子表名不动**。

| 过渡 | 能核什么 | |
| --- | --- | --- |
| 用**超表的列集合**核对"指标是否已知" | **现在就有**（schema 已定），零依赖 | 与 seed 并用 |
| **用配置 / seed 的设备清单** | 设备编号与采集点编号 | ✅ **选定** |
| 留出接口，增量 3 接入真档案 | 三者齐全 | 增量 3 落地时 |

⚠️ 两处实现约束：**必须本地缓存**（万级设备下每条报文查 PG 不成立）；**缺省 `001` 只对登记为单点的设备生效**（第 1 项 §8.3）。

**【AI 补全】检测不能拖慢写入的时序。** "解析后立刻"若包含**查库 / 查缓存**，就变成一次异步等待，会卡在攒批路径上。建议的切法（供取舍）：

- **同步判定**（不需外部信息）：格式、字段完整性、值域、**指标是否在超表列集合内**
- **缓存判定**（需要档案）：设备编号 / 采集点编号存在性

⭐ 第 1 项检测清单的**第 1 条（重复 `ts`）天然在这条链上**——解析后即可判（同一子表同一 `ts` 在批内重复）。

### 7.2 轴 4 与轴 10 的冲突：**已由轴 4 的修订消解**

原冲突长这样：

```text
轴 10：解析后与设备管理核对 → 没档案的报文应被拦下
轴 4 （自动建表方案）：子表不存在就自动建 → 相当于"没有档案也照写"
```

**如果设备档案是权威，那"子表不存在"就意味着"这台设备没注册"**——这时**不该建表，该拒绝**。而**业界标准的解法正是注册制**（未注册设备 → 拒绝 + 告警，而不是建表）。

⭐ **轴 4 修订为"预建"之后，这个冲突消失了**：**表存在 ⇔ 设备已注册**。两个轴现在指向同一件事。

**分期的形态**：

| 阶段 | 建表在哪 | 谁执行 |
| --- | --- | --- |
| **增量 2** | **手动 / 脚本预建**（拟成可重复执行的脚本） | 平台侧初始化步骤（按模拟器的设备清单） |
| **增量 3 起** | **设备管理在注册时预建** | 设备注册流程 |

⇒ ⭐ **增量 2 那个建表脚本就是增量 3"注册时建表"的原型**——将来把逻辑搬进注册流程即可。**这条分期线画得很干净：同一件事，先由脚本做，后由注册流程做。**

#### 被否决的方案：自动建表

| 方案 | 否决理由 |
| --- | --- |
| **自动建表**（`INSERT ... USING ... TAGS`，子表不存在则自动创建） | ① **表名写错会静默多建一张表**，读起来像成功——正好命中第 1 项头号失败模式（子表名生成不确定 → 幂等破、重复行不报错）；② **它绕过了设备档案**——与轴 10"解析后与设备档案核对"的方向相反（没档案也照写）；③ **与轴 1 的路径选择互斥**——自动建表属 SQL 系，而参数绑定在建表语义上是"报错"而非"自动建"；④ 官方明说它需要 *frequent table existence checks* |
| **按需预建**（先走参数绑定，遇"表不存在"再补一条自动建表语句） | 它保住了自动建表的能力，但**同样绕过了"表存在 ⇔ 已注册"这条不变量**；而预建已经把建表动作前移到注册环节，这层兜底不再需要 |

### 7.3 剩下六条的业界参考

| 轴 | 业界怎么做 | 可参考的数字 / 形态 |
| --- | --- | --- |
| **1 写入路径** | 业界的客户端（Telegraf、官方 SDK）**默认就把批量做对**，使用者不纠结底层写法。InfluxDB 官方明说 Telegraf 与客户端库"**employ most write optimizations by default**" | ⇒ **判据的重心不在"哪条路径"，在"批量有没有做对"** |
| **2 攒批触发条件** | ⭐ **不是二选一，是"或"**：Telegraf 的形态是「**攒到 1000 条 或 满 10 秒，先到先 flush**」 | **条数 + 时间双触发**；另有**缓冲上限**（`metric_buffer_limit = 10000`）兜住积压 |
| **3 批大小** | 官方给了具体数字：**InfluxDB：optimal = 5000 lines**；**Telegraf 默认 = 1000** | ⚠️ **不能直接搬**（不同系统），但**量级在 10³**；而且 InfluxDB 把"一条请求写多点"列为**首要优化** |
| **5 失败怎么知道** | Kafka / SQS 的模型都是「**由消费者控制 ack**」；失败 = 没 ack | 我们的抓手是 TDengine 特有的 **`exec` 返回 `affectRows`** —— 比"没 ack"更精确 |
| **6 A 类重试** | ⭐ **BullMQ 默认不重试**——要重试**必须显式**配 `attempts` + `backoff`。内置 `exponential`（`2^(n-1)×delay`）与 `fixed`，**都支持 `jitter`**；SQS 侧对应 `maxReceiveCount`，官方警告**别设太低** | **指数退避 + 抖动**是共识；jitter 的存在是为了**避免重试风暴同步**（这一点我们在增量 0 第 6 讲见过实例：EMQX 的 mass client reconnections） |
| **9 连接管理** | InfluxDB 明确建议 **gzip 压缩**（"benchmarks have shown up to a **5x** speed improvement"）；容量上限是普遍现象（Kinesis 每 shard 写 1000 记录/s；TDengine 的 `0x80000022 rpc too many session`） | 连接数**不是越多越好**，上限真实存在；**压缩是便宜的提速手段**（待核实：`@tdengine/websocket` 是否支持 gzip） |

### 7.4 由此可以带走的三个判断

1. **业界对"批量"的态度是默认优化，不是可选项**——所以轴 2、3 不是"要不要做"，是"参数定多少"。
2. **"至少一次 + 幂等"是标准组合，"恰好一次"是营销词**——你的轴 8 已经站在标准答案上。
3. **"没注册就不该写"是业界的方向**——你的轴 10 与之同向，轴 4 是过渡期的权宜；**增量 3 落地时要把两者接上**。

## 9. 定稿：结论四件

> 十轴全部作答。按决策卡模板收口四件：**选定 / 代价陈述 / 退出成本 / 触发点**。

**① 选定**

```text
写入路径  参数绑定 STMT —— 走**不带 `USING`** 的形态（写具体子表名 + 绑参表）
          ⚠️ 带 `USING` 的 STMT 会自动建表，会顶掉"表存在 ⇔ 已注册"这条不变量（§10 N3）
          代价：表名写死在 SQL 里 ⇒ **每个子表一条语句**——"一个 stmt 句柄 + 一次 exec 覆盖
          整批"（§10 N1 实测的 5.5×）只在 `USING` / `tbname` 形态下成立，写死子表名时拿不到
          （§10 N2 形态② 或能兼得，未验——见 §8）
建表      预建。增量 2 用可重复执行的脚本；增量 3 起由设备注册预建。不做自动建表
攒批      条数 或 时间，先到先 flush
批大小    500 条（默认，可配）；单次 bind/exec 硬上限 32767 行（§10 N5）
flush     2 秒（默认，可配）→ 交接点 250 行/秒
批的子表  每批多个子表（高基数下的唯一形态）
失败判定  异常优先（分可重试 / 重试无意义 / 需人介入三类），再核对影响行数
重试      队列层：BullMQ exponential + jitter
          写入层不另造重试——失败直接抛回队列，数据全程在 Redis
消费语义  先入库成功 → 再 ack；ack 粒度 = 整批
连接      2~4 条（可配）；连接级重连用连接器内建 retries/backoff
检测      解析后立刻：格式 / 值域 / 指标是否在列集合内（同步）；设备与采集点存在性（缓存）
```

**② 代价陈述（这套写入方式会怎么坏）**

| # | 失败模式 | 什么时候会咬人 |
| --- | --- | --- |
| 1 | **参数绑定调试难**——失败时看到的是绑定调用栈，不是 SQL 文本 | 第一次在生产排查写入失败 |
| 2 | **部分成功只知总量、不知哪几行**（`getLastAffected()` 是总数） | 跨 VNODE 的部分失败 |
| 3 | **整批重投**——好数据陪着坏数据一起重投 | 批内出现 B 类错误行时 |
| 4 | **漏建子表会直接报错**（预建的代价） | 新设备上线忘记建表；或建表脚本与命名规则不一致 |
| 5 | **`flush_interval = 2 s` 抬高了入库延迟下界** | 端到端延迟要求进入秒级以内时（增量 5 告警） |
| 6 | **多子表批 + 突发**：设备整秒对齐 → 批几乎同时到期 | 万级设备下若连接数配少了 |
| 7 | ⚠️ **误用带 `USING` 的写法 ⇒ 子表不存在时静默建表**（"表存在 ⇔ 已注册"失效，回到 §1 的头号失败模式） | 实现时照抄官方 Node 示例 |
| 8 | ⚠️ **缺子表的报错形态随路径而异**——**STMT2** 路径的报文是 C 源码路径（`clientStmt2.c[4946]…`，`code=555`）；本实现走的 **STMT1** 路径则是干净的 `WebSocketInterfaceError` + `code=9731` + `Table does not exist` | 排查漏建表——两条路径都带码，告警可按码分类 |
| 9 | ⚠️ **非法绑定与"连接已废"要分开处置**——实测（STMT1）非法绑定之后连接仍健康，但连接级错误（`108` / `104`）必须作废**那一条**连接并重连 | 上游送来一个坏值，或一条连接确已半开，而实现把"这一批失败"与"连接已废"混成一件事 |

**③ 退出成本（想换掉要付什么）**

| 换什么 | 代价 |
| --- | --- |
| 写入路径（STMT → 裸 SQL） | **低**——攒批与失败处理可复用，只换执行层；但会丢掉效率第一档 |
| `flush_interval` / 批大小 | **零**——可配项，改默认值即可 |
| 预建 → 自动建表 | **低**，但要接受"**表名写错会静默多一张表**"（否决理由见 §6 轴 4） |
| 队列层重试参数 | **零**——可配 |
| 从"整批重投"改成别的 ack 粒度 | **做不到**——`affectRows` / `getLastAffected()` 都不给行级定位（技术约束） |

**④ 触发点**

见 §8 的 13 项与 §6 各轴的标注。**三条最该盯**：

| 触发 | 回头改什么 |
| --- | --- |
| **定实现形态时** | 确认 `@tdengine/websocket` 的**客户端版本与服务端版本如何对齐**（连接器只有 `3.4.0` / `3.5.0`，服务端实测 `3.4.2.8`） |
| **增量 3 设备注册落地** | 把建表脚本的逻辑搬进注册流程（本项与增量 3 的衔接点） |
| **增量 5 要求秒级以内告警** | 重估 `flush_interval = 2 s` |
| **规模进入十万级** | 重估批大小、连接数与 `VGROUPS` |

## 10. 写入形态探针（2026-10-09 本机实测）

> 探针：`apps/nestjs-server/scripts/tdengine-stmt-probe.mjs`（用仓库里真正的 `@tdengine/websocket@3.5.0`，连本机 `3.4.2.8.community`）。
> **本节结论直接改写 §4.8 的容量口径、§6 轴 1 与轴 4 的论证、以及 §8 的待实测项**，并据此修正 §9 的选定表述。

| # | 实测 | 结果 |
| --- | --- | --- |
| **N1** | ⭐ **一次 exec 能不能跨多个子表** | ✅ **能**。100 子表 × 5 行 = 500 行，**一次 exec 21 ms**，`getLastAffected = 500`；同样数据逐子表 exec（100 次）**116 ms——慢 5.5 倍** |
| **N2** | **跨子表的两种写法** | **两种都可用**：① `INSERT INTO ? USING stb (tags) TAGS (?,?) VALUES (…)` + **`setTableName()`**（官方 Node 示例形态）；② `INSERT INTO db.stb (tbname, tag…, ts, …) VALUES (?,…)` + **`tbname` 作普通绑定参数**（官方 Java 示例形态） |
| **N3** | ⚠️ **带 `USING` + 子表不存在** | **自动建表**——子表被建出来、数据写进去、`getLastAffected = 1`，**不报错** |
| **N4** | 不带 `USING` + 子表不存在 | 两条路径的形态不同：本实现强制的 **STMT1** 抛 **`WebSocketInterfaceError` + `code=9731` + message `Table does not exist`**（干净、带码）；旧探针的 **STMT2** 默认路径报文是 **C 源码路径**（`clientStmt2.c[4946]stmtGetStbColFields2()`），**同样带码（`code=555`）** |
| **N5** | ⭐ **单次 bind/exec 的行数上限** | **32767 行成功（22 ms）、32768 行失败**（`bind number out of range or not match`）。与列数无关（1 列 35000 同样失败）⇒ **是行数上限，值 = 2¹⁵−1** |
| **N6** | `exec(sql)` 遇 SQL 错 | **抛 `TaosResultError`，带 `code`**（实测 `9730 Invalid column name`） |
| **N7** | `setTimestamp()` 收 epoch 毫秒数字 | ✅ 可用，回读与传入一致 |
| **N8** | `getLastAffected()` 的返回类型 | 写入器强制的 **STMT1** 路径上返回 **`number`**（实测 `value=1`、`typeof=number`）；**BigInt 形态属 STMT2 路径**（旧探针的默认），本路径不出现 |
| **N9** | 一次非法绑定之后 | **STMT1 路径上连接仍健康**——四种绑定形态（`566` / `65535` / `9730` / 类型不符或 `NaN`）之后均以**同一条连接的下一次成功写入**（`affected=1`）证明，不只是"没抛异常"；"持续重连失败"（后续操作全部 `Failed to reconnect to any available address`）属 **STMT2** 路径（§8 第 11b 项即把该现象归因于 `stmt2 recover exceeded max attempts`） |

**连接器 STMT 的实际 API 面**（`WsStmt`）：`prepare / setTableName / setTags / newStmtParam / bind / batch / exec / getLastAffected / close`。
⚠️ **类型映射方法挂在 `newStmtParam()` 返回的绑参对象上**（`setTimestamp` / `setFloat` / `setInt` / `setBigint` / `setVarchar` …），**不在 stmt 上**——§6 轴 1 列的那族方法名是对的，归属要说清；调用形态是 `newStmtParam()` → `setXxx([...])` → `bind()` → `batch()` → `exec()`。

⚠️ **N2 的形态②（`INSERT INTO <stb> (tbname, …)` 且 `tbname` 作普通绑定参数）的两项关键行为尚未取到干净样本**——子表不存在时是报错还是静默建表、一次 `exec` 能否覆盖多个子表（§8 第 15 项）。本实现走的是**写死子表名**的 STMT1 形态（§9 选定）：它保住了"表存在 ⇔ 已注册"的防线与缺子表的干净报错（N4），代价是每个子表一条语句、拿不到 N1 的 5.5×；形态② 若两项都成立，正是能兼得的那条路。

**两条连接器质量信号**（供准入判据参考）：

- `@tdengine/websocket@3.5.0` 把 **`typescript` 列进 `dependencies`**（应在 dev），并把 **`winston` + `winston-daily-rotate-file`** 作为运行时依赖——官方连接器绑一个日志框架。
- 连接器只有 **`3.4.0` / `3.5.0`** 两个大版本，而服务端实测 `3.4.2.8`。**客户端版本与服务端版本如何对齐，是本项未定的开口**（探针用 3.5.0 打 3.4.2.8 是通的，但这不等于该这么配）。

**由 N1 / N3 / N5 改写的三处结论**：

| 原结论 | 改写后 |
| --- | --- |
| §4.8「单条 SQL 默认约 4 MB ≈ 13 万行/批——批上限在 P1 规模下不会先撞到」 | **那是裸 SQL 的口径**。**STMT 路径的单次 bind/exec 上限是 32767 行**，低得多。默认批 500 依然安全，但容量模型要按这条重算 |
| §6 轴 4「预建 ⇒ STMT 在子表不存在时**报错**，这层报错是防线」 | ⛔ **只在不使用 `USING` 语法时成立**。带 `USING` 的 STMT **会自动建表**，与裸 SQL 一样——**防线不存在，且失败形式退回"静默多建一张表"**（§1 的头号失败模式）。⇒ **实现必须刻意选不带 `USING` 的写法** |
| §6 轴 1「Node 侧用哪种写法待实测」 | ✅ **两种都可用**（N2）。选型判据变成：**要不要 `USING` 的自动建表能力**——按轴 4 的结论，**不要**，所以走不带 `USING` 的形态 |

**由 N1 强化的结论**：轴 3 后半"每批多子表是高基数下的唯一形态"**成立，且实现上更干脆**——**一个 stmt 句柄 + 一次 exec 覆盖整批**，不必"每子表一个句柄"（⚠️ 该形态需 `USING` / `tbname`；本实现写死子表名时拿不到，见 §9 选定与 §10 N2）。⚠️ 但**"部分成功"的粒度仍是整批**：`getLastAffected()` 给的是总数（N1 实测 500），**不给行级定位**，§6 轴 5 与轴 8 的"整批重投"结论不变。
