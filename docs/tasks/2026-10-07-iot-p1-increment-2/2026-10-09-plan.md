## Task 3 设备档案 + 存在性检测

决策 1 §8.1 定的模型 C：**子表名里的两段都由平台生成**，设备只报一个"自己稳定"的本地编号。

- **承载**：TS 配置模块（不进 PG）——增量 3 换成真设备档案，**子表名不动**
- 两个映射：`localDeviceId → deviceId`、`(localDeviceId, localPointId) → pointKey`
- 取值规则（§8.2 / §8.3）：`deviceId` 16 位全大写随机串、`pointKey` 3 位递增补零、分隔符 `_`
- ⚠️ **三条配套规则要落进代码**：① `pointKey` **只增不复用**；② 缺省 `001` **只对登记为单点的设备**生效，多点设备漏 `pointId` ⇒ **拒绝 + 告警**；③ `localPointId` 超长**拒绝，不截断**
- ⚠️ **归一化**：TDengine 标识符折小写、**标签值保留原样** ⇒ 两边比对前**先统一转小写**（决策 1 §9.1 V3）
- **本地缓存 + 失效**——万级设备下逐条查档不成立（决策 2 §6 轴 10）
- ⚠️ **模拟器与档案必须同源**：模拟器报的 `localDeviceId` 不在档案里 ⇒ 判未知设备、全量丢弃 ⇒ **判据 1 直接不成立**。设备清单**只能有一处定义**
- ⚠️ **建表脚本也要读这份档案**（枚举子表名）⇒ 3 个消费方（server 消费者 / 建表脚本 / 模拟器）指的是同一份。**承载位置待定，见文末**
- **验收**：单测覆盖两个映射、缺省规则、超长拒绝、归一化

## Task 4 TDengine 建库 / 建表 / 建流脚本

- **形态**：可重复执行（`IF NOT EXISTS`、建流前先判存在）；接一个 `pnpm ops:tdengine-init`；**不进应用启动路径**（C3）；由 `ops:env-up` 串上（与 `migrate` / `seed` 同形）
- **原始库** `wewant_iot`：`PRECISION 'ms' KEEP 1095 DURATION 10`
- **超表** `telemetry`：`ts` + 每测点「值 + `_unit`」；`TAGS (deviceId VARCHAR(16))`
- **子表**：按档案枚举，`{deviceId}_{pointKey}`，`USING telemetry TAGS ('<deviceId>')`
- **降采样库** `wewant_iot_ds`：`PRECISION 'ms' KEEP 3650 DURATION 10`
- **三张表** `telemetry_1m / _1h / _1d`：16 列同形；`ALTER STABLE telemetry_1m KEEP 1095`（全案唯一的超表级 `KEEP`）
- **三条流**：`PERIOD(…)` 触发；**平级**——都 `FROM wewant_iot.telemetry`；`PARTITION BY tbname` 紧跟 `FROM` 之后、`INTERVAL` 之前；⭐ **计算子句不带 `%%trows`、也不带增量 `WHERE`**
- **时区**：`Asia/Shanghai` 设在服务器 / 集群级，并写进 `taos.cfg`（流级 `CONFIG(timezone=…)` 在 3.4.2.8 不可用）
- ⚠️ **本任务要一并收口的四条未实测**：
  1. **`_unit` 两列**未单独实跑过（决策 1 §9.1 标注，与其余列同形、风险低）
  2. `PERIOD(1d, 8h)` 的 **offset 语法**（决策 4 §14.4）
  3. 不指定 `OUTPUT_SUBTABLE` 时**输出子表名的默认值**（同上）
  4. `TAGS (… AS …)` **标签继承**的实际行为（同上）
- **验收**：空库跑一遍、再跑一遍都不报错；`SHOW TABLES` 见全部子表（⚠️ 无数据的子表不出现在超表 `SELECT` 里，列子表要用 `SHOW TABLES`）；写入一条后超表 `SELECT` 可见

## Task 5 队列层

- 依赖 **`bullmq`**（MIT）——⚠️ **只有 server 一个 workspace 消费，按 catalog 判据不满足 ⇒ 留应用本地**（与 `@tdengine/websocket` 同处置）
- 队列名 **`iot:telemetry:ingest`**
- **两类连接配置不同**：Queue（生产者）**快速失败** + `enableOfflineQueue: false`；Worker（消费者）**无限等待** + `maxRetriesPerRequest: null`
- **保留策略**：`removeOnComplete: true`（或只留一小批）；`removeOnFail: { count: 5000 }`——⭐ **failed 集合就是"待人工看"的那个队列**（决策 2 §9 的 B 类处置）
- **重试**：`{ attempts: 5, backoff: { type: 'exponential', delay: 200, jitter: 0.5 } }`——⚠️ **BullMQ 默认不重试、默认不退避、抖动默认 0**，三样都要显式配
- **验收**：单测覆盖两类连接配置的差异；顺带实测确认 `attempts` 的实际计数口径（决策 2 §8 第 12 项）

- **入队在解析之前**：job 里放**原始报文**（缓冲层 §3.1）；增量 1 的"解析 + 校验 + 计数"随之**移到消费者**

- ⚠️ **连带**：持久会话重连会灌一波积压——BullMQ 正好吸收它，不用额外做

## Task 7 消费者 worker（独立入口）

- **形态**：与 HTTP 的 `main.ts` 并列的第二个入口，部署为**独立进程 / 独立 compose 服务**（缓冲层 §2.2）——可独立启停、可多实例、可独立扩缩
- **链路**：解析 → 检测 → 攒批 → STMT 写入
- **检测**（决策 1 §6.6 清单 + 决策 2 §6 轴 10 的切法）
  - **同步判定**（不需外部信息）：格式 / 字段完整性 / 值域 / **指标是否在超表列集合内**
  - **缓存判定**（需要档案）：设备与采集点存在性
  - **批内重复 `(子表, ts)`**——本套 schema 的头号失败模式；⭐ 它同时是 `affectRows` 核对的前提（不去重会把"覆盖"误报成"部分失败"）
- **未知测点**：**丢弃 + 计数 + 告警**——⚠️ 告警**必须带上报的那个 `key`**，否则人只知道"有未知测点"，不知道多了什么
- **攒批**：条数 500 或 2 s，先到先 flush；单次 bind/exec 硬上限 **32767 行**
- **写入**：参数绑定 STMT，⭐ **刻意走不带 `USING` 的形态**——带 `USING` 会在子表不存在时**静默建表**，顶掉"表存在 ⇔ 已注册"这条不变量；形态是**一个 stmt 句柄 + 一次 exec 覆盖整批**
- **核对**：`getLastAffected()`——⚠️ 返回 **BigInt**，直接 `JSON.stringify` 会抛
- **ack**：⭐ **入库成功 → 再 ack**；ack 粒度＝**整批**（`affectRows` 不给行级定位，"丢弃失败那行、ack 其余"技术上做不到）。⚠️ 写入层**不另造重试**——失败直接抛回队列，数据全程在 Redis
- **失败分类**：A 类（可重试）走队列重试；B 类（重试无意义）耗尽后进 failed 集合 + 人工。⚠️ `Table does not exist` 的告警级别**高于其它 B 类**——正常路径下它不该出现，一旦出现就是**平台侧自己错了**
- ⚠️ **一次非法绑定会把连接拖废**（决策 2 §10 N9）——"这一批失败"与"连接已废"要分开处理
- **优雅停机**：`SIGINT` / `SIGTERM` + `worker.close()`
- **验收**：数据落库；**强杀消费者 → 重启不产重复**（判据 3）
- ⚠️ **P1 不用 sandboxed processor**（**AI 判断**）：官方给它是缓解 CPU 密集处理器阻塞事件循环，P1 单机不是这个场景，先把形态跑通；触发点＝出现 `Stalled` 日志
