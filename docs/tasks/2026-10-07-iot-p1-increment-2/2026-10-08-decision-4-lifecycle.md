## 1. 背景：这一项要决定什么

**要做什么**：给遥测数据定下"**活多久、怎么老去、怎么删**"。

**为什么现在做**：⭐ **`KEEP` 不是"以后再调"的参数，它是建库语句的一部分**：

```sql
CREATE DATABASE power PRECISION 'ms' KEEP 3650 DURATION 10 BUFFER 16;
```

前两项定了 schema 与写入方式，**但建库语句还没法写**——因为 `KEEP` 与 `DURATION` 未定。

**不做的后果**：用默认值（`KEEP 3650` ＝ 10 年）。**默认值本身是个决定**——只是没人做过。

## 4. 项级背景

### 4.1 三个时间参数及它们的关系

| 参数 | 作用域 | 含义 | 默认 | 范围 / 约束 |
| --- | --- | --- | --- | --- |
| **`KEEP`** | 库级 / 超表级 | 数据保留天数，**超期自动删除** | **3650 天** | `[1, 365000]`；**必须 ≥ 3 × `DURATION`** |
| **`DURATION`** | 库级 | 单个数据文件覆盖的时间跨度 | **10d** | `[60m, 3650d]` |
| **`TTL`** | 表级 | 表存在超过 TTL 后**删表**（不是删数据） | 0（不限） | ⚠️ **与 `KEEP` 不联动**——官方原文："if `KEEP` is smaller than `TTL`, data may be deleted before the table is removed" |

⭐ **`KEEP ≥ 3 × DURATION` 这条约束值得单独注意**：它是硬约束，且**方向上把"文件跨度"与"保留期"绑在一起**。
【AI 判断，待验证】一个可能的解释来自同类系统的做法——TimescaleDB 明确说它**按 chunk（分片）整体删除，只删"全部数据都在时间范围之外"的 chunk**，而按行删很慢。⇒ 保留期至少覆盖若干个完整文件，才能让过期删除按文件整体进行。**这是类比推理，TDengine 官方未给出理由。**

### 4.2 ⭐ `KEEP` 的边界【本机实测】

**一条实测（重要且直观）**：在 `KEEP 365` 的库上写入 2 天前的数据 —— 被拒：

```
ERR[1547] Timestamp data out of range
```

⇒ **`KEEP` 不只是"到期删旧数据"，它还直接约束"能写多旧的数据"。**

⭐⭐ **这条与"断网补传"直接相关**：设备离线很久后补传的数据，**如果比 `KEEP` 还老，就写不进去了**——而这类写入在官方错误码表里对应 **`0x8000030B` Data expired**（第 2 项 §4.5 已列）。**即：`KEEP` 的取值决定了"补传窗口有多长"。**

**`KEEP` 的另外三条行为**（已在第 1 项核实）：

| 项 | 内容 |
| --- | --- |
| **超表级 `KEEP`** | **必须小于库级**，且**不立即生效**——要先 flush 再 compact |
| **社区版多级存储** | ❌ 不支持。只能一个 `KEEP` 值，**配多个也只取最大的那个** |
| **超表级能否更长** | ❌ **不能**（因为必须小于库级）⇒ **"某些超表留更久"在同库内做不到，只能另建一个库** |

### 4.3 删除：四种手段与它们的边界

| 手段 | 形态 | 边界 |
| --- | --- | --- |
| **过龄自动删** | `KEEP` 到期 | 只有一个阈值（社区版）；不能按设备/测点删 |
| **按时段删** | `DELETE FROM stb WHERE ts < '…'` | ⚠️ **`WHERE` 只支持对第一列（主时间戳）过滤**；**不可逆**——官方建议先跑同样的 `SELECT` 确认 |
| **空间回收** | 删除只**打标记**，行还在盘上 | 空间在 **`KEEP` 生效时**或**手工 `COMPACT`（企业版）**时回收 |
| **物理覆写** | `SECURE_DELETE`（库级 / 表级 / 语句级，按位或） | 合规场景；有代价 |

⚠️ **删列的破坏性**（第 1 项实测）：`DROP COLUMN` 之后**该列数据不可再查**（`Invalid column name`）。这是"减字段"而非"删数据"的路径，但同样不可逆。

### 4.4 ⭐ 降采样：社区版**实测有两条路**（不止一条）

这是本项材料里**最重要的一节**：**社区版有可用路径**，不止 `TSMA` 一条——而**真正能解决本项问题的是流计算**。

#### 路 A · 流计算（stream）——【本机实测】**可用，且端到端跑通**

| 实测项 | 结果 |
| --- | --- |
| `CREATE STREAM` 能否建 | ✅ **能**，`SHOW STREAMS` 返回记录 |
| 单节点是否需要手工建 snode | ✅ **不需要**——`SHOW SNODES` 显示 snode 已自动存在；手工再建报 `Only one snode can be created in each dnode` |
| 流的状态 | `Undeployed` → **`Running`**（有个自动部署周期，不是建完立刻生效） |
| **降采样是否真产出** | ✅ **产出**：`SELECT * FROM outD` → `ts="…16:11:00" v_avg=26` |

**跑通的形态**（`PERIOD` 定时触发 + 窗口聚合）：

```sql
CREATE STREAM <db>.s_downsample
  PERIOD(20s) FROM <db>.src
  INTO <db>.out_1m
  AS SELECT _wstart AS ts, AVG(v) AS v_avg FROM <db>.src INTERVAL(1m);
```

| ⚠️ 实测踩到的三处 | 说明 |
| --- | --- |
| **`INTERVAL` 作为流触发类型不被接受** | `INTERVAL(1m) FROM …` 报语法错误；**`PERIOD` 可以**。⚠️ 文档是 4.x 线，**与 3.4.2.8 不完全一致** |
| **`AGG` 是保留字，不能作表名** | 目标表取名为 `agg` 时，连 `SELECT * FROM agg` 都报语法错误 |
| **输出表第一列必须是 `TIMESTAMP`** | 报 `The first column of stream output must be timestamp`——语义校验，不是语法错误 |

⭐ **一个判断方法上的收获**：语法错误（9728）与语义错误（9816 / 16656）**要分开看**——**报的是语义错误，说明语法已被接受**。上面"流是否可用"这个结论，正是靠这个区分判定的。

#### 路 B · `TSMA`（时间段小物化聚合）——【已核实】

⚠️ **先归位**：`TSMA` 是**查询加速器**，不是生命周期工具——**它不省存储，反而多占**（官方原文：其中间结果 *"generally **larger** than the original data size"*）。

- ✅ 社区版可用。**后台走流计算**——官方原文：*"TSMA background calculation uses stream computing, each TSMA creation will create a stream"*（⇒ 它与路 A **不是平级的两条路**，是流计算的一个特化封装）
- 输出是**同库的一张不可见超表**（"invisible to the user"），随 `DROP TSMA` 自动删；**用户照常查原始超表，由优化器改写**去读它
- ⚠️ **`querySmaOptimize` 默认 0**——**建了默认也不生效**
- ⚠️ 官方明说它 *"do not guarantee real-time accuracy, but can ensure ultimate correctness"*；`maxTsmaCalcDelay` 默认 600 s，落后超过 10 分钟则查询不用它
- ⚠️ **只有时间窗、只有九个函数**（`min` / `max` / `sum` / `first` / `last` / `avg` / `count` / `spread` / `stddev`，参数须**普通列**）；`WHERE` 筛普通列、`GROUP BY` 含普通列、非 `INTERVAL` 窗口**一律用不上**
- ⚠️ **会反向锁住原始表**：标签列不可删、标签名与子表标签值不可改、被它用到的列不可删（须先删 `TSMA`）；加列不受影响但新列不进任何 `TSMA`
- ⚠️ 全集群上限 `maxTsmaNum` **默认 10**（范围 `[0,10]`），且**每个 `TSMA` 占一个流**

⛔ **所以它不解决本项的问题**：它优化的是"**已经查得到的东西查得更快**"，而本项要的是"**原始只留短、汇总留长**"。它的输出留在同一个库、跟着库级 `KEEP` 一起过期——**既不可能延长留存，也不减少存储**。

#### ❌ 走不通的：`RSMA`（按时间窗降采样存储）

- **仅企业版**（自 v3.3.8.0）。官方原文：*"Starting from v3.3.8.0, TDengine **Enterprise** provides downsampled storage"*
- 它的机制是"数据从低层迁移到高层时自动降采样"，与"保留原始短期 + 聚合长期"的分层存储绑定——**社区版没有分层存储，所以这条路整体不存在**

#### 路 C · 应用层自己算（一定可用）

不依赖数据库特性：消费者/定时任务算完聚合，写进另一张超表或另一个库。

#### 行业对照：主流时序库怎么做

**TimescaleDB（已在第 2 项的调研中取到）**：

| 它的概念 | 对应的 TDengine 概念 |
| --- | --- |
| **retention policy**（自动删旧原始数据） | **`KEEP`** |
| **continuous aggregates**（后台随新数据自动刷新的物化聚合） | **流计算**（`TSMA` 是查询加速，不改存储与留存） |
| **drop by chunk**（按分片整体删，不按行删） | **按 `DURATION` 分的数据文件整体过期删除** |

⭐ **它的官方推荐形态是一句话**（原文）：*"By combining retention policies with continuous aggregates, you can **downsample your data and keep useful summaries of it instead**"* —— **删原始、留汇总**。

⚠️ **但这个形态在 TDengine 社区版有个额外的结构约束**：`KEEP` 是**库级**，而**超表级 `KEEP` 只能比库级更短** ⇒ **"原始短留 + 聚合长留"不能靠超表级 KEEP 实现，只能把聚合结果放到另一个库**。

### 4.5 容量量级

| 项 | 量 |
| --- | --- |
| 目标规模 | 万级设备 × 1 Hz ≈ **10,000 行/秒** |
| 行宽 | 约 **32 字节**（`ts` 8 ＋ 3×`DOUBLE` 24） |
| 未压缩 | ≈ **27 GB/天** |
| 按官方压缩口径（约 1/10） | ≈ **2.7 GB/天 ≈ 1 TB/年** |

⚠️ **本机测不出可信的压缩比**（第 2 项已说明：测试数据是确定性序列，压缩比失真）。⇒ **真实压缩比要等增量 6 用真实波动数据实测。**

⭐ **于是"`KEEP` 给多少"这件事，第一次有了成本含义**：

| `KEEP` | 原始数据量级（按 1/10 压缩，参考值） |
| --- | --- |
| 90 天 | ≈ 0.25 TB |
| 365 天 | ≈ **1 TB** |
| 1095 天（3 年） | ≈ **3 TB** |
| 3650 天（默认） | ≈ **10 TB** |

⚠️ 而上表用的是**未经验证的压缩比**；若真实压缩比只有 1/5，则量级翻倍。

### 4.6 与写入链路的耦合

| # | 耦合 | 影响 |
| --- | --- | --- |
| 1 | **`KEEP` 决定"能写多旧"** | 补传窗口的上限（§4.2 实测）——太老的补传数据会报 `Data expired` |
| 2 | **超表级 `KEEP` 不立即生效** | 改了之后要先 flush + compact，**不是即时行为** |
| 3 | 降采样的流**会占用 snode 与流资源** | 流数量有上限（`maxTsmaNum` 只是 TSMA 的；流的数量另有约束，见 §6） |

### 4.7 生命周期与"数据不可变"的关系（合规口径）

工业/环保场景有一条通行原则：**采集数据不可修改**（决策人熟悉这一条——HJ212 体系里的数据质量约束）。

由此产生一个需要显式回答的问题：

> **"到期删除"算不算"修改数据"？**

【AI 判断】两者不冲突，但要**分清三件事并分别口径**：
1. **不可修改**：指已采集的数据在有效期内**不得被篡改**（业务规则）
2. **到期删除**：指**超出约定保存期**后按制度销毁（合规规则）——它是**制度化的**，不是"修改"
3. **两者都需要审计**：**谁、什么时候、依据什么删了什么**——否则"不可修改"这句话无法自证

⇒ ⭐ **真正的设计含义**：**删除动作本身要留痕**。这一条与"**应用层只追加、物理删除走 `SECURE_DELETE`**"是同一件事的两面。

⚠️ 而**保存期定多长**属于**业务/合规输入**，不是技术输入——目前**没有输入**（前提复议里把它列为"D3 留存与审计的合规倒推"）。

### 4.8 ⚠️ 一个没被任何地方覆盖的：备份与恢复

**现状**：仓库 backlog 里有「**数据库备份与恢复演练**」条目，但它的内容是 **`pg_dump` 定时备份**——**那是 PostgreSQL 的**。

⇒ **TDengine 侧的备份与恢复，此前没有任何地方覆盖过**，而它属于"数据生命周期"里"保留"的另一半（**防丢**，而不只是**防涨**）。

**官方给的现成工具**【已核实】：

| 项 | 内容 |
| --- | --- |
| 工具 | **`taosdump`**——官方高性能备份 / 恢复工具，**列式压缩格式** |
| 支持的粒度 | **全量 / 库级 / 表级 / 时间范围 / 仅元数据**；**支持可续跑** |
| 用法 | `-o` 备份 / `-i` 恢复；**含在服务端与客户端安装包里**；跑在 Windows / macOS / Linux |
| ⚠️ 版本 | **自 v3.4.2.0 起全新升级**（更高性能、更小体积）；新版**支持导入旧版 avro 格式，但不再生成 avro**。**本机实测版本 3.4.2.8 ⇒ 已是新版** |

## 5. 决策轴与答复

### 5.1 轴清单（含答复摘要）

| # | 问题 | 决策人的答复 |
| --- | --- | --- |
| 1 | `KEEP` 给多少天？依据？ | **3 年**。依据＝**业务/合规**（金升阳要求溯源 3 年；环保行业需累积数据） |
| 2 | `DURATION` 给多少？ | **默认 10 天**。依据＝文件数量可控（37/年、111/3 年） |
| 3 | 要不要降采样？用哪条路？ | **要；用流处理** |
| 4 | 降采样的粒度与聚合函数？ | **粒度＝分钟 / 小时 / 天三级**；⚠️ **聚合函数暂不定**，留到 P2 上真实设备后按业务指标定 |
| 5 | 降采样结果放哪？ | **单独建一个库**，**按 10 年存储** |
| 6 | 怎么删？ | **靠 `KEEP` 自动删除**；有特殊场景再手动操作 |
| 7 | 要不要 `SECURE_DELETE`？ | **不要** |
| 8 | 要不要超表级 `KEEP`？ | **不用**，按库级即可 |
| 9 | 备份与恢复怎么做？ | **要做，且定期做**：**每月 1 次**，以增量方式将原始数据备份导出到专门位置（生产上可能是独立磁盘 / 专用存储服务器）。目的＝**`KEEP` 删除后这些数据仍能恢复**，满足特定场景的追溯需要——**也算合规要求的一种** |
| 10 | 合规口径怎么定？ | **要开启数据库级审计**：修改与删除操作——**无论是 `KEEP` 策略自动删除，还是人为在库中修改/删除**——都应有审计记录 |

### 5.2 决策人原话

> 1. Keep 这块我计划是给 3 年，在工业场景下，之前在金升阳那边，他们要求数据可以溯源 3 年。虽然那时候说的是图片场景，但数据最起码也应该是这样子的。在环保行业，其实他们也是需要累积数据的。像以前在环保行业的一些项目里面，会给他们导出历史的空气质量监测数据，一般来说，会给他们补足前 5 年的数据。
> 2. 审就按照默认的 10 天一份的维度去处理，应该就可以了。一年 37 份数据文件，三年 111 份文件，不算太多。
> 3. 降采样采用流处理。
> 4. 降采样的粒度，分钟、小时、天这三个应该都是要的。但是具体到不同指标分别采用什么样的聚合函数，我目前确实没办法去确定。这得根据具体的业务指标来，不同的指标聚合方式应该是不同的，大概应该在 P2 阶段上真实模拟设备的时候再去确定。就像之前在环保行业，不同的监测指标，做这种从 5 分钟到小时、从小时到日均的统计都是不同的。
> 5. 降采样的结果单独建一个库，按 10 年的维度去存储。
> 6. 数据的自动删除还是靠 keep 机制去删，如果有特殊的场景的话，再手动去操作。
> 7. 不要 SECURE_DELETE。
> 8. 不用超表级 KEEP，按库级即可。
> 9. 备份和还原这个肯定是要做的，而且要定期去做。按照每个月 1 次的以频率增量的方式，将原始数据备份导出，存储在专门的位置。如果到生产环境的话，这个位置可能就是一块单独的磁盘，又或者是专用的存储服务器。这样能够保证，按照库级 Keep 策略将原有的原始数据删除之后，这些数据也能够恢复回来，满足特定场景下的追溯需要。这也算是合规要求的一种。
> 10. 要开启数据库级的审计。对于修改和删除操作，无论是按 keep 策略自动删除，还是人为在数据库中进行的修改和删除，都应该有审计记录。

## 6. AI 补全与纠偏（逐轴）

### 轴 1 · `KEEP` = 3 年

✅ **值合法、依据成立**：1095 天在 `[1, 365000]` 内；且 `1095 ≥ 3 × 10`（`DURATION`）✓

⭐ **本轮实测改变了本轴的风险等级**：**`KEEP` 可以后改**——`ALTER DATABASE … KEEP 1095` 实测成功。⇒ **这是可逆的决定**，选错了不必重建库。（与轴 2 相反，见下。）

⚠️ **一处需要显式处置的冲突**：决策人提到"环保行业会给**补足前 5 年**的数据"——**5 年 > 3 年**。若要把 5 年前的历史导入，**`KEEP 1095` 会直接拒绝**（`Timestamp data out of range`，§4.2 实测）。

【判据】**"在线保留期"与"导入历史"是两件事**。导入更早的历史有两条路：① 导入前**临时调大 `KEEP`**（可行，因为 `KEEP` 可 `ALTER`）；② 导入到一个**独立的归档库**（各自有各自的 `KEEP`）。
⇒ **3 年这个值本身没问题**，但"导入超过 3 年的历史数据"必须写成一条**需要单独处置的操作**，不能默认它可以直接进主库。

⚠️ **一处口径提醒——业务说"能溯源 3 年" ≠ `KEEP` 给 3 年**：`KEEP` 是**到期即物理删除**，第 1096 天就查不到。两者差一个"余量"。⇒ 处置有两条：留余量，或**靠归档兜底**。

⭐ **本轴与轴 9 是配套的**：决策人选了月度归档，**`KEEP` 才敢卡在业务线上**。这个组合自洽——但**依赖关系要写明**：**轴 1 的安全边界由轴 9 保障**；若轴 9 不做或做不到，轴 1 就该留余量。

**量的核算**：3 年 × 约 1 TB/年 ≈ **3 TB**（按 1/10 压缩，第 2 项 §4.8 口径）。

### 轴 2 · `DURATION` = 10 天

✅ 算术对（365/10→37、1095/10→111）；10d 是默认值；`1095 ≥ 3 × 10` ✓

⭐ **本轮实测最关键的一条**：**`DURATION` 不能后改**——`ALTER DATABASE … DURATION 30` 报 **9728 语法错误**。
⇒ **这是本决策卡里真正"一次定对"的参数**，比 `KEEP` 更要紧。选错的代价是**重建库**。

⚠️ **补全：`DURATION` 的作用不只是"文件数量"**。它同时是**过期删除的粒度**——社区版按**整个数据文件**过期删除，所以：
- `DURATION 10d` ⇒ 删除以 10 天为粒度发生，**最坏情况下数据会比 `KEEP` 多留近 10 天**
- `DURATION` 越大删除越粗、文件越少；越小删除越细、文件越多

⚠️ **补全：同一族参数还有两个不可后改的**（实测）：
- `ALTER DATABASE … KEEP 20` → 被拒：**`9753 Invalid duration value, should be keep2 >= keep1 >= keep0 >= 3 * duration`** ⇒ **确认 `KEEP ≥ 3 × DURATION` 是硬约束**；错误信息里的 `keep2/keep1/keep0` 是**多级存储的三个 KEEP 槽位**（社区版只用一个，另两个随它一起变）
- `ALTER DATABASE … VGROUPS 3` → 同样被拒 ⇒ **`VGROUPS` 不可后改**
- 对照：`ALTER DATABASE … BUFFER 32` → ✅ **可改**

⚠️ 【AI 判断】"111 个文件"这个理由**本身不构成压力**——TDengine 的文件按 vgroup 分，本机建库默认 `vgroups=2`，实际文件数是 **111 × vgroups**。但**理由的方向是对的**：`DURATION` 越大，管理越简单。

### 轴 3 · 降采样用流处理

✅ **实测可用**，本轮再次端到端验证（一级流 + **二级链式流**都产出，见 §7）。

⚠️ **补全四处（前两处是本轮实测新发现）**：

1. ⚠️ **输出表是"懒创建"的**：流建好后，**在源表发生第一次新写入之前，输出表根本不存在**——`SELECT` 报 `Table does not exist`（实测）。
   - 对应参数：**`NODELAY_CREATE_SUBTABLE`**（建流时即创建输出表）
   - **⇒ 运维含义**：**"建流成功"不等于"降采样在工作"**。**验收判据必须是"输出表存在且有数据"**，不能是"`CREATE STREAM` 返回成功"。
2. ⚠️ **一条流 ≠ 一台设备一张输出表**：流支持 `PARTITION BY tbname`（按子表）与 `ROLLUP BY`（按标签层级）分组，**一条流就能按设备分组、产出多张输出子表**。⇒ **万级设备不需要万条流**——这一条决定了轴 3 的方案在规模上是否成立。
3. ⚠️ **建流时必须声明输入策略**：`WATERMARK`（容忍多久的乱序）/ `EXPIRED_TIME` / `IGNORE_DISORDER`。**补传场景必然触发乱序**，这三个现在不写，将来就是数据不准。
4. ⚠️ **流会补算历史**：本轮实测——流创建后源表若不再写入，它**不动**；**一旦有新写入，它把该表的历史数据一并算出**（121 行全部产出）。好处是不用手工回填；代价是**建流那一刻会有一波重算负载**。

### 轴 4 · 粒度三级；聚合函数待 P2

⚠️ **这一轴有一件事必须现在定，不能整条推到 P2**。

⭐ **"聚合函数待定"会决定降采样表的列集合**。按概念卡 §5.1 的分法：
- 选了 `AVG` ⇒ **必须同时存 `SUM` 和 `COUNT`**，否则上层粒度算不对
- 想要**中位数 / 百分位** ⇒ **不可再聚合**，**必须回到原始数据**

⇒ **本轴与轴 1 直接耦合**：**原始数据只在线 3 年**。若 P2 定聚合函数时发现某指标需"从原始重算"，而彼时数据仍在 3 年内，则无碍；**若已超过，就只能从归档恢复（轴 9）**。

⭐⭐ **可以现在就定、且与具体指标无关的一条规则**：
> **第一级（分钟）降采样表不要只存 `avg`，要存可再聚合的中间量**（`SUM` / `COUNT` / `MIN` / `MAX`）。

它把"函数待定"的风险大幅降低——上层任意粒度的 `avg` 都能从 `sum/count` 重算，粒度和函数都可以后选。
⚠️ **本轮实测验证了这个坑真实存在**：见 §7 的 `avg of avg` 实测，偏差达 **14%**。

⚠️ **补全：三级之间是"链式"还是"各自从原始算"？**（本轮实测：**链式可行**——在输出表上再建流成功）
- **链式**（分钟→小时→天）：省资源，但受"可再聚合性"约束（第一级存什么决定第二级能算什么）
- **各自从原始算**：三条流都读原始表，灵活但每条都扫全量
- 【AI 判断】按"存中间量"的规则，**链式可行且更省**；代价是**延迟逐级累积**（每级都有部署 + 触发周期）

⚠️ **补全：窗口对齐必须显式设时区**（本轮实测，见 §10 Q2）：
- 实测容器 `timezone = Etc/UTC`，`INTERVAL(1d)` 的窗口起点落在 **UTC 00:00**，`INTERVAL(1h)` 落在整点
- ⇒ **窗口按服务器时区对齐**。**中国工厂必须把 `timezone` 设为 `Asia/Shanghai`**，否则"日"会从**北京时间 8 点**切到次日 8 点——"日产量"直接错位
- ✅ **决策人已定：时区全部采用上海时区**（§9）
- ⚠️ 实测补充：**流级 `CONFIG(timezone=…)` 在 3.4.2.8 上不可用**（`9728` 语法错误，该选项属 v3.4.3 文档线）⇒ **时区只能设在服务器 / 集群级**（`ALTER ALL DNODES 'timezone' 'Asia/Shanghai'`，实测生效），并需同步进 `taos.cfg` 以免重启回退

### 轴 5 · 降采样结果单独建库，留 10 年

✅ **判断正确，而且正好绕开了那个结构约束**（超表级 `KEEP` 只能比库级短 ⇒ "原始短留 + 聚合长留"只能另建库）。
✅ **本轮实测确认**：`CREATE DATABASE … KEEP 3650 DURATION 10` 成功；`3650` 在范围内且 `3650 ≥ 3 × 10` ✓

⚠️ **补全：另建库的代价是"跨库查询"**（本轮实测）：
- ✅ **跨库 `UNION ALL` 可用**
- ✅ **跨库 JOIN 可用**（`FROM db_a.t1 a, db_b.t1 b WHERE a.ts = b.ts` 实测通过）
- ⇒ **"查最近 1 小时原始 + 查 1 年日聚合"可以在一条 SQL 里完成**，不需要应用层拼两次
- 另：`taosdump` 文档证实**虚拟表可跨库引用物理表**（*"a virtual table in db2 referencing a physical table in db1"*）——若两边 schema 不同，用虚拟表统一更省事

⚠️ **补全：把 10 年的成本算出来**（让这个决定有依据）：
| 项 | 量 |
| --- | --- |
| 万级设备 × 每分钟 1 条 | 10,000 × 1,440 = **1,440 万行/天** |
| 一年 | ≈ **52.6 亿行** |
| 十年 | ≈ **526 亿行** |
| 行宽 32–40 字节 → 未压缩 | ≈ 1.7–2.1 TB |
| 按 1/10 压缩 | ≈ **170–210 GB** |

⚠️ 上表是**分钟级**；小时级约再除 60、天级再除 24。**⇒ 10 年降采样库是几百 GB 量级，可行**——这个决定有成本依据。

⚠️ **补全：要与轴 1 对齐一处设计意图**：**原始库 3 年、降采样库 10 年** ⇒ **3 年以上的数据"只能查聚合、不能查原始"是有意设计**，不是遗漏。这一句要写进部署说明。

⭐ **留存结构确认为"三级不同"**（决策人补充：分钟级只留 3 年，靠**超表级 `KEEP`** 处理；且分钟级也要备份）：

| 层 | 位置 | 留存 | 机制 |
| --- | --- | --- | --- |
| **原始** | 原始库 | **3 年** | 库级 `KEEP 1095` |
| **分钟级聚合** | **降采样库** | **3 年** | ⭐ **超表级 `KEEP 1095`**（库级是 3650，它只能更短 ✓） |
| **小时级 / 天级聚合** | 降采样库 | **10 年** | 继承库级 `KEEP 3650` |

⚠️ **三点注意**：
1. **超表级 `KEEP` 不立即生效**——必须先 `flush` 再 `compact`，数据才会按超表级 `KEEP` 被清掉（§4.1）
2. ⇒ **本条改写了轴 8 的结论**：原答"不用超表级 `KEEP`"，现在**要用**——只用在降采样库的分钟级超表上（详见轴 8）
3. ⚠️ **分钟级 3 年 ⇒ 3 年以上的分钟级数据只能从备份恢复**——所以**分钟级也必须纳入备份**（见轴 9）

### 轴 6 · 自动删除靠 `KEEP`，特殊场景手动

✅ 合理。

⚠️ **补全三条 `DELETE` 的边界**（已核实）：
1. **`WHERE` 只能过滤第一列（主时间戳）**——**不能按设备 / 测点删**
2. **不可逆**——官方建议先跑同样的 `SELECT` 确认
3. ⭐ **空间不立即释放**：删除只是**打标记**；社区版**没有 `COMPACT`**（企业版专属），空间要等 **`KEEP` 生效时**才回收
   - **⇒ 运维含义**：手动 `DELETE` 之后**磁盘不会立刻变小**——这很容易被误判成"删除没生效"

⚠️ **补全："特殊场景"需要具体化**。三类【AI 判断】：
- **设备退役**：⚠️ 因为 `DELETE` 只能按时间删，**做不到"按设备删"**；可行的是 `DROP TABLE <子表>`（整张子表删掉）
- **误入脏数据**：靠同 `ts` 覆盖修正，或按时间窗 `DELETE`
- **合规删除请求**：接轴 10

### 轴 7 · 不要 `SECURE_DELETE`

✅ 合理。内部自用、无"彻底删除"的合规要求。

⚠️ **一处澄清**：`SECURE_DELETE` 与轴 10 的审计**是两件事**，不冲突——审计记录"**谁删了什么**"，`SECURE_DELETE` 保证"**删了不可恢复**"。不因为它们都带"合规"味道就绑在一起。

⚠️ **一处提醒**：`SECURE_DELETE` 是**库级 / 表级 / 语句级**参数。若将来合规要求变了要开，**能否后补需要核实**——本卡已实测出"同族参数有的可 `ALTER` 有的不可"（轴 2），不能假定它能补。

### 轴 8 · 超表级 `KEEP`（**结论已修订为"要用"**）

⚠️ **本轴结论在决策人补充后发生变更**：原答"不用超表级 `KEEP`"，现改为 —— **要用，但只用在降采样库的分钟级超表上**（决策人：分钟级保留 3 年，"通过超表的 keep 去处理"）。

✅ **合法性**：超表级 `KEEP 1095` < 库级 `KEEP 3650` ✓——硬约束满足（§4.1）。

⚠️ **补全三条**：
1. **不立即生效**：超表级 `KEEP` 要先 `flush` 再 `compact` 才按它清数据（§4.1）⇒ **改这个值有生效延迟**，不能当即时开关
2. **它是"只能更短"的单向阀门**：要"某些超表留更久"，超表级做不到，**只能另建库**
3. ⚠️ **与轴 5 的分工**：现在**两种手段同时在用**——**"更长"靠另建库**（轴 5）、**"更短"靠超表级 `KEEP`**（本轴）。组合自洽，但**必须写进部署说明**，否则将来没人知道分钟级为什么是 3 年

### 轴 9 · 每月 1 次增量备份

⭐ **这是本项最有价值的一条**——它把"删除"和"可恢复"配成了对，正好补上轴 1 的边界。

⚠️ **但有一处术语必须纠正**：**`taosdump` 没有"增量备份"能力**。
- 官方能力：**全量**（默认全部用户库，或 `-D` 选库 / 指定表）
- `-C / --checkpoint` 是**断点续跑**（同一次备份被打断后接着跑），**不是增量备份**
- **`-S` / `-E` 支持时间范围** ⇒ **这才是你要的形态**

⇒ **你要的"增量"，实际形态是"按时间切片的滚动归档"**：每月导一次 `-S <上月起点> -E <上月终点>`。
- 与"差异备份"的区别：**恢复时要按序恢复所有月份的文件**，不能只恢复某一个月
- 但对你"长期归档、需要时按时间段找回"的目的，**这个形态是对的**

⚠️ **补全：备份必须包含流的定义**——否则恢复后降采样就没了
- `taosdump -M / --content=ext-meta` 会备份 **virtual tables / streams / topics 的 DDL**（产出 `stream.sql` / `topic.sql` / `vtb.sql`）
- ⚠️ `-M` **自 v3.4.2.5 起才支持**；**默认 `basic` 不含流定义**
- ⇒ **只做默认备份，恢复后 `CREATE STREAM` 那段就丢了**

⚠️ **补全：恢复不能覆盖生产**
- 恢复到**独立库 / 独立实例**，查完即弃（`-W / --rename` 支持改库名恢复）
- 理由：恢复是**覆盖式**的（企业版的 `taosd --restore` 官方明说"existing data on the dnode is cleared"）

⚠️ **补全：备份必须发生在 `KEEP` 删除之前——这条要写成可校验的判据**
> **备份周期必须显著小于 `KEEP`。**

本卡组合：**1 个月 ≪ 3 年** ⇒ 每个数据点有约 **36 次**备份机会 ⇒ **安全**。✅

⚠️ **补全：备份要能恢复才算数**
- "做了备份"与"能从备份恢复"是两件事 ⇒ **必须定期做恢复演练**（正是 backlog 里那条"备份与恢复演练"）
- 演练有个**前置**：得先定义"**恢复到哪、恢复完放哪**"

⚠️ **补全：备份文件是明文的**
- 用户说生产上放"独立磁盘 / 专用存储服务器" ✓ 方向对
- 但 `taosdump` 的 `binary` / `parquet` 格式**未提供加密**（企业版的 `CREATE FULL BACKUP` 才有 `WITH PASSWORD`）⇒ **导出的原始数据是明文**，**访问控制要做在存储这一层**

⚠️ **补全：要备的是两个库，不是一个**
- 决策人说的是"将原始数据备份导出"。但**降采样库也要备**——它的数据**一旦丢失无法从原始重算**（原始 3 年后已删）。**两个库都是不可再生的。**
- 好消息：降采样库数据量远小于原始，成本低

⚠️ **补全：一个连接细节**——`taosdump -Z / --driver` 支持 **WebSocket（6041）**，与本项目 ADR 定的连接方式一致 ⇒ **备份工具不需要额外装原生客户端驱动** ✓

### 轴 10 · 开启数据库级审计

⛔ **这一条在社区版落不了地。**

**官方原文**（`security-guide/audit-and-compliance/`）：
> Use the latest Enterprise edition when possible. **The Community edition does not provide audit capabilities.**

而且审计库带一整套**企业版专属约束**：`VGROUPS` 必须 **1**、`KEEP` **默认且必须 ≥ 1825d（5 年）**、`WAL_LEVEL` 必须 **2**、**`ENCRYPT_ALGORITHM` 不能是 `none`**（须 SM4-CBC 一类）、`PRECISION` 必须 **ns**。

**本机实测复核**：
- `CREATE DATABASE … IS_AUDIT 1` → **`24835 Audit database must be encrypted`**
- 加 `ENCRYPT_ALGORITHM 'SM4-CBC'` → **`1056 invalid encryption key`**
- ⇒ **审计库建不起来**
- ⚠️ 而 `SHOW VARIABLES LIKE 'audit%'` 在社区版**返回 7 行**（`audit=1`、`auditLevel=3`、`auditInterval=5000` …）——**参数存在 ≠ 功能可用**。这正是"参数可见性"最容易造成的误判。

⇒ **决策人的诉求里其实是两件事，要分开处置**：

| 诉求 | 社区版能否满足 | 处置 |
| --- | --- | --- |
| **(a) 人为修改 / 删除的留痕** | ❌ 数据库层没有 | ① ⭐ **权限收敛**——生产上不给应用 `DROP` / `DELETE` / `ALTER` 权限；② **应用层审计**——所有写经应用，应用记日志；③ **连接收敛**——限制谁能直连数据库 |
| **(b) `KEEP` 自动删除的留痕** | ❌ 数据库层没有 | ⚠️ **无技术替代**——这是数据库内部行为，应用层看不见。但**月度归档（轴 9）本身提供了跨期的"数据存在性证据"**：每月一份快照，可反推"某个时间段的数据曾经存在" |

⭐ **一条定位纠正**：**审计是"事后发现"，权限是"事前阻止"**。在社区版没有审计的前提下，**重心应放到权限收敛**；而且——**权限收敛本身是审计的前提**：若谁都能直连数据库，任何应用层审计都可被绕过。

⚠️ **两处触发点要登记**：
1. **升级到企业版**——触发点＝合规要求真正落到"必须有数据库级审计"
2. ⚠️ **"有没有合规要求"这个前提目前是空的**（§4.7 已记）——**轴 10 的诉求建立在一个尚未确认的前提上**

⭐ **一条旁证**：企业版审计库的 `KEEP` **默认且必须 ≥ 1825 天（5 年）**——恰好与决策人提到的"环保行业补足前 5 年"对上。说明"5 年"在合规语境里是有依据的取值。⚠️ 但这是旁证，**不能反推"我们的留存也该是 5 年"**。

## 10. 补充探索：四个问题的答复

### Q1 · 原始数据已存在时，能否手动触发流处理去算以前的聚合？

**结论：能，而且比"手动触发"更省事——但三条路里只有一条在我们的配置下可用。**

| 路径 | 是否可用 | 说明 |
| --- | --- | --- |
| **① 建流即回填** | ✅ **可用（本卡采用）** | `FROM <源表>` 写法下，**每次触发都重扫源表** ⇒ 建流后一次写入即把全部历史算出来（M24 实测：121 行） |
| **② `RECALCULATE STREAM [db.]name FROM start_time [TO end_time]`** | ❌ **不可用** | ⚠️ 官方原文：**"Manual recalculation is not supported for scheduled triggers (PERIOD)"**。而 3.4.2.8 上我们**只能用 `PERIOD`**（`INTERVAL` 作触发类型被拒，§4.4） |
| **③ 删流重建** | ✅ 可用 | 官方对"从某时刻起重算且无终点"场景的推荐做法：*"drop the stream, recreate it"* |

⚠️ **连带一条**：`FILL_HISTORY` 与 `FILL_HISTORY_FIRST` 两个选项**同样不支持 `PERIOD`**（M30）——官方原文 *"Not supported in PERIOD (scheduled trigger) mode"*，且 *"If neither FILL_HISTORY nor FILL_HISTORY_FIRST is specified, historical computation is disabled"*。**但这两句针对的是 `%%trows` 写法**——`FROM <源表>` 不依赖它们。

⭐ **对我们的实际含义**：
1. **不需要"手动触发"**——建好流 + 任意一次写入，历史聚合就全量算出来了
2. **要重算历史，最可靠的是"删流重建"**；⚠️ 重建前**先清输出表**，否则新旧结果混在一起（官方提醒：重算可能导致新旧窗口不对齐，需手工删旧结果）

### Q2 · 统计窗口能否自定义？（8:00→次日 8:00 / 剔除周末 / 按班次）

**结论：前两项能，第三项只能做到"固定班次"，完整班次统计要落在应用层。**

#### (a) 8:00 → 次日 8:00 ✅ 能

⭐ **实测（M22）**：服务器时区设为 `Asia/Shanghai` 后，
- `INTERVAL(1d, 8h)` ⇒ 窗口起点 **北京时间 08:00**
- `INTERVAL(1d)` ⇒ 窗口起点 **北京时间 00:00**（自然日按本地 0 点）

语法即查询语法里的 `INTERVAL(interval_val [, interval_offset])`——**第二个参数就是起点位移**（M19 另测 `INTERVAL(1h, 30m)` 起于 11:30 / 12:30 / 13:30）。

⚠️ 与决策人第 6 条配套：**必须先把 `timezone` 设为 `Asia/Shanghai`**，否则 8:00 是 UTC 8:00。

#### (b) 剔除周末 ⚠️ 能，但要注意语义

- ✅ 时间函数可用：**`WEEKDAY(ts)`**（0 = 周一）/ `DAYOFWEEK(ts)` / `TO_CHAR(ts, 'yyyy-mm-dd hh24:mi:ss')`（M20）
- ✅ 窗口查询里可以有 `WHERE`（M21 实测通过）
- ⇒ 写法：`SELECT _wstart, … FROM … WHERE WEEKDAY(ts) < 5 INTERVAL(1d, 8h)`

⚠️ **语义提醒**：`WHERE` 在**聚合之前**过滤 ⇒ **周末那天会"没有窗口"**，而不是"值为 0 或 `NULL`"。
- 对"工作日日均值"这是对的
- 但若业务要"这天没生产"的**显式记录**，得另外标注（这属于应用层语义，不是窗口能表达的）

#### (c) 按班次统计 ⚠️ 只能做"固定班次"

- ✅ **固定班次**（如三班倒 8:00 / 16:00 / 24:00）：`INTERVAL(8h, offset)` 可以做到
- ❌ **做不到**：换班时间变动、节假日、非固定班次、跨天班次与非生产时段混排

⭐ **一条定位判断**：**"按班次统计"本质是"按业务日历分组"，不是"按固定时间窗分组"**——数据库的窗口函数只处理后者。
【AI 判断】**可行方案**：**班次边界做成一张维度表（放 PG）**，报表在应用层按班次边界聚合；若源数据里带"开工 / 停工"状态列，也可用 **`STATE_WINDOW`** 按状态切段。

### Q3 · 归档文件的恢复粒度，以及能否自研导出

#### (a) `taosdump` 按时间范围备份后，能否只还原中间一部分？

⛔ **不能按时间挑。** 官方参数表明确：`-S / --start-time` 与 `-E / --end-time` 均 **"Effective only for backup"**（只对备份有效）。

✅ 可以按 **库**（`-D`）与 **表**（位置参数 `dbname [tbname ...]`）挑。

⇒ **"按时间切片归档"给的是"按月份选择"的能力，没给"按设备 / 按更细时间选择"的能力。**

#### (b) 那"只导入某设备某段时间"怎么做？

**两步**：
1. 把整库归档**先恢复到旁路实例 / 旁路库**（`taosdump -i … -W "db->db_tmp"` 支持改名恢复）
2. 从旁路库按条件 `SELECT` 出来，再 `INSERT` 进主库

#### (c) 自己做导出策略可行吗？✅ 可行，而且这正是 (b) 的正解

现成能力有三条：

| 途径 | 说明 |
| --- | --- |
| `taosdump -F parquet` | 官方工具，支持 `binary`（默认）/ `parquet` 两种格式 |
| **`SELECT … >> export_file`** | ⭐ **TDengine 查询语法自带导出子句**（`SELECT` 语法中即有 `[>> export_file]`） |
| REST / WebSocket 拉数据 | 我们本就用 `@tdengine/websocket`，可自行落盘 |

⚠️ **权衡**：自研要自己维护"备份窗口、断点续跑、校验、重试、并发"——而这些官方工具的 `-C`（断点续跑）、`-T`（默认 8 线程）、`-k`/`-z`（重试与间隔）都是现成的。

【AI 判断】**建议的分工**：**导出用官方工具**（成熟、可靠、格式自描述），**按需导入自己写**——该需求是"低频、有针对性"的，写一段"从旁路库按条件捞数 → 写主库"的脚本成本可控，且没有替代品（官方恢复不支持时间范围）。

### Q4 · 人为对数据干预（剔除异常值 / 重算 / 补全），业界是否允许？

**结论：业界允许，但通行规则是"允许修正、不允许覆盖原值"——修正要留痕、原值要能追溯。**

#### (a) 行业参照（三处口径一致）

| 领域 | 做法 |
| --- | --- |
| **环保 / HJ212 体系** | **数据标记（QC flag）+ 修约**是标准操作——平台侧有专门字段区分有效值 / 无效值 / 人工修约 |
| **SCADA / Historian**（PI、Wonderware） | 都提供 **data correction / backfill** 功能，且通常保留修改记录 |
| **财务 / 审计** | 更严：**不可覆盖，只能红冲**（反向分录） |

⭐ **共通点不是"能不能改"，而是"改完能不能说清"。**

#### (b) ⛔ 但 TDengine 上有一个具体问题

- **没有 `UPDATE`**；同 `ts` 写入 = **静默覆盖**（第 1 项已定）
- ⇒ **"剔除异常值"若靠覆盖，原值永久消失**——与"可追溯"直接冲突
- ⚠️ 叠加**社区版没有审计**（轴 10）⇒ **改了也无痕**

#### (c) ⭐ 处置：把"改值"改成"加列"

| 操作 | ❌ 不要这样做 | ✅ 应该这样做 |
| --- | --- | --- |
| **剔除异常值** | 覆盖成 `NULL`（原值消失） | ⭐ 加 **`qc_flag`** 列做标记，**值保留** |
| **重算数据** | 覆盖原值 | ⭐ 加 **`corrected_value`** 列，**原值列不动** |
| **补全数据** | —— | 直接插入（本就是新增） |

⭐ **这条路现在就能走通**：第 1 项已实测 **`ADD COLUMN` 是元数据操作**（与数据量无关）——**"加一个值"可以后补**，正是那条收敛判据的兑现。且它**与 §4.7 的"不可修改"口径完全一致**：**只追加、不覆盖**。

#### (d) ⚠️ 三条连带代价

1. **降采样会跟着变**：原始值被修正后，降采样结果**被重算**（M27 实测）——**但只在 `FROM <源表>` 写法下**；`%%trows` 写法会把该窗口写坏（M25）
2. ⚠️ **修正本身没有审计**（社区版）⇒ 只能靠**应用层修正日志** + **权限收敛**（轴 10）
3. ⚠️ **"补全数据"要注意时间戳精度**：M28 实测 `13:10:00.744` 与 `13:10:00.000` 是**两条不同的主键**，同一分钟内并存——**补全时精度不一致会把同一时刻拆成多行**

## 11. 定稿：结论四件

> 十轴作答、6 项开口项确认、4 项探索答复。按决策卡模板收口四件：**选定 / 代价陈述 / 退出成本 / 触发点**。

**① 选定**

```text
原始库
  KEEP         1095 天（3 年）
  DURATION     10 天（⚠️ 不可后改 —— 全案唯一"一次定对"的参数，见 §7 M2）
  PRECISION    ms

降采样库（独立建库）
  库级 KEEP     3650 天（10 年）；DURATION 10 天
  分钟级超表     超表级 KEEP 1095 天 —— 全案唯一的超表级 KEEP
  小时 / 天级    继承库级 3650 天

时区           Asia/Shanghai（服务器 / 集群级，写进 taos.cfg）
               ⚠️ 流级 CONFIG(timezone=…) 在 3.4.2.8 不可用（§7.1 M21）

降采样
  路径         流计算 CREATE STREAM
  计算子句       FROM <源表>   ⚠️ 不是 %%trows（§7.1 M25：%%trows 会在补传时静默写坏已算窗口）
  触发          PERIOD（3.4.2.8 上 INTERVAL 作触发类型被拒）
  分组          PARTITION BY tbname
                 · 一条流覆盖全部设备——万级设备不需要万条流
                 · 且只有带分组才产出超表 —— 分钟级超表级 KEEP 的前提
  粒度          分钟 → 小时 → 天（三级链式；在上一级输出表上再建流）
  聚合列        第一级存 SUM / COUNT（并 MIN / MAX）—— 不只存 AVG（§7 M12 实测偏差 14%）
  窗口          INTERVAL(<n>, <offset>)；offset 用于对齐业务日（如 1d, 8h ⇒ 早 8 点）

删除           靠 KEEP 自动过期；特殊场景手动 DELETE（只能按时间过滤、不可逆、空间不立即释放）
SECURE_DELETE  不用
备份           每月 1 次；taosdump -S/-E 按时间范围滚动归档
                 · 范围：原始库 + 降采样库（分钟级也在内，因为它 3 年就过期）
                 · 内容：-M ext-meta（含 stream / topic / vtable 的 DDL）——否则恢复后流会丢
                 · 落点：独立磁盘 / 专用存储服务器（导出文件是明文，访问控制做在存储层）
                 · 恢复：恢复到旁路库（-W 改名）→ 按条件 SELECT → INSERT 进主库

审计           社区版不可用（§6 轴 10）⇒ 权限收敛 + 应用层审计
数据修正        只追加、不覆盖：加 qc_flag / corrected_value 列，原值列不动
```

**② 代价陈述（这套生命周期会怎么坏）**

| # | 失败模式 | 什么时候会咬人 |
| --- | --- | --- |
| 1 | ⭐ **`%%trows` 写法会把降采样写坏**——补传数据落在已算过的窗口上，该窗口被重算成"只有这一条"，**原值静默消失、不报错** | 实现时照抄官方示例；**且验收时看不出来**（结果仍是"合理"的数字） |
| 2 | **"建流成功"≠"降采样在工作"**——输出表懒创建，源表无新写入前它不存在 | 按"`CREATE STREAM` 返回成功"验收，实际降采样是空的 |
| 3 | ⛔ **`DURATION` 不可后改** | 将来想换更细 / 更粗的过期删除粒度 ⇒ **只能建新库迁移** |
| 4 | **超表级 `KEEP` 不立即生效**（要先 flush 再 compact） | 分钟级数据不会在到期日立刻清 ⇒ **实际留存略超 3 年**，且不可预期 |
| 5 | **备份是"3 年以上"的唯一天花板**——`KEEP` 已删的数据只能靠归档找回 | ⚠️ **备份中断超过 3 年，那段数据永久丢失**；且"备份了"不等于"能恢复" |
| 6 | **恢复的粒度很粗**——`taosdump` 的 `-S`/`-E` 只对备份有效，恢复不能按时间挑 | 要找回"某设备某段时间"，得先恢复**一整个月的整库归档**到旁路库 |
| 7 | **修正无痕**——社区版没有审计 | 谁在什么时候改了哪条，数据库层查不到；只能靠应用层日志（而它挡不住直连库的修改） |
| 8 | **补传窗口 = 3 年**——比 `KEEP` 更老的数据写不进去（`Timestamp data out of range`） | 导入"补足前 5 年"这类历史时 |
| 9 | ⭐ **降采样只能回答"事先设计好的问题"**——聚合函数留到 P2 才定 | 若 P2 发现某指标需要中位数 / 百分位（**不可再聚合**），而原始数据 3 年后已删 ⇒ 只能从归档恢复 |
| 10 | **两个库的留存不同步**（原始 3 年 / 聚合 10 年） | 3 年后跨库联合查询会**突然少掉原始那一半**；这是有意设计，但容易被当成故障 |

**③ 退出成本（想换掉要付什么）**

| 换什么 | 代价 |
| --- | --- |
| 降采样路径（流 → 应用层自己算） | **中**——输出表结构可复用，但流定义与窗口逻辑要重写；已算历史要重跑 |
| 三级降采样（→ 只做一级） | **低**——删掉上层流即可；已产出的聚合表还在 |
| 第一级聚合列（补 sum/count） | **零**（加列是元数据操作）；⚠️ 但**已算过的历史要重算**（删流重建） |
| 计算子句（`%%trows` ↔ `FROM <源表>`） | **低**——重建流；⚠️ 但要**先清输出表**，否则新旧结果混在一起 |
| `KEEP`（3 年 → 别的值） | **低**——`ALTER DATABASE … KEEP` 实测可改 |
| ⛔ `DURATION` | **做不到**——实测不可 `ALTER`，只能建新库 + 迁移 |
| 超表级 `KEEP` | **低**——可改；⚠️ **生效有延迟**（flush + compact） |
| 备份方案（`taosdump` → 自研） | **中**——导出可平移，但**恢复工具要自己写**（官方恢复不支持时间范围） |
| 审计（无 → 有） | **高**——需企业版；且**历史操作无法补录** |
| "同库内做分层留存"（某些超表留更久） | **做不到**——超表级 `KEEP` 只能比库级短，更长只能另建库 |

**④ 触发点**

| 触发 | 回头改什么 |
| --- | --- |
| ⭐ **P2 定聚合函数时**（上真实设备） | 补第一级降采样表的聚合列。⚠️ **必须排在原始数据 3 年到期之前**——超过就只剩归档可救 |
| ⭐ **备份建成之后立即** | **做一次恢复演练**——"能备份"和"能恢复"是两件事；且这是本项**唯一"越晚越无法补救"**的验证 |
| **要导入超过 3 年的历史数据** | 临时调大 `KEEP`（可 `ALTER`），或建独立归档库 |
| **合规要求落到"必须有数据库级审计"** | 升级企业版；登记进 `docs/governance/backlog.md` |
| **班次 / 业务日历统计成为需求** | 在 PG 建班次维度表、应用层聚合；可能反过来影响降采样粒度 |
| **存储成本成为问题** | 重估分钟级留存（3 年）与降采样库 `KEEP`（10 年） |
| **要求更细的过期删除粒度** | ⛔ `DURATION` 不可改 ⇒ 建新库迁移 |
| **增量 6（可观测性与压测）** | 实测真实压缩比、`FROM <源表>` 的重扫代价、流的数量上限 |
