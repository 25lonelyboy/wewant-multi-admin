## 1. 结论摘要（**已定稿**）

| # | 轴 | 结论 |
| --- | --- | --- |
| 1 | 一张超表覆盖全部，还是按设备类型分 | **按设备类型分**；**"类型"＝设备的功能类别**（贴片机 / 印刷机），**宁可粗分**（细分难合、粗分可加列） |
| 2 | 采集点划在哪里 | **按"一个设备可有多个采集点"建，一对多**；**契约新增 `pointId` 且允许缺省**（缺省＝单采集点设备）；**`pointId` 进载荷、不进主题** |
| 3 | 标签放哪几个维度 | **设备编号、设备类型、设备品牌、位置**（采集点编号改由子表名承载）。**位置是冗余**——接受"历史按当前值解释"的 Type 1 语义，见 §4.4 |
| 4 | 多列还是单列 | **多列**。判据＝**指标集合不频繁变化**，且 TDengine 对变化（`ADD COLUMN`）的代价实测很小 |
| 5 | 幂等键 | **`(子表, ts)`** ——时间戳为第一列，设备与采集点由子表标识承载 |
| 6 | 测点列的数据类型 | **按分档规则定**（§6.4），**P1 的清单＝模拟器三个测点，全为 `FLOAT`** |
| 7 | 虚拟表 | **P1 不做**，后续按业务分析与报表需要再整合 |

**唯一标识**：**`(deviceId, pointKey)` 复合**——**两段都由平台生成**（`deviceId` 平台签发、`pointKey` 按 §8.3 只增不复用）；**子表名 = `{deviceId}_{pointKey}`**。设备报的是 `localPointId`，经**档案**映射到 `pointKey`（见 **§8**）。⭐ 幂等靠 `tbname`，所以这两段**一旦有数据就冻结**。

## 2. 逐轴：决策人的答案

### 轴 1：按设备类型分

> 【决策人】应该是按照不同类型的设备去分的。因为在 IoT 场景下，不同类型的设备：① 采集的指标不一样；② 在生产现场所处的位置不一样；③ 关注的东西不一样。所以应该是不同设备一张超表。这后续可能需要和物模型结合，在平台端去定义不同类型的设备各自有哪些属性。

### 轴 2：采集点按一对多建

> 【决策人】以前在环境监测，是一个站点对应一个采集点。但是在物联网这一块，确实有可能一个设备有多个采集点。这里应该尽量去兼容这种情况，所以还是得按照"一个设备有多个不同的采集点"去划分。如果它只有一个采集点，那和设备的关系就是一对一；如果有多个，就是一对多。因此需要按照一对多的关系去建模，以便以后的兼容。

### 轴 3：标签四个维度

> 【决策人】最起码要加上设备编号、采集点编号、设备类型、设备品牌。因为我对物联网这块实际业务并不是很熟悉，所以目前只能想到这些了。

### 轴 4：多列

> 【决策人】在了解了 TDengine 的这些特性之后，应该是按照多列去建模会更好一点。① 兼容分次上报：它的特性能够兼容分次上报这种情况；② 扩展成本低：宽表的扩展成本比较低，后续可以和物模型结合，若有新增的指标，可以及时做表结构的扩展；③ 利于数据分析：对于后续的数据应用分析，宽表会更加友好。

### 轴 5：幂等键

> 【决策人】目前我看来，主键最起码要加上设备编号和采集点编号。在这种宽表的情况下，最起码要加上这两个。

### 轴 6：浮点用 `FLOAT`、整数用 `INT`

> 【决策人】如果是浮点数，应该用 `float`，四字节就够了，因为从物理世界采集的数据，精度其实并不会特别大。如果是整数类型，用 `int` 就够了。

### 轴 7：虚拟表后续再做

> 【决策人】虚拟表这一块，后续根据实际的业务分析需要、报表再去做整合就行。

## 3. AI 补全与纠偏

### 轴 1 — 结论成立，但**两条理由不成立**，且漏了"类型怎么切"

**【AI 纠偏】理由②「位置不一样」与理由③「关注的东西不一样」不构成"分超表"的判据。**

- **位置**是**静态属性** → 它的正确归宿是**标签**。用"同一张超表 + 位置标签"表达即可，恰恰**不需要**分超表。
- **"关注什么"** 是**应用层 / 报表**的事，与存储层的类型划分无关。

**唯一站得住的判据只有一条：指标集合（列集合）不同。** 因为超表内所有子表共享同一套列（§1.3），指标不同就不能共用一张超表。这个判据与 §1.7 官方"推荐多列模型"的立场一致——多列要求列集合先固定。

**【AI 补全】这条选择的债要一并记下**：按类型分多张超表之后，"跨类型的统一列表"就必须靠 `UNION ALL`（**每一次查询手工对齐列**）或虚拟表（**层级建时定型**）。这笔债会在轴 7 回来（见 §4 耦合）。

**【AI 补全】"类型"按什么切——决策人的方向是"按设备的功能类别"**：

> 【决策人】我预想中的设备类型应该是像**贴片机和印刷机**这种的分法。因为这两种不同的设备，它做的东西不一样，关注的内容也不一样，采集的指标肯定也不一样。但是这个也不好说，它是按品牌还是什么呀？

分超表的**唯一硬约束**是"列集合必须一致"（§1.3）。所以：

| 口径 | 是不是判据 |
| --- | --- |
| **指标集合** | ✅ **唯一直接判据** |
| **设备功能类别**（贴片机 / 印刷机） | ✅ **代理判据**——够用的原因：功能决定采集什么，所以指标集合通常由它决定 |
| **品牌** | ❌ **已经是标签**（轴 3）——**能按标签表达的差异，不该升格成分表的依据** |
| **型号** | ❌ 同上；型号差异用**并集列 + `NULL`** 承载 |

**代理判据什么时候会失准**（三条，需要留意）：

| 情形 | 后果 |
| --- | --- |
| 同类不同品牌，某品牌多/少几项指标 | 并集里出现常年 `NULL` 的列 |
| 同类不同型号，高端型号指标更多 | 同上 |
| 不同功能，但指标集合恰好相同（如通用的"温度 + 振动"） | 可以共用一张超表，按功能分反而多一张 |

**【AI 判断】取向建议：宁可粗分，不要细分。** 因为两侧代价**不对称**：

| 分得太粗 | 分得太细 |
| --- | --- |
| 稀疏列多——但**加列便宜**（实测元数据操作）、缺列填 `NULL`，存储层有专门优化（§1.7） | 跨表查询要 `UNION ALL`（**每次手工对齐列**） |
| **可逆**：随时 `ADD COLUMN` 补 | **不可逆**：想合并要**迁历史数据**（子表不能单独改结构） |

**环保经历是现成样本**：大气站 vs 水站——**按"监测介质"分**，不是按品牌；同一介质内 108 项不齐，当年就是**宽表并集 + 每行不同列有值**。所以"按功能类别分 + 类别内稀疏"这条路是被实践过的，而且**它的代价（冗余列）在 TDengine 里比在当年的关系库里低**（§1.7）。

**降级触发点**：当某个功能类别内，品牌/型号间的指标集合差异**大到并集里大部分列常年为 `NULL`** 时，再考虑在该类别内按品牌拆表。

**【AI 补全】与物模型的边界**：TDengine 的**超表 = 存储层的"设备类型"**，增量 3 的**物模型 = 应用层的"设备类型"**，两者**不自动同步**（§1.1）。所以"与物模型结合"需要明确三件事：**谁定义、谁同步、不同步会怎样**。

### 轴 2 — 结论与官方定义一致，但**当前契约下落不了地**

**【AI 纠偏】方向正确**：官方用的词就是 **DCP（data collection point）**，一台设备可有多个 DCP，每个 DCP 一张表。落到语句上就是：**子表 = 采集点，设备标识进标签**。这不是"兼容未来"，而是**本来就该这么建**。

**【AI 纠偏】⚠️ 一处硬冲突**：我们的载荷（增量 1 已冻结进 `packages/contracts`）是

```json
{ "deviceId": "sim-001", "ts": 1759747200000, "metrics": [{ "key": "temperature", "value": 36.5, "unit": "℃" }] }
```

**里面没有"采集点"这个身份。** 因此"按一对多建模"在**当前契约下无法落地**——子表名无从生成。这是**落在设备侧**的改动（决策轴第 1 条），必须在契约层解决。

**【决策人】选定方向 A：契约新增 `pointId`。** 三个方向与取舍：

| 方向 | 做法 | 结论 |
| --- | --- | --- |
| **A** | 契约新增 `pointId` 字段 | ✅ **选定**。落在设备侧，但**现在改模拟器零成本**，现场硬件要到部署时才需固件支持 |
| B | 约定 `metrics[].key` 带采集点前缀（如 `p1.temperature`），消费者侧解析 | ❌ 否决。把结构语义压进字符串，弱类型；解析规则无处约束，两端容易各写各的 |
| C | P1 先按"一设备一采集点"（一对一）跑通，一对多留到增量 3 | ❌ 否决。**子表不能单独改结构**，粒度定错要重建；而且"兼容一对多"本就是选它的理由 |

**⚠️ 方向 A 派生出一个未答的小问题：`pointId` 进载荷，还是进主题？**

| 做法 | 影响 |
| --- | --- |
| **进载荷** | 一条报文可带多个采集点的数据；**主题结构不动**（增量 1 已冻结，不动最省） |
| **进主题**（`wewant/devices/{deviceId}/{pointId}/telemetry`） | 表达"采集点独立上报"更自然，但**主题层级改变**——落在设备侧、且增量 1 的契约与子表命名全要跟着改 |

**【AI 补全】行业调研（决策人要求）——工业 MQTT 的事实标准怎么做的**：

**Sparkplug B**（Eclipse 规范 v3.0.0，2022-11-16；**已由 ISO/IEC 采纳，编号 ISO/IEC 20237**——Eclipse 官方公告原文："Going forward, the Sparkplug® specification will also be known as ISO/IEC 20237"）规定的主题命名空间是：

```text
namespace/group_id/message_type/edge_node_id/[device_id]
```

| 发现 | 原文 / 说明 |
| --- | --- |
| **采集点（device）在主题里** | `device_id` 是主题的一层 |
| **但它是可选层级** | 原文字面用方括号 `[device_id]`：*"the device_id is an optional element within the topic namespace as some messages will be either originating or destined to the edge_node_id and the device_id would not be required."* |
| **"有没有这一层"由消息类型表达** | 配对的消息类型：节点用 `NBIRTH/NDEATH/NDATA/NCMD`，设备用 `DBIRTH/DDEATH/DDATA/DCMD` |
| **测点在载荷里** | DDATA 原文：*"If multiple metrics on the device change, they can all be included in a single DDATA message"*，且载荷是**有序 metrics 列表** |
| **device_id 的唯一性范围** | 在同一 Edge Node 内**必须唯一**；**跨 Edge Node 可重复** |

**层级对照**：Sparkplug 的 `Edge Node ↔ 我们的设备`、`Device ↔ 我们的采集点`、`Metrics ↔ 我们的测点`。

**旁证（不同流派）**：Azure IoT Hub 的主题只到设备级（`devices/{device-id}/messages/events/`，上一轮已核实），**没有采集点这一层**；LwM2M over CoAP 则把实例放进资源路径（`/ObjectId/InstanceId/ResourceId`）。

**【AI 补全】判据**：把某一层放进传输标识，取决于**它是否需要独立寻址**——能不能**单独订阅、单独授权、单独限流**。这正是增量 1 写下的"**主题即授权单位**"。

**对照我们的现状**：认证粒度是**设备级**（凭据绑在设备上），**采集点不独立持有凭据** → 按采集点做 ACL 没有需求 → **判据指向"进载荷"**。

⚠️ **两点要说清**：
1. Sparkplug 那招（**可选层级** + 消息类型区分）在**固定层级**的主题里不好直接抄——我们主题是四段定长，加一段要么全加要么不加。
2. **这是判据推出来的倾向，不是替决策人定**。除非你要按采集点做独立限流或独立订阅，否则"进载荷 + 不改已冻结的主题结构"更省。

**【AI 补全】不看实现、只看业务：这个选择影响的是四个能力**

| 能力 | 进主题 | 进载荷 |
| --- | --- | --- |
| **按采集点独立订阅** | ✅ 订阅 `…/+/p1/telemetry` 即"所有设备的第一路" | ❌ 只能订全量，应用层过滤 |
| **按采集点做访问控制** | ✅ 可以只授权某一路 | ❌ **补不了**——只能全给，让对方自己筛（安全上不可接受） |
| **按采集点限流** | ✅ 一路刷数据不波及他路 | ❌ 只能按设备限流 |
| **一条报文带多个采集点** | ❌ **强制拆成多条报文** | ✅ 天然支持 |

⭐ **所以影响的分量，取决于"有没有人按采集点寻址"。** P1 现状：**只有一个消费者（写库），没有** → 四个能力一个都用不上。

**但两侧的不对称值得记下**：

- **进载荷**的缺口**部分可补**（订阅全量后应用层过滤），**唯独"访问控制"补不了**——若将来要把某一路数据给第三方，载荷方案做不到隔离。
- **进主题**的缺口**补不了**（改主题要设备配合），而且它**强制设备侧"一路一报文"**——如果现场设备是一条报文带多路（网关代读多路串口就是这种），改成一路一报文会带来两个业务后果：**同一时刻的数据不再天然对齐**（本来同报文同 `ts`，拆开后可能不同时刻到达）；**报文数上升**（每条报文有固定开销）。

**判据可以收敛成两句由现场回答的问题**：

1. **设备侧一条报文是一个采集点，还是多个？**（网关代读多路 → 一条报文多采集点）
2. **有没有"只关心某一路"的下游？**（第三方取数、按点位授权、单点限流）

**两条都答"否"就进载荷**；任一条答"是"就进主题。

**【AI 补全】** 两个配套约束：**子表名怎么起**（表名上限 **192 字符**）；**子表数量 = 设备数 × 采集点数**（官方建议每 VGROUP 表数 ≤100 万，P1 规模无风险，但要登记容量触发点）。

### 轴 3 — 四个维度里**一个错位**、**缺一个高价值维度**

**【AI 纠偏】"采集点编号"作为标签是冗余的。** 若轴 2 定为"子表 = 采集点"，采集点编号**已经由子表名（`tbname`）唯一确定**，再作标签没有筛选价值。标签的价值是"**按它能筛出一批子表**"（§1.5）。

反过来：**只有选"一设备一子表 + 采集点做标签"的模型时，采集点编号才是标签。** 所以**轴 2 与轴 3 是耦合的**——轴 2 定了，轴 3 的答案才能定。

**【AI 补全】采集点编号不进标签之后，"按采集点筛"还筛得动吗？——筛得动，且是子表级裁剪。**

本机实测（`EXPLAIN` 证据）：

```sql
EXPLAIN SELECT tbname, v FROM pt WHERE tbname = 'p1'
→ QUERY_PLAN = "-> Table Scan on p1 (…)"

SELECT tbname, v FROM pt WHERE tbname LIKE 'p%'   -- 前缀筛，多张子表
```

`WHERE tbname = …` **不是行级过滤，而是把扫描裁剪到了那一张子表**。所以"采集点作子表名"并不牺牲筛选能力。

**但要分清两件事**：

| | 用途 |
| --- | --- |
| **子表名（`tbname`）** | **标识**——精确定位一张子表 |
| **标签** | **维度**——按它**裁剪一批**子表，并支持 `GROUP BY` 聚合 |

**真正的代价不是"筛不了"，而是"采集点没成为一等维度"**：要做"跨设备按采集点聚合"（例如"所有设备的第一路电流对比"），就得从子表名里解析字符串，或 `ADD TAG` 补上。

⭐ **而"补上"是可逆的**（本机实测）：`ADD TAG` 是元数据操作（~5 ms，与数据量无关）；**改单张子表的标签值也允许**——`ALTER TABLE <子表> SET TAG loc = 'A车间'` 成功执行，且中文值正常往返。所以"现在不加标签"不是不可逆的决定，代价只是**回填**（每张子表 SET 一次，子表多时要写批量脚本）。

**【决策人】位置做冗余、进标签**——为以后的筛选做准备，且认为"元数据多几个标签代价不大"。

**【AI 实证】这个选择的后果（本机实测）**——建一张超表，位置**同时**作标签与普通列：

| 步骤 | 标签 `loc` | 普通列 `loc_at_write` |
| --- | --- | --- |
| 写入 `(ts, v, 'A车间')`、`TAGS('A车间')` | `A车间` | `A车间` |
| **`ALTER TABLE h1 SET TAG loc = 'B车间'`** | **`B车间`** | **`A车间`（不变）** |
| 同一条历史数据再查 | **显示 `B车间`** | 显示 `A车间` |
| `WHERE loc = 'A车间'` | **0 行（筛不到）** | —— |

**结论：标签是"表级当前值"，改了会追溯性改写全部历史。** 所以"为筛选做准备"这个目的达成了；但**"那时候在哪"这个问法，标签答不了**。要保历史，只能靠**普通列**（行级）或**按版本切子表**——见 §4.4 的 SCD Type 2。

**【AI 补全】"代价不大"判断正确**：`ADD TAG` 实测是元数据操作（~5 ms，与数据量无关），标签值也能逐张子表 `SET TAG` 回填。

**【AI 补全】硬约束与未答项**：标签列 **≤128 个**、总长 **≤16 KB**、**至少一个**、**不能与测点列同名**、**不能是保留字**；`deviceId` 的 `VARCHAR(N)` 要覆盖最长 ID；"设备类型 / 品牌"用 `VARCHAR` 还是**整数枚举**（枚举更省、压缩更好，代价是可读性差 + 要维护码表）；另有 **`JSON` 标签**可打包"品牌+型号+厂商"，但**不可加/删/改列宽**，且一个表只能有一个 JSON 标签。

### 轴 4 — 结论对，但**三条理由有两条指向反面**

**【AI 纠偏】理由①「兼容分次上报」不是多列的优点。** 分次上报的安全性来自 **`NONE` 语义**（省略列保留旧值，§3.8 实测），**与模型无关**——单列模型分次写同样安全。这条归因不成立。

**【AI 纠偏】理由②「扩展成本低」对单列更有利。** 单列模型新增一个测点**不需要改任何表结构**（新指标就是新的标签值 / 新行）；多列模型要靠 `ADD COLUMN`——虽实测很便宜（元数据操作），但仍是结构变更，而且**若该超表将来要用于虚拟表继承，父级 schema 会冻结**。

**【AI 补全】真正该用的判据是这条**：官方对两个模型的取舍口径是——**测点的"量类型"是否频繁变化**。频繁变化 → 单列；稳定 → 多列。**我们的测点集合由设备类型决定，不频繁变化**，所以选多列成立；而单列的代价是**压缩率下降 + 每次分析都要 pivot**。

**【决策人】确认这条判据**：根本原因就是**采集指标应当不频繁变化**；另一个补充理由是**TDengine 对"变化"的代价实测很小**（`ADD COLUMN` 是元数据操作）——虽然仍比单列的"零结构变更"有代价，但**代价可接受**。

**【AI 补全】宽度这个约束正好被轴 1 化解**：一张超表 **≤4096 列**（含标签）。若轴 1 选的是"一张超表装全部设备"，撞上限只是时间问题；**轴 1 选"按类型分"，正好为轴 4 选多列扫清了障碍**。另：单行最长 **48 KB**（3.0.5.0 起 64 KB）。

### 轴 5 — **概念错位**：幂等键在 TDengine 里就是主键，而主键第一列必须是时间戳

**【AI 纠偏】"设备编号 + 采集点编号"不构成 TDengine 的主键。** 官方硬约束：**第一列必须是 `TIMESTAMP`，系统自动设为主键**（§3.1）。设备与采集点在 TDengine 里的正确位置是**子表标识**，不是主键列。

**真正的幂等键是 `(子表, ts)`，即 `(设备, 采集点, ts)` —— 时间戳必须在里面。**

**好消息**：若轴 2 定为"子表 = 采集点"，那么 **`(子表, ts)` 天然就是完整幂等键，不需要再加任何列**。轴 5 的答案由轴 2 决定。

**【AI 补全】重复投递的幂等是白送的**：契约里 `ts` 是**设备事件时间**且不随重投递改变 → 两次相同数据落在同一主键 → **覆盖，不产生重复行**。这一条**正面回答了增量 1 遗留的"QoS 0 静默丢数据 → 需要幂等"**。

**【AI 补全】`COMPOSITE KEY` 在 P1 需不需要？** 判据是：**同一 `(子表, ts)` 上会不会出现两条不同的读数**。P1 是每设备每秒一条、`ts` 由设备生成 → **不会** → **P1 不需要 `COMPOSITE KEY`**。
**触发点**：设备时钟粒度变粗（同秒双发）、或将来"补传历史数据"与实时数据撞同一 `ts`。

**【决策人】表述更正**：时间戳必须在幂等键里，此前的表述是笔误。

**【AI 补全】⭐ 幂等键与标签的关系——本机实测**：**标签不是唯一键，`tbname` 才是。** 实测：两张子表挂上**完全相同**的标签值，同一 `ts` 各写一条 —— **两条都保留、互不覆盖**。

```sql
INSERT INTO p1 USING pt TAGS ('same','same') VALUES (1759747300000, 1.0);
INSERT INTO p2 USING pt TAGS ('same','same') VALUES (1759747300000, 2.0);
SELECT tbname, ts, v FROM pt WHERE ts = 1759747300000;   -- → 两行都在
```

**推论（必须写进约束）**：幂等性由 **`(tbname, ts)`** 保证，**不由标签保证**。所以 **子表命名必须是确定性的**（如 `{deviceId}_{pointId}`）。如果同一台设备、同一个采集点被建成了**两张不同名的子表**，**幂等就破了、会产生重复行**，而且不报错。

这同时解释了官方的设计动机：**STMT 在子表不存在时报错、而 `taos shell` 自动建表**——正是为了防"表名写错 → 多一张表 → 数据分家"。

**【AI 补全】代价陈述（失败模式）**：两条**不同**数据撞同一 `(子表, ts)` → **后一条静默吃掉前一条，不报错**（§3.6）。

### 轴 6 — 方向对，但**"一刀切"有精度陷阱**，且缺了单位

**【AI 纠偏】「浮点用 `FLOAT`」要看量纲。** `FLOAT` 是单精度、约 **6-7 位有效数字**。对温度 / 电流 / 电压这类**瞬时量**够用；但**累计量**（累计流量、电表总电量、累计产量）会持续增长，数值变大后**低位精度丢失**，应评估 `DOUBLE`（约 15-16 位有效数字）。

**【AI 纠偏】「整数用 `INT`」不够细。** `INT` 4 字节、约 ±21 亿：**状态 / 瞬时整数**可用 `INT` 甚至 `TINYINT` / `SMALLINT` 更省；**累计计数**可能超 → `BIGINT`。

**【AI 纠偏】别忘负值**：温度、温差、功率因数都可能为负，**不要用 `UNSIGNED`**。

**【AI 补全】两处遗漏**：
- **`BOOL`（1 字节）**：开关量 / 状态位用它，比 `INT` 省 3/4。
- **类型选错不可逆**（实测）：`MODIFY COLUMN` **只能扩长变长类型**（`BINARY` / `VARCHAR` / `NCHAR` / `GEOMETRY`），**非变长类型完全不能改**。`FLOAT` 想改成 `DOUBLE` → **做不到，只能新增一列**。

**【AI 补全】⭐ 最要紧的缺口：`unit` 没有归宿。** 载荷里有 `unit` 字段，但入库方案里没有它的位置。这正是决策轴第 4 条「单位与量纲的契约」——**单位不进库，历史数据就不可比**（改单位不报错，只让历史不可解释）。

> 【决策人】单列的情况下可以加多一列；但在宽表的情况下，就得每个指标加多一列来存单位。

**【AI 补全】第三条路（通常更对）：单位进测点主数据，不进时序库**——分析见 §4.2，它与"位置"是同一类问题，判据见 §4.3。

**【AI 补全】非数值测点**：契约里 `value: number`。真实设备有 `BOOL` / 枚举 / 文本。P1 可以只管数值，但**这是落在设备侧（契约）的约定**，应登记触发点。

### 轴 7 — 范围判断合理，但**这不是"纯延期"**

**【AI 补全】"以后再做"不是零成本。** 虚拟表的层级**建的时候定型**：**父 VST 一旦有子，schema 就冻结**（`ADD/DROP COLUMN`、标签增删改全部被拒，§5.4）。所以将来建树时，**公共列集合必须在那一刻就是对的**。

**【AI 补全】更实际的一条**：**轴 1 选了"按类型分多张超表"，"跨类型统一列表"的需求从第一天就存在**——它只是**还债的时点**可以推。要写下：还债的两种手段（`UNION ALL` 每次对齐 / 虚拟表 层级定型）与**触发点**（出现第一个"跨设备类型统一列表"的报表）。

## 4. 时变主数据：位置与单位是同一类问题

两条看似无关的缺口，根因是同一个——**这一节是本轮最有价值的产出**。

### 4.1 位置：一个"会变的属性"，与它的三种处理方式

> 【决策人·第一轮】位置这一块应该通过设备管理里面的元数据去管理，因为设备在现场的位置是可移动的。否则以后一旦设备发生移动，不就是要改标签了吗？
>
> 【决策人·第二轮】**做一下冗余，把它放到标签里面，为以后的筛选做准备。** 而且元数据增加几个标签，代价应该不大。

**两轮的判断需要拼起来看，根因在第一轮要说准**：

- 标签的判据**不是"不可变"，而是"不随时间变化"**；而且**标签值本来就能改**——本机实测 `ALTER TABLE <子表> SET TAG loc = 'A车间'` 成功执行，中文值正常往返。
- 真正的问题是**改了之后历史怎么解释**：设备 3 月从 A 车间搬到 B 车间，改标签后**2 月的数据也会被解释成 B 车间**——这是**追溯性改写**，不是保留历史。两侧实测数据见 §3 轴 3。
- ⭐ **这正是术语表 #23 里已经识别过的那个缺口**——「主数据的失效 / 生效日期」。同一类问题，第二次遇到。

**所以"位置"是一个会变的属性**：它不适合做"必须恒定的"标识，但**适合做"当前筛选"的维度**。最终选择 = **冗余进标签**：

| 得到什么 | 失去什么 |
| --- | --- |
| 能按位置**筛**当前时序数据；标签代价低（实测 `ADD TAG` 元数据操作） | **不能回答"当时在哪"**——改标签会追溯性改写历史。这就是 §4.4 的 **SCD Type 1** |

**若将来需要"当时在哪"，动手的地方是**：把当时值固化进**普通列**（行级），或**按版本切子表**——两者都是**结构变更**，属 §4.4 的 Type 2。

**但代价必须讲清——这是双库分治的第一个真实代价**：位置留在 PG 之后，**TDengine 里无法按位置直接筛时序**（`FROM stb WHERE location = 'A'` 做不到，TDengine 连不到 PG）。三条出路：

| 出路 | 代价 |
| --- | --- |
| ① 先查 PG 拿设备清单 → 再拿清单查 TDengine（两跳） | 查询变两段，分页与聚合都要在应用层拼 |
| ② 把位置**冗余一份**进标签 | 接受"历史按当前值解释"的口径漂移 |
| ③ 建"设备-位置-时间段"历史，按时间片切 | 最正确也最贵 |

**归属提醒**："设备档案 / 设备注册"属**增量 3**。所以"位置放设备管理"等价于**把位置推给增量 3**——要写清归属，否则会变成"没人管"。

### 4.2 单位：同一个问题的另一个形态

> 【决策人】如果是用单列的情况下，可以加多一列；但在这种宽表的情况下，就得每个指标加多一列来存单位了。

对。但还有**第三条路，且通常更对**：**单位不进时序库，进测点主数据**。

| 方案 | 代价 |
| --- | --- |
| 每指标加一列 | 宽表列数**翻倍**；单位是**字符串**，压缩率远差于数值 |
| **单位进主数据**（测点元数据） | 读时序要带单位得跨库拼——**与位置完全同构** |
| 单位进标签 | **粒度不对**：标签是采集点级，单位是测点级 |

**理由**：单位**不随时间变化**（若变，那是测点重定义）→ 它是**测点的元数据**，不是时序数据的一部分。

**【决策人】倾向"放主数据与物模型维护"** —— 由此派生出**归一化转换**这一步，见 §4.5。

### 4.3 由此得到一条可复用的判据

位置、单位、量纲、设备型号、品牌——它们都属于"**不需要逐条重复、但可能被用来解释或筛选**"的元信息。**决定它们放哪的判据只有一句**：

> **它会不会被用来"筛 / 聚合时序数据"？**
>
> - **会** → 必须在时序库里有一份参照物（标签，或作为列冗余）
> - **不会** → 放主数据（PG），用时在应用层拼

**这就是双库分治的边界。** 边界不划在"数据属于谁"，划在"**这个属性参不参与时序查询**"。

⭐ 这条同时回答决策卡**附录 A** 的两条轴：**轴 4（单位与量纲的契约）**与**轴 3（数据生命周期）**——它们不是"时序库的问题"，是"**双库边界的问题**"。

### 4.4 行业怎么管"会变的属性"：Kimball 缓慢变化维度（SCD）

"人员调动后报工归属不清"不是本项目特有的问题，数据仓库领域有一整套成熟答案，**上面的三种出路与它一一对应**。

**Kimball 维度建模的三型**（原文见查证台账）：

| 型 | 做法 | 官方定性 |
| --- | --- | --- |
| **Type 1 · Overwrite** | 新值**覆盖**旧值 | *"type 1 attributes always reflects the most recent assignment, and therefore **this technique destroys history**"*；并提示**受影响的聚合表与 OLAP 立方体需要重算** |
| **Type 2 · Add New Row** | 维度**加一行** + **代理键**；至少三个附加列：**生效日期 / 失效日期 / 当前行标识** | *"**a new primary surrogate key is assigned and used as a foreign key in all fact tables**"* |
| **Type 3 · Add New Attribute** | 加一列存旧值（"alternate reality"） | 用得相对少 |

**业务系统（OLTP）侧的等价物**是**系统版本化时态表**（SQL Server 2016+）：主表 + **历史表**，系统自动维护每行的**有效期**，支持 **point-in-time 分析**。

⭐ **Type 2 的核心常被误读**：它**不是**"要建一张很重的生命周期表"，而是这一句——**事实表里存的是"当时那版维度的代理键"**，也就是**把"当时值"固化进事实本身**。旭诚那套"站点独立生命周期"是它的**重实现**；轻量版就是这一句。

**对应到本项目**：

| SCD | 在 TDengine 里能做到吗 |
| --- | --- |
| **Type 1（覆盖）** | ✅ **就是现在的做法**——改标签。实测已证历史被追溯改写 |
| **Type 2（加行 + 代理键）** | ⚠️ **标签是表级的，承载不了"行级的历史快照"**。等价物只有两个：**① 用普通列把当时值固化进行里**（实测对照 `loc_at_write` 保持不变）；**② 按维度版本切子表**（子表 = 维度的一个版本）——但子表数随变更次数增长，且**会冲掉 `(tbname, ts)` 幂等**（同一 `ts` 可能落进两张子表） |
| **Type 3（加一列存旧值）** | ✅ 可行，与 ① 同构 |

**所以"冗余进标签"是 Type 1 语义**：**能筛"当前在哪"，不能回答"当时在哪"。**

### 4.5 单位进主数据之后，多出来的一步：归一化转换

> 【决策人】单位这一块是可以放到主数据和物模型里面去维护的。那这样是不是就有了另外一步要做了？就是数据采集上来的时候，要和标准单位做一次转换。

**这个推论成立，而且这一步是必然的。** 单位归主数据 = 平台持有**标准单位**；设备上报的是**它自己的单位**（载荷里的 `unit`）。两者不一致时，链路上必须有一次归一化。

补三点代价：

| # | 说明 |
| --- | --- |
| 1 | **转换不可逆且丢精度**：℉→℃ 有舍入；**原始值一旦不留，就无法回溯校验** |
| 2 | **转换错误是静默的**：设备的 `unit` 报错或缺省 → 照转（或按默认值转）→ **历史数据静默污染，不报错**。与增量 1 的 QoS 0 静默丢数据同类 |
| 3 | **行业原则是"存事实，解释可重算"**（计量 / 合规场景通例，也是 HJ212 那套"数据不得修改"的同源原则）。所以真正该问的是：**转换在写时做还是读时做？** |

| 时机 | 代价 |
| --- | --- |
| **写时做** | 查询快，但**不可重算**——将来标准单位改了、或发现换算系数错了，历史改不回来 |
| **读时做** | 可重算，但每次查询要 join 主数据 |
| **折中** | 存**原始值**，并留一个能标识"当时用的哪个单位 / 系数"的东西——但那等于**单位又回到了时序库** |

⚠️ **这里与 §4.3 的判据撞上了**：如果单位会被用来**校验或重算**时序，它就**参与**了时序语义 → 按判据，时序库里必须有一份参照物。所以"单位进主数据"**不是无条件正确的**，取决于**要不要能校验与重算**。

## 5. 生产前提复核：本项决策的最终论据

> **口径**：§2–§4 的讨论是在 P1 **当前形态**下做的。这一节把七条决策放到**真实生产前提**下逐条重过——不是重开讨论，是检验它们的**完备性**：方向对不对、还差什么。

### 5.0 复核的前提：模拟器与生产的差距

七条决策都建立在模拟器的隐含假设上，**这些假设在生产里多数不成立**：

| 维度 | 模拟器（P1 现状） | 生产现实 |
| --- | --- | --- |
| **设备是不是我们写的** | 是 | **不是**——固件改不动，升级要现场施工 |
| 设备规模 | 100 台 | 千级 → 十万级 |
| 上报形态 | 每台每秒一条、一条带全部测点 | **混合**：一条报多个采集点（网关代读多路）／一个采集点分多条（测点频率不同）／事件触发 |
| 上报频率 | 统一 1s | 1s ～ 15min 混合 |
| 时间戳 | 平台生成、毫秒、准确 | **设备本地时钟**，可能偏几分钟到几天 |
| 顺序 | 天然有序 | **断网补传 → 大量乱序 + 大批量** |
| QoS | 0 → **1**（2026-10-09 改，见第 3 项 §9） | 生产大概率 1+（**重复投递**）——现已对齐 |
| 消费者 | 1 个（写库） | 多个：告警 / AI / 看板 / **第三方** |
| 设备身份 | 我们分配 | 平台签发 + 设备持凭据（增量 1 的认证触发点） |
| 设备状态 | 不变 | 会**搬迁 / 换型 / 报废 / 固件升级** |
| 测点集合 | 固定 3 个 | 固件升级会**新增**；不同品牌型号不同 |
| 隔离要求 | 无 | 可能有**第三方只能看自己的设备** |
| 部署 | 单节点 | 需要副本 / 高可用 |

### 5.1 逐轴判定

| 轴 | 生产前提下 | 要补什么 | 触发点 |
| --- | --- | --- | --- |
| **1 按设备类型分超表** | ✅ **更成立**——列集合一致才能共用，生产下类型更多更需要它 | **责任人缺口**：自动建表**只建子表**，超表必须预先存在 → 需要"**类型注册 → 建超表**"的流程，归属**增量 3**。当前决策没写谁做 | 设备类型到两位数；或第一次"设备换型" |
| **2 采集点一对多 + `pointId`** | ✅ **成立**，且被 Sparkplug 的形态印证 | **唯一标识是 `(deviceId, pointKey)` 复合**（两段都由平台生成，见 §8），不是单一个（Sparkplug 同款：`device_id` 在同 Edge Node 内唯一、跨 node 可重复，见 #107）；**设备报的 `localPointId` 应允许缺省**（大量设备本就单采集点）；消费者须能处理"一条报文 N 个采集点"与"一个采集点 N 条报文"**两种形态**——统一做法是先摊平成 `(localDeviceId, localPointId, key, value, ts)` 的测点记录，再经档案解析出 `pointKey`、按子表分组攒批 | —— |
| **3 标签清单** | ⚠️ **要补** | **① 加层级维度**（区域 → 车间 → 产线 → 设备）。生产里"看整个车间的数据"是刚需，而按 §4.3 判据，**要用来筛时序就必须是标签**；**② 区分标签的来源**：设备自报的"类型/品牌/位置"**不可信**（增量 1 已识别 `clientId`＝连接身份 vs 载荷 `deviceId`＝设备自报的差异），这些标签应由**平台档案在建子表时填**，不从载荷取 | 第一次要按层级聚合 |
| **4 多列模型** | ✅ **成立**（生产的"测点集合稳定"仍基本成立——只在固件升级时变） | **未知测点策略**：设备报的 `key` 可能不在超表列集合里（固件升级 / 配置错 / 恶意）。三条路——**丢弃+计数**（最保守）／**告警**／**自动加列**（需 schemaless，本项目不用）。**这条必须定**，因为它决定"静默丢数据"还是"schema 被污染"；另需**加列的发布流程**（实测便宜 ≠ 不需要流程） | P1 schema 落地前 |
| **5 幂等键 `(子表, ts)`** | ⚠️ **最脆弱的一条** | **① 时间戳精度要求**：秒级精度的设备同一秒两条 → **静默覆盖丢数据**。"P1 每秒一条不会"这个前提在生产**不成立**——契约要写明精度要求，并对秒级设备给兜底（可考虑 `COMPOSITE KEY` 加序号列，这正是之前判"P1 不需要"的**触发点**）；**② 双时间轴**：生产必须同时记**事件时间（设备 `ts`）与平台接收时间**，当前 schema 里没有接收时间（增量 1 已识别为遗留）；**③ 补传通道**：补传必然乱序，而"同一子表须按 `ts` 升序提交"是官方要求（乱序触发服务端额外排序） | 出现秒级精度设备；断网补传需求出现 |
| **6 测点列类型** | ⚠️ **要按生产测点分档** | 生产里**累计量是常客**（电表、流量计、产量计数）→ `FLOAT` 的 6-7 位有效数字**不够** → 累计量用 `DOUBLE` / `BIGINT`。且**类型不可逆**，上线后再改要迁数据。现在应写**分档规则**，清单留给增量 3 物模型 | 增量 3 物模型定型后复核 |
| **7 虚拟表延期** | ✅ **成立**（P1 不做） | 要记：生产下"跨类型统一列表"是刚需（看板 / 报表），而虚拟表**只读、不支持订阅**、**父 VST 有子后 schema 冻结** → **建树的时点**是个决定（早建灵活但可能锁错，晚建则公共列难改） | 第一个"跨设备类型统一列表"的报表 |

### 5.2 结论：**七条方向全部成立，推翻了 0 条**

要补的不是"选错了"，是"**没选到的地方**"。三类：

| 类别 | 涉及轴 | 内容 |
| --- | --- | --- |
| **要加的约束** | 轴 2、5、6 | 唯一标识的复合性；时间戳精度要求；类型分档规则 |
| **要加的维度** | 轴 3、4 | 层级标签；标签的可信来源；未知测点策略 |
| **要接的上下游** | 轴 1、7 | "类型注册 → 建超表"的流程（增量 3）；虚拟表建树的时点 |

⭐ **一个共性**：这些缺口**都不是 TDengine 造成的**，而是**"从单机模拟走向多来源现场"必然出现的**——是**系统边界扩张**带来的，不是**存储选型**带来的。所以它们的影响面在**契约、设备档案、消费链路**，不在存储引擎。

### 5.4 本项的最终论据（一段话）

> 七条决策在**生产前提下没有一条需要推翻**——它们的依据（列集合必须一致、时间戳即主键、`NONE` 保留旧值、标签是表级当前值、虚拟表是读侧能力）都来自**存储引擎的确定行为**，不随设备形态改变。缺口按归属切开后，**真正属于本项决策的空白只有 3 条**（未知测点策略、接收时间列、时间戳精度契约），另 2 条已由本项决策确定、只需写清，其余 8 条属接入 / 消费 / 运维 / 合规域。**所以本项的风险不在选型，在完备性**：把上面这几条带上，这套 schema 就能从"P1 模拟"平移到"生产现场"，而不需要重建数据模型。**外部参照（§5.5）印证了这个判断**：与 AWS IoT Lens 的七条 IoT 专属设计原则对照，命中的正是"解耦摄取与处理"这条——它就是我们的 ADR-010。

### 6.1 本项已定（**七轴 + 唯一标识 + 三个结构类开口项**）

### 6.3 测点列类型的分档规则（开口项 3 的结论）

**先记一条约束**：**非变长列完全不能 `MODIFY`**（只有变长类型能扩长）→ **类型选错只能新增列**。所以规则要**先写下**，不是每次临时判断。

| 量的性质 | 判据 | 类型 |
| --- | --- | --- |
| **瞬时量**（温度、电流、振动、压力） | 量级稳定，6-7 位有效数字够用 | **`FLOAT`**（4 字节） |
| **累计量**（累计流量、电表总电量、累计产量） | **数值持续增长 → 高位变大后低位精度丢失** | **`DOUBLE`**（8 字节） |
| **需要 7 位以上有效数字的瞬时量**（高精度计量） | 同上 | `DOUBLE` |
| **状态 / 枚举**（开关、档位、码值） | 小范围 | **`TINYINT`** / `SMALLINT` |
| **布尔量** | 只有两态 | **`BOOL`**（1 字节，比 `INT` 省 3/4） |
| **累计计数**（总次数、总件数） | 持续增长，可能超 ±21 亿 | **`BIGINT`** |

⚠️ **两条硬提醒**：

1. **不要用 `UNSIGNED`** —— 温度、温差、功率因数都可能为负，无符号列容不下负值
2. **契约的 `value` 是 JS number（双精度），而列是 `FLOAT`（单精度）时写入会静默截断** —— 生产上若某测点需要双精度，**列类型必须跟着用 `DOUBLE`**，否则精度在写入时丢掉且不报错

**应用到 P1 的清单**（＝模拟器当前的测点集）：

| 测点 | 单位 | 量级 / 特性 | 类型 |
| --- | --- | --- | --- |
| `temperature` | °C | 瞬时量，base 62 / spread 6 | **`FLOAT`** |
| `vibration` | mm/s | 瞬时量，base 1.8 / spread 0.9 | **`FLOAT`** |
| `current` | A | 瞬时量，base 4.3 / spread 1.1 | **`FLOAT`** |

⭐ **三个都落 `FLOAT`，所以这条规则在 P1 用不出差别**——它的价值在**将来识别出"累计量"的那一刻**。真实设备上累计量是一大类（电表、流量计、产量），而它们在 `FLOAT` 上会**在高位静默丢精度**。
**触发点**：增量 3 物模型定型后，用真实指标清单过一遍上面这张表。

**① 选定**

```text
超表     按设备功能类别分（宁可粗分）；子表 = 采集点
唯一标识 (deviceId, pointKey) 复合 → 子表名 = {deviceId}_{pointKey}（§8）
契约     新增 pointId（可缺省），进载荷、不进主题

模型     多列；行 = 一个采集点的一个时刻
主键     (子表, ts)；P1 不加 COMPOSITE KEY
类型     按分档规则（累计量 DOUBLE/BIGINT、瞬时量 FLOAT/INT、状态 BOOL；不用 UNSIGNED）
虚拟表   P1 不做
```

**② 代价陈述（这套 schema 会怎么坏）**

| # | 失败模式 | 什么时候会咬人 |
| --- | --- | --- |
| 1 | **同一 `(子表, ts)` 上的第二条不同读数 → 静默覆盖**，不报错 | 设备时间戳精度粗到秒、同秒双发；或补传数据与实时数据撞 `ts` |

| 3 | **位置标签的 Type 1 语义 → 历史报表口径随当前值漂移** | 设备搬迁之后，任何按位置的历史统计 |
| 4 | **未知测点被丢弃**（默认策略）→ 设备多了个指标而平台静默不要 | 设备固件升级新增测点 |
| 5 | **跨设备类型的统一列表要每次手工对齐列** | 第一个"跨类型统一列表"的报表（轴 1 + 轴 7 的债） |

**③ 退出成本（想换掉要付什么）**

| 换什么 | 代价 |
| --- | --- |
| **换时序库**（不与本项冲突，但要知道） | 契约与消费链路基本不动（TDengine 语义已隔离在消费者内）；**数据要迁**；主键 / 类型 / 子表命名这套是 TDengine 特性，换库要重设计 |

### 6.5 收尾补条：两处**必须在契约里冻结的取值**

> 定稿时按"**这个决定将来改，会不会导致历史数据迁移或设备侧调整**"过了一遍（实测见下表）。结论：**结构性的边界已被识别并慎待**，但有**两处"取值"没冻结**——它们本身不复杂，**但一旦有数据就不能改**。

**实测出来的结构性边界**（本机 3.4.2.8.community）：

| 试的动作 | 结果 |
| --- | --- |
| 给已有超表加 `COMPOSITE KEY` | ❌ `not support alter column with option except compress` |
| 给已有超表加**普通列** | ✅（对照） |
| 改主键列类型 | ❌ |
| **改子表名** | ❌ 两种常见语法均报 `syntax error`（**未找到支持的表重命名语法**） |
| **删列** | ✅ 但**数据不可再查**（`Invalid column name`）——删列是破坏性的 |

**两处取值已定（见 §8）**：

| # | 项 | 取值 |
| --- | --- | --- |
| 1 | **子表命名规则** | `{deviceId}_{pointKey}`——`deviceId` 为 16 位全大写随机串、`pointKey` 为 3 位递增数字，分隔符 `_`（§8.2） |
| 2 | **缺省值** | `localPointId` 缺省 = `001`；适用范围由 §8.3 规则 2 限定 |

⚠️ **冻结的理由不变**：**表名一旦建了就改不了**（实测）→ 改格式 = 旧子表对不上 = **数据分家、幂等破**。
⭐ **一处性质变化**：取值**锚在两段平台生成的字符串上**，所以「非法字符怎么处理」不再成其为问题——设备报的 `localPointId` **不进表名**（§8.4）。

**其余各项为什么不构成破坏性隐患**：

| 决策 | 改它的后果 |
| --- | --- |
| 轴 1 按功能类别分（宁可粗分） | 只在"发现划错"时才要迁；**"宁可粗分"把这个概率压到最低**（粗分只是稀疏，不是错） |
| 轴 3 标签 | **加标签是纯加法**（`ADD TAG` 实测是元数据操作） |
| 轴 4 多列 | **加列是元数据操作**（实测）；⚠️ 但**删列是破坏性的**（实测） |
| 轴 6 `FLOAT` | 类型不能改 → 加新列回填，**只影响一列**，不是全表迁移 |
| 轴 7 虚拟表 | 不做 = 零结构约束；将来建 VST / VCT 也是纯加法 |
| 轴 2 `pointId` 进载荷 | 已选"对两种设备形态都兼容"的一侧，**不动主题层级** |

⭐ **一条规律**：**加法（加列 / 加标签 / 加通道 / 建虚拟表）安全；结构性（主键 / 列类型 / 表名 / 超表切分）一旦定了不能变。** 结构性的四项都已被识别并慎待，只漏了"表名格式"与"缺省值"这两个**具体取值**。

### 6.6 对"设备侧不确定性"的对策框架与检测清单

**起因**：曾以"**根因在设备侧，不该由 schema 兜**"为由判定不做结构性兜底。**这个理由不成立**——它是追责逻辑，不是工程逻辑。生产系统以"**上游不可靠**"为设计前提，这点在外部参照里有明文（§5.5 原文）：

| 出处 | 原文要点 |
| --- | --- |
| AWS IoT Lens **原则 2** | 设备会因 "connectivity issues or **misconfigured settings**" 离线比预期更久——**把"设备配错"当常态** |
| 同条原则 | 要求云侧 "**create metrics to track** devices that are not connected or communicating on a regular timeframe"——**检测是明写在标准里的** |
| 原则 5 | 要求**设备侧**主动定期上报状态——**不能假设云侧能知道设备状态** |
| 原则 3 | 设备侧数据"精简"、云端"补全"——**假设设备给的不完整** |
| 原则 7 | **defense in depth**，多层控制 |

**正确的对策是三层，结构性兜底是最后一层**：

```text
第 1 层 · 准入约束   契约里写死要求（毫秒 ts、pointId 字符集 …）
第 2 层 · 检测       违反时"看得见"（计数 + 告警），不静默
第 3 层 · 结构兜底   检测之后仍不可接受，才改数据模型
```

⭐ **第 2 层是主答案**：绝大多数"设备不可靠"的后果，正确处置是"**让它可见 + 治理根因**"，而不是"用存储买单"。

**检测清单（现状：除解析失败外基本空白——这是本项之外的一处真实缺口）**

| # | 检测什么 | 为什么 | 现状 | 归属 |
| --- | --- | --- | --- | --- |
| 1 | **重复 `ts`**（同一子表、同一 `ts` 被写多次） | 会**静默覆盖**（§3.6）——本套 schema 的**头号失败模式** | ❌ | **第 2 项** |
| 2 | **时钟偏移**（设备 `ts` 与平台接收时间之差） | 设备时钟不可信（增量 1 遗留）；偏移超阈值应告警 | ❌（连接收时间都没存，B1） | 第 2 项 + 增量 6 |
| 3 | **未知测点 `key`** | 设备固件升级多报指标 → 现在会静默丢弃 | ❌ | **第 2 项**（§6.2 第 6 条） |
| 4 | 数值越界 / 非法值（NaN、超量程、负值进了无符号位） | 脏数据污染存储与后续分析 | ❌ | 第 2 项 |
| 5 | **设备"该来没来"** | 掉线无法与"不报"区分 | ❌ | **增量 6**（B10） |
| 6 | 解析失败 | 系统边界输入 | ✅ 增量 1 已有计数 | —— |
| 7 | **写入影响行数对账** | 判断"到底写进去了没有" | ⚠️ 随第 2 项落地 | 第 2 项 |

**C 类的结论（修正后）**

| 项 | 判断 | 理由（**已替换**） |
| --- | --- | --- |
| 8 · 提前加 `COMPOSITE KEY` | **不提前加，但必须补上检测第 1 条** | 理由不再是"责任在设备"，而是"**触发点天然早于规模**"——风险在接第一台秒级设备时暴露，那时数据量小、**迁移窗口存在**。⚠️ **但前提是你看得见它**——所以第 2 层是必需的，不是可选的 |
| 9 · 测点列全用 `DOUBLE` | 留到**增量 6**用真实存储数字判 | 那时才有依据 |
| 10 · 加 `raw` 原始值列 | 同上 | 加了它才有"重算"能力；不加则单位 / 精度错误只能靠历史数据之外的信息修 |

**第 3 层的判据（什么时候才该做）**：

> ① **检测到之后，损失是否仍不可接受？**（例如"同秒多条"在业务上是否必须全保）
> ② **发现窗口是否存在？**（触发点会早于规模出现，还是会在数据很大时才浮现？）

**本项的处置**：第 1 层落 §6.5 的两条冻结值；**第 2 层作为第 2 项（写入方式）的输入**——检测就是"失败处理"的一部分；第 3 层本轮判定为不做，判据与触发点已写明。

⭐ **一处方法论上的收获**：判断"要不要为上游的不确定性预留"时，**别问"谁的责任"，要问"有没有更便宜的一层能兜住，以及发现窗口在不在"**。

## 8. 子表命名与采集点标识（2026-10-09 定）

> §6.5 把「子表命名规则」与「`pointId` 缺省值」列为**必须冻结的两处取值**，但没有给值。本节给出值，并交代它们依据的模型。
> ⚠️ **本节同时改写 §1 的「唯一标识」一行**：子表名里的两段**都由平台生成**。

### 8.1 模型：平台生成 + 内部映射（记为 C）

| 模型 | 子表名里的采集点来自 | 要下行通道吗 | 设备要配合什么 |
| --- | --- | --- | --- |
| **A · 设备自报** | 设备报的 | 不要 | 编号要守平台规范 |
| **B · 平台生成 + 下发** | 平台生成、下发 | **要** | 收得下、存得住 |
| **C · 平台生成 + 内部映射** | **平台档案里的权威名** | **不要** | 只报一个"自己稳定"的编号 |

**选定 C**。三条依据：

1. **行业形态**——AWS IoT 在**制造阶段**把身份装进证书（IoT Lens：*"The first step to provisioning a device is to **install an identity**"*）；Azure DPS 的 `device ID` **可由平台指定**（enrollment 里的 "desired device ID"，不指定才沿用设备的 registration ID）⇒ ⭐ **"平台握权威名、设备只提供注册键"是标准做法**
2. **工业场景的前提**——一个工厂的设备来自不同厂商，**没有统一编号机构**，也**不能要求厂商改固件** ⇒ **A 的前提不成立**
3. **环保经验的对照**——国控/省控的站点编号由**平台统一编**、再**给到数采去设置**，那是 **B**；它成立靠三个前提（**有行业规范 / 数采支持设置站点编号 / 有人去填**），**工业三个都不在**

⚠️ **但行业版的 C 还有一步我们 P1 做不到**：Azure DPS 会把分配结果**回传给设备**（*"The DPS instance … **passes that information back to the device**"*）——**我们没有下行通道**，设备侧只能一直用它自己的本地编号。

**档案表**（增量 2 用 seed 配置承载，增量 3 起换成真设备档案）：

| 列 | 谁产生 | 进不进子表名 |
| --- | --- | --- |
| `localDeviceId` | 设备报的（连接身份） | ❌ |
| `deviceId` | **平台签发** | ✅ |
| `localPointId` | 设备报的（**可缺省**） | ❌ |
| `pointKey` | **平台生成** | ✅ |

⭐ **它同时是"存在性检测"的依据**——设备与采集点对不对得上，查的就是这张表。

**一层消费还是两层：两层**（2026-10-09）。判据与 `pointId` 同一个：

> 能不能要求**设备本身**在出厂 / 现场组态时，被配成平台签发的那个编号？

**不能**——现场设备来自不同厂商，采集点层既然不要求厂商配合，设备层同样不能要求。⇒ **`deviceId` 也走档案映射**（与 `pointKey` 同一条路）。

- **行业对照**：Azure DPS 正是这一形态——设备提供 registration ID（证书 CN），平台另有 device ID，**两个并存、由 enrollment 关联**；AWS 相反，身份在**制造阶段**装进证书
- ⚠️ **代价：两套设备标识并存** ⇒ 实现时必须**处处分清用哪一个**：

| 出现位置 | 用哪个标识 |
| --- | --- |
| MQTT 主题 `wewant/devices/{…}/{channel}` | `localDeviceId`（设备报的） |
| MQTT `clientId` | `localDeviceId` |
| 载荷字段 | `localDeviceId` |
| **TDengine 子表名** | `deviceId`（平台签发） |
| **标签** | `deviceId`（平台签发） |
| 档案表 | **两个都有**——它就是两者的对应关系 |

⚠️ **两处因此要跟着确认**：① 增量 1 冻结的主题结构里那个占位名写的是 `{deviceId}`，**实际含义是"设备报的编号"**——改注释还是改字段名，落地时定；② 标签清单里要不要**同时挂 `localDeviceId`**（便于按设备自报的编号反查），属**第 2 条标签清单**的范围。

### 8.2 取值

| 项 | 值 |
| --- | --- |
| `deviceId` | **16 位随机字符串**，平台侧生成，**全大写、不含下划线**（例 `AWEAWQ05E8PF53WH`） |
| `pointKey` | **3 位递增数字，不足补零**，同设备内唯一（例 `001`） |
| 分隔符 | `_` |
| 子表名 | `{deviceId}_{pointKey}` → `AWEAWQ05E8PF53WH_001` |

- **字符集**：`deviceId` 为 `[0-9A-Z]{16}`、`pointKey` 为 `[0-9]{3}` ⇒ **两者都不含 `_`，拼接无歧义**
- **长度**：16 + 1 + 3 = 20，远低于表名上限 192
- ⚠️ **存储形态**：TDengine 的标识符**不分大小写、存储时折成小写** ⇒ 设计时写的 `AWEAWQ05E8PF53WH_001`，库里是 `aweawq05e8pf53wh_001`（§9.1 V3）。**"全大写"是生成侧的约定**（防 `0/O`、`1/I` 一类易混字符），不是存储形态

### 8.3 四条配套规则

1. ⭐ **`pointKey` 只增不复用**——删掉的号不再分配。否则第 2 路拆掉后新装一路又拿到 `002`，**同一张子表里前后是两个不同的物理采集点**，历史被读成新点且不报错
2. ⭐ **缺省 `001` 只对"档案登记为单点"的设备生效**——多点设备漏 `pointId` 字段时**拒绝 + 告警**，不用缺省。否则第 3 路的数据会被静默写进第 1 路的子表
3. **`localPointId` 超长要拒绝，不能截断**——它落在档案表的键列上，截断会让两个不同的长编号**撞成同一个键**
4. **规范化只针对"同一台设备前后不一致"**（统一大小写、去首尾空白）；**设备之间编号不一致不管**——那正是 C 要支持的

### 8.4 `localPointId` 不需要字符集约束（C 的红利）

`localPointId` **不进表名**，只进档案表的键列 ⇒ **设备报含 `_`、含 `.`、大小写混杂都可以**。

（对照：模型 A 下 `deviceId="a_b"` + `pointId="c"` 与 `deviceId="a"` + `pointId="b_c"` 会生成**同一个表名**——这个风险在 C 下不存在。）

### 8.5 代价

| 项 | 代价 |
| --- | --- |
| **档案必须真的存在** | 报到之前档案里那条记录就得有——**"注册"不是一个流程名词，是一个必须有人或程序做的动作** |
| **多一次查表** | 每条报文都要拿到 `pointKey` ⇒ **必须本地缓存 + 失效**（万级设备下查 PG 不成立，见第 2 项 §6 轴 10） |
| **映射一旦有数据就冻结** | `(localDeviceId, localPointId) → (deviceId, pointKey)` 改了就是**数据分家**——与模型 A 同强度，**C 买到的不是"更稳"，是"平台能定名、设备不必守规范"** |
| **比行业版少一环** | 分配结果回传不了设备（无下行通道） |

### 8.6 命名对齐（2026-10-09 定）

**两段标识各有"平台签发的"与"设备报的"之别，名字必须一眼分清**，否则 §8.1 那张"哪个位置用哪个"的表就没有抓手：

| 位置 | 现在写的 | 对齐后 |
| --- | --- | --- |
| 契约载荷字段 | `deviceId` | **`localDeviceId`** |
| 主题占位名（`telemetryTopic` 的形参与注释） | `{deviceId}` | **`{localDeviceId}`** |
| 采集点字段（§6.1 已定新增、可缺省） | —— | **`localPointId`** |

⚠️ **两处的改动性质不同**：

- **主题**：**wire format 不变**（仍是 `wewant/devices/<id>/telemetry`），改的只是形参名与文档里的占位名
- **载荷字段**：**真改名**，wire format 随之变化

⚠️ **代码改动不在本轮**——契约与各处调用点的改名，随增量 2 的实施计划一起做。

### 8.7 标签清单：P1 版与分期（2026-10-09 定）

**口径**：标签清单**不是一次冻死的**——§6.4 定的四个（`deviceId` / 设备类型 / 设备品牌 / 位置）是**目标形态**；具体哪几个进、什么时候进，**跟设备档案（增量 3）一起、按业务需要定**。

**支撑这个口径的实测事实**：**`ADD TAG` 是元数据操作**（~5 ms，与数据量无关）⇒ **加标签可后补**，代价只是给已有子表回填。

**P1 版 ＝ 只留 `deviceId`**（⇒ 它的类型随之定为 **`VARCHAR(16)`**）：

| 标签 | P1 | 为什么 |
| --- | --- | --- |
| `deviceId` | ✅ 留 | 定长 16 位；它让 `GROUP BY deviceId` 干净——子表名是 `{deviceId}_{pointKey}` 拼出来的，直接 `GROUP BY tbname` 拿到的是拼串 |
| 设备类型 | ❌ | **超表本身就按功能类别分**（轴 1）⇒ P1 只有一类设备时它**查不出任何额外的东西**。真实场景里"一张超表内还要再分档"（如贴片机里的高速机 / 中速机）时才有用 |
| 设备品牌 | ❌ | P1 无用例；设备是模拟的，无真实品牌 |
| 位置 / 产线 | ❌ | P1 无此概念；**且它是"会变"的维度**，等增量 3 一起判（见 8.7.1） |

⚠️ **标签 ≠ 指标**：标签是**设备 / 采集点的属性**（决定"查哪些设备"），**指标落在列上**（决定"查哪些量"）。

#### 8.7.1 新增触发点：增量 3 设计设备档案时

> ⭐ **两件事必须在那一刻做完**，因为它们都**不能推迟到"业务提出来"的时候**：

**① 过一遍"哪些维度会变、要不要能回答'当时'"**

判据：**标签与普通列都可以后补，但两者都补不出已经过去的值。**

⇒ **会变、且要答案"当时"的维度，必须在它第一次变之前就记**——标签不够，要**普通列**（行级固化）或**一张变更历史表**。

**② 定层级位置放哪几层**

输入是一条已确认的事实：

> 工厂里**存在多条产线共用、放在公共区域的设备**（空压机、动力柜一类）——**它们不属于任何一条产线，但有明确位置**。

⇒ **只用 `line` 一个标签，这些设备归不了组**；⇒ **层级至少要能表达"产线之外的公共区域"**（如 `area` / `workshop` / `line` 三层，其中 `line` 允许为空）。

⚠️ **为什么列到增量 3 而不是现在**：P1 的设备是**模拟器造的**，没有真实产线归属 ⇒ **P1 期间不存在"会变的维度值"，没有历史可丢**。真正的触发点是**第一台真实设备接入之前**。

⚠️ **别与"效率基线"混淆**：那是**真实产线改造前**必须先采的数据（前提复议 §3 B2），**不是本项**；P1 的模拟数据也当不了基线。

## 9. P1 超表清单（2026-10-09 定；DDL 已实跑复核）

```sql
CREATE DATABASE <原始库> PRECISION 'ms' KEEP 1095 DURATION 10;
CREATE STABLE telemetry (
    ts          TIMESTAMP,
    temperature FLOAT,
    vibration   FLOAT,
    current     FLOAT
) TAGS (deviceId VARCHAR(16));

CREATE TABLE <deviceId>_<pointKey> USING telemetry TAGS ('<deviceId>');
```

| 项 | 值 | 依据 |
| --- | --- | --- |
| **张数** | **1** | P1 只有一类设备（轴 1 的"按功能类别分"在 P1 退化为单一类别） |
| **表名** | **`telemetry`** | 取**泛化名**。它把"P1 这一类设备"占住了——**引入第二类设备时，这张表的定位要重新交代**（表名改不了） |
| **列集合** | `ts` + `temperature` / `vibration` / `current`，**全 `FLOAT`** | 三个都是瞬时量（§6.3 的分档规则）；列名即载荷的 `metrics[].key` |
| **标签** | **只 `deviceId`，`VARCHAR(16)`** | §8.7（P1 版） |

### 9.1 实跑复核（3.4.2.8.community，2026-10-09）

| # | 实测 | 结果 | 影响 |
| --- | --- | --- | --- |
| **V1** | 表名 `telemetry` / 列名 `current` 是否保留字 | ✅ **都不是**，DDL 直接通过 | 无需反引号 |
| **V2** | 子表名格式 `{deviceId}_{pointKey}` | ✅ 可建、可写、可查 | §8.2 的格式成立 |
| **V3** | ⭐ **标识符大小写** | **不敏感**：`CREATE TABLE p1.TEST_X` 之后再建 `p1.test_x` 报 **`1539 Table already exists`**；`tbname` 读回来是 **`test_x`**（折成小写） | 见下 |
| **V4** | 标签**值**的大小写 | ✅ **保留**（`'AWEAWQ05E8PF53WH'` 原样返回） | 与标识符的行为不同 |
| **V5** | ⚠️ **无数据的子表** | **不出现在超表的 `SELECT` 里**——建了 `test_x` 但没写数据，超表查询结果里没有它（`SHOW TABLES` 里有） | 建表脚本跑完后，**要列子表得用 `SHOW TABLES` / `ins_tables`**，不能靠超表查询 |

**V3 的两个含义**：

1. ✅ **原先担心的"大小写差异造出两张子表、静默分家"不存在**——TDengine 的标识符根本不分大小写
2. ⚠️ **但全大写是"生成侧"的约定，存储侧是小写** ⇒ **PG 档案里的 `deviceId`（大写）与 TDengine 子表名（小写）不一致**，两边比对前**必须先归一**（统一转小写）。这条要随档案的实现一起落地

**V5 的一条连带**：它不影响"表存在 ⇔ 已注册"这条不变量——那条靠**STMT 在子表不存在时报错**来探测，与查询无关（第 2 项 §6 轴 4）。
