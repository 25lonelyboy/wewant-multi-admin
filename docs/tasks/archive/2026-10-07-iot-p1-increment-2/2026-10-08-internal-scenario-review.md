# 复议：以"工厂内部效率自用"为前提下，前两项决策的问题与遗漏

- **日期**：2026-10-08
- **触发**：决策人提出——"以工厂内部效率提升自用的 IoT 场景为条件，结合业界标准与实践，看我们的决策有没有问题、有没有没考虑到的"
- **范围**：第 1 项（schema）与第 2 项（写入方式）的已定结论；不重开单项讨论
- **处置**：**作为 P2（上真实设备）的启动输入，不在 P1 内实施**——逐条"推到 P2 不会返工"的确认见 §5
- **口径**：**【已核实】**＝一手来源或既有台账条目（出处在附录）｜**【AI 判断】**＝无来源的推论，待验证

---

## 0. 这个前提改变了什么

前两项决策是在**"先打穿链路、再谈场景"**的顺序下做的。把前提明确成"**工厂内部、自用、目标是效率提升**"之后，暴露出三处**前提级**的差异——它们不是细节，是框定问题的方式。

---

## 1. 三个前提级发现

### 发现 1 ⭐ 场景是"效率提升"，但数据模型是"预测性维护"

"工厂内部效率提升"要回答的是四个问题：**做得多快（节拍/产量）、停了多少（可用率）、良了多少（良品率）、耗了多少（能耗）**。

而模拟器当前的三个测点是 —— `temperature` / `vibration` / `current`：

| 类别 | 典型测点 |
| --- | --- |
| **设备健康**（现在采的） | 温度、振动、电流 |
| **效率**（场景要的） | **运行/停机状态、产量计数、良品/不良数、能耗、节拍** |

⇒ **决策本身没定错，但"指标倒推"这一步没有走**——而这正是本项目第 5 讲自己立的原则：**先定指标 → 再定采集 → 再定主数据**。

⚠️ **后果**：schema 已定稿、子表命名规则已冻结、类型分档已定，**但测点集合不是从任何效率指标倒推出来的**。现在改是**最便宜的时候**（还没接真实设备、还没产生历史数据）。

> **一处相关的行业参照**：制造运营 KPI 有国际标准 —— **ISO 22400**（-1 框架与词汇、-2 KPI 定义），它给的不是"随便采点什么"，而是**一组标准指标及其所需数据**。⚠️ 该标准正文付费，本轮只取到第三方转述（见附录），标 🟡。

### 发现 2 ⭐ 我们的架构是"云直连"形态，而工厂内部场景是"边缘连接"形态

**微软官方对两条产品线的分工**（原文，2026-10-08 取）：

> **Azure IoT Hub**：…suited for scenarios where devices **connect directly to the cloud** over standard protocols such as MQTT, AMQP, and HTTP.
>
> **Azure IoT Operations**：…enabling **edge-connected** solutions for **industrial and OT environments**. Azure IoT Operations is Microsoft's **primary recommendation for new edge-connected solutions**.

⭐ **同一家厂商，把"IoT"和"工厂/OT"分成了两个产品，而且工业场景的首选是"边缘连接"那个。**

而我们的架构是：`设备/模拟器 → EMQX → 后端 → TDengine` —— **设备直连平台 broker，没有边缘层**。

**AWS IoT Lens 的设计原则 6**同样给了理由（原文）：

> Edge gateways can be used to mediate data flows between a low latency local-area network (LAN) and … the high-latency wide-area network (WAN), **protocols used in each environment** and can also **mediate between security and administrative domains such as in a Perdue Enterprise Network Architecture (PERA), ANSI/ISA-95 network segmentation**.

⇒ **网关在工厂里不是可选项，它同时承担三件事**：协议桥接、网络分区跨越、管理域跨越。

⭐ **而我们其实已经见过这个形态**——第 1 项定的"**一条报文可能带多个 `pointId`（网关代读多路）**"就是网关存在的证据。**但架构图上没有它。**

### 发现 3 与工厂既有系统的关系没有定义

工厂内部通常**已经有 SCADA / Historian（如 PI、Wonderware）/ MES**。我们的决策里：

- **双库分治（PG + TDengine）是我们内部**的库分工（ADR-009 D2）
- **"我们与既有 MES/SCADA 是什么关系"是平台之间**的边界 —— **从未讨论过**

⚠️ 而这**恰恰是决策人最熟悉的那一层**（金升阳期间他做的正是 MES 侧对接外部 IoT 平台的接口与数据流）。

要回答的不是"选哪个方案"，而是三个问题：**是与既有并列还是作为其数据源？谁的数据权威？联调边界画在哪一段？**

**一处行业参照**：微软把 **Azure Device Registry** 定位成"represents IoT devices and **industrial assets** as standard resources"——即**设备/资产档案是平台的独立标准组件**，与连接方式解耦。这与我们第 1 项把"设备档案"挂到增量 3 是一致的；但**档案里要不要含"与既有系统的对应关系"**，我们没定。

## 2. 逐项复核：哪些决策需要加强

前提变了之后，大部分结论仍然成立——**只有两处需要加强**：

| 决策 | 在"工厂内部自用"前提下 |
| --- | --- |
| 第 1 项 · 轴 1 按功能类别分超表 | ✅ 成立。但**"类型"怎么切应当由效率指标的需求决定**（见发现 1） |
| 第 1 项 · 轴 2 `pointId` 进载荷 | ✅ 成立，**且风险更低**——自用场景下"按采集点做访问控制"的需求基本消失 |
| 第 1 项 · 轴 3 标签（含位置 Type 1） | ⚠️ **要加强**：**效率分析天然按车间/产线/工位分组**，所以**层级维度比原判断更必要**（原判断里位置只是"顺带加"） |
| 第 1 项 · 轴 5 幂等键 | ✅ 不变 |
| 第 2 项 · 轴 2/3 攒批 500 条 / 2 s | ⚠️ **要留意**：端到端 ≈ 2 s + 队列 + 写入，**对"效率看板"够用**；但若要**停机实时判定**，这个延迟要与增量 5 一起看 |
| 第 2 项 · 轴 4 预建 | ✅ **自用场景下更顺**——设备数量可控、有内部台账 |
| 第 2 项 · 轴 9 连接 2~4 条 | ✅ 不变 |
| 第 2 项 · 轴 10 与设备管理核对 | ✅ **自用场景下更容易**——设备清单是内部的、可控的 |

## 3. 没考虑到的方面

### A. 架构层

| # | 缺什么 | 依据 |
| --- | --- | --- |
| **A1** | **边缘 / 网关层**（见发现 2） | 微软平台分工原文；AWS IoT Lens 原则 6 |
| **A2** | **OT/IT 网络分区与边界**——EMQX 与 TDengine 各自放在哪一层？跨不跨边界？ | AWS 原文（ISA-95 network segmentation）；NIST SP 800-82r3 的 OT 分区与单向网关（台账 #55） |
| **A3** | **与既有 SCADA / Historian / MES 的关系**（见发现 3） | —— |

### B. 业务层

| # | 缺什么 | 依据 |
| --- | --- | --- |
| **B1** | **指标倒推没走**（见发现 1） | 本项目第 5 讲；ISO 22400（🟡） |
| **B2** | ⭐ **效率基线缺失**——内部效率项目要证明"提升了多少"，前提是**改造前的数据**。而这类项目最容易在**上了系统之后才发现没有 before 数据** | 【AI 判断】 |
| **B3** | **谁用、用来干什么**（决策卡轴 8"业务倒推"）——目前只到"落库可见" | 决策卡附录 A 轴 8 |

### C. 现场层

| # | 缺什么 | 依据 |
| --- | --- | --- |
| **C1** | **现场落地成本**：接线、施工、工人配合、流程改动。工业 IoT 的失败常在这一层，而不在技术层 | 【AI 判断】 |
| **C2** | **施工/上线的停机窗口**——工厂不会为了装传感器停机 | 【AI 判断】 |
| **C3** | **现场的时间同步条件**——工厂是否有可用的 NTP/PTP？若有，"设备时钟不可信"这条的严重性下降、处置方式也不同 | 【AI 判断，待核实】 |

### D. 合规层

| # | 缺什么 | 依据 |
| --- | --- | --- |
| **D1** | **网络安全等级保护（等保 2.0）**——GB/T 22239-2019 的安全扩展要求**明确覆盖"工业控制系统"**。我们只在 OT 安全处沾边（数据二极管那一条），**没有正面处理"这个系统要不要过等保、按几级"** | 台账 #54（该标准 ✅ 已核实） |
| **D2** | **IEC 62443 的 zones / conduits**——OT 网络分区要按它划，而不是按感觉划 | 台账 #53（✅ 已核实） |
| **D3** | 数据留存与审计的合规倒推（第 4 项会碰） | —— |

⭐ 一条相关原文（AWS IoT Lens 原则 7）：**"industrial IoT requires more thought around reliability, safety and compliance"**——**合规在工业场景是被官方单独点名的**，不是通用条款。

### E. 反过来——"自用"这个前提让几件事变得不必要

这是**正向发现**：原以为要做的一些事，在这个前提下可以**降级**：

| # | 原来列的 | 自用前提下 |
| --- | --- | --- |
| **E1** | 多租户 / 第三方数据隔离（原 B6） | **不必要**——只有内部用户 |
| **E2** | 对外 SLA 与合同口径 | **不必要** |
| **E3** | 极致的带宽/字节优化（如 epoch 毫秒省字节的收益） | **优先级可降**——内网带宽充足 |

## 4. 结论：分三档

### 第一档 · 现在就该补（P1 内，因为**现在改最便宜**）

| # | 补什么 | 为什么现在 |
| --- | --- | --- |
| 1 | **补"指标倒推"**：先明确 P1 要支撑的**第一个效率指标**（哪怕只有一个，例如"设备运行率"），据此**复核测点集合** | 模拟器现在只有三个健康类测点；schema 已定稿但**尚未产生历史数据**，改起来最便宜 |
| 2 | **在架构图上补出边缘/网关层的位置** | P1 可以是"设备直连"的简化，但**必须写明这是简化、现场是网关代读**——否则它会变成一处没人知道的分歧 |

### 第二档 · 挂触发点（不要现在做，但要登记）

| # | 项 | 触发点 |
| --- | --- | --- |
| 3 | **OT/IT 网络分区**（EMQX 与 TDengine 各在哪一层） | 真实部署时 |
| 4 | **与既有系统的关系**（并列 / 数据源 / 权威） | 接入第一个真实工厂时 |
| 5 | **等保 2.0 定级与合规评审** | 系统投产前 |
| 6 | ⭐ **效率基线**（改造前数据） | ⚠️ **接入第一个真实产线之前**——见下 |

⭐ **第 6 条的触发点有"时序要求"**：它**不能等到上系统时才想起来**，因为那时"改造前"已经过去了。**基线必须在改造之前采**——这是一条**越晚越无法补救**的项，所以它虽然属"将来"，但**现在就要记在显眼处**。

### 第三档 · 可以降级

第 3 节 E 组三项（多租户隔离 / 对外 SLA / 极致带宽优化）——**在"工厂内部自用"前提下不必要**。

## 5. 处置：本复议作为 **P2 启动输入**，不在 P1 内实施

**处置决定（2026-10-08）**：本节结论**留到 P2（上真实设备）时处置**。P1 阶段只做"**提前看见**"，不实施。

### 5.1 逐条确认"推到 P2 不会返工"

| 项 | 为什么不会返工 |
| --- | --- |
| **发现 1（测点集合）** | **加列是元数据操作**（第 1 项实测，20 万行 vs 1000 行同为 ~5 ms）⇒ 测点集合是**可扩的**，不锁死。**主键、子表命名、类型分档都与测点集合无关**，所以它们先定不影响 |
| **发现 2（边缘层）** | 属**架构层**——P2 加网关**不改 schema、不改写入方式** |
| **发现 3（与既有系统）** | P2 才可能有真实工厂与既有系统 |
| **A 架构 / C 现场** | P2 或更后 |
| **D 合规** | 定级会**影响部署形态**，但改部署形态**不返工数据模型** |

⇒ **除下一条外，推到 P2 不会造成返工。**

### 5.2 ⚠️ 唯一例外——且它有时间要求

> ⭐ **效率基线（§3 B2）**：它**也可以在 P2 做**，但**必须排在 P2 的第一步**。
>
> 理由：基线要在"**改造之前**"采，**一旦改造发生就无法补救**——这是本复议里**唯一"越晚越无法补救"**的一条。

### 5.3 P2 启动时的读取顺序

| 序 | 做什么 | 对应 |
| --- | --- | --- |
| **第 0 步** | ⭐ **先采效率基线**（改造前的产量/停机/良率/能耗） | §3 B2 |
| 1 | 定**测点集合**（从效率指标倒推） | §1 发现 1 |
| 2 | 定**边缘 / 网关形态** | §1 发现 2 |
| 3 | 定**与既有 SCADA / Historian / MES 的边界** | §1 发现 3 |
| 4 | **合规定级与网络分区**（等保 / IEC 62443） | §3 D |
| 5 | 现场落地与停机窗口 | §3 C |

⭐ **本复议的另一个用途**：它同时是"**P1 离真实生产还差什么**"的答案——这正是 P1 目标里"**公开证据链**"的一部分，不是一份到此为止的过程材料。
