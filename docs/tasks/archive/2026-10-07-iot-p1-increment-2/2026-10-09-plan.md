## Task 2 `device-registry` 独立包：设备档案 + 映射

决策 1 §8.1 定的模型 C：**子表名里的两段都由平台生成**，设备只报一个"自己稳定"的本地编号。

- ⭐ **新包 `packages/device-registry`**——装**运行期数据**，不装契约
- ⭐ **为什么独立**：模拟器与 pure-web **都不依赖它** ⇒ C7 由**依赖边界**保证（放进 `contracts` 会让模拟器与前端都拿得到平台侧标识）
- 两个映射：`localDeviceId → deviceId`、`(localDeviceId, localPointId) → pointKey`
- 取值规则（决策 1 §8.2 / §8.3）：`deviceId` 16 位全大写随机串、`pointKey` 3 位递增补零、分隔符 `_`；P1 全部登记为**单点设备** ⇒ `localPointId` 缺省 `001`
- ⚠️ **三条配套规则要落进代码**：① `pointKey` **只增不复用**；② 缺省 `001` **只对登记为单点的设备**生效，多点设备漏 `pointId` ⇒ **拒绝 + 告警**；③ `localPointId` 超长**拒绝，不截断**
- ⚠️ **归一化**：TDengine 标识符折小写、**标签值保留原样** ⇒ 两边比对前**先统一转小写**（决策 1 §9.1 V3）
- ⭐ **暴露给消费方的只有接口**（查映射 / 已登记判定），数据是可替换的实现细节 ⇒ 增量 3 换成读设备档案时**不动消费方**（backlog 已记）
- ⚠️ **`deviceId` 必须是固定值**，不能每次生成——§8.5 定了"映射一旦有数据就冻结"，随机重生成会让旧子表对不上 ⇒ **数据分家**
- ⭐ **模拟器不读档案**（C7）——它按 T1 的**同一个约定函数**生成 `sim-%03d`
- **消费方**：worker 的消费者（缓存判定）+ 建表脚本（枚举子表名）
- ⚠️ **万级设备下逐条查档不成立** ⇒ 消费方要**本地缓存 + 失效**（决策 2 §6 轴 10）
- **验收**：单测覆盖两个映射、缺省规则、超长拒绝、归一化

## Task 3 TDengine 建库 / 建表 / 建降采样子表脚本

- **形态**：可重复执行（`IF NOT EXISTS`；并清理遗留的降采样流）；接一个 `pnpm ops:tdengine-init`；**不进应用启动路径**（C3）；由 `ops:env-up` 串上（与 `migrate` / `seed` 同形）
- ⭐ **脚本落在 worker 应用里**（它要读 `device-registry`），根 `package.json` 只做转发——与探针脚本同样的处置

- **超表** `telemetry`：`ts` + 每测点「值 + `_unit`」；`TAGS (deviceId VARCHAR(16))`（决策 1 §9，DDL 已实跑复核）
- **子表**：按档案枚举，`{deviceId}_{pointKey}`，`USING telemetry TAGS ('<deviceId>')`
- **降采样库** `wewant_iot_ds`：`PRECISION 'ms' KEEP 3650 DURATION 10`
- **三张表** `telemetry_1m / _1h / _1d`：16 列同形；`ALTER STABLE telemetry_1m KEEP 1095`（全案唯一的超表级 `KEEP`）
- **降采样子表**：按同一份档案枚举，`{deviceId}_{pointKey}_{level}`，`USING telemetry_<level> TAGS ('<deviceId>')`。⚠️ **不用 TDengine 流**——降采样改由 worker 进程内定时重算（选型与依据见 [降采样设计](2026-10-12-downsample-design.md)）
- **时区**：`Asia/Shanghai` 设在服务器 / 集群级，并写进 `taos.cfg`（窗口对齐取服务器时区，配错不报错只会把数据分进错的窗口）
- **验收**：空库跑一遍、再跑一遍都不报错；`SHOW TABLES` 见全部子表（⚠️ 无数据的子表不出现在超表 `SELECT` 里，列子表要用 `SHOW TABLES`）；写入一条后超表 `SELECT` 可见

## Task 4 队列层

- 依赖 **`bullmq`**（MIT）——⭐ **进 catalog**：生产者（server）与消费者（worker）**两个 workspace 消费**，满足判据第 1 条（消费者从 server 内独立成应用之后，这条才成立）
- 队列名 **`iot-telemetry-ingest`**（⚠️ BullMQ 用 `:` 作 Redis 键分隔符，队列名含冒号构造即抛）；它是**跨应用共享常量** ⇒ 与 T1 的主题常量同处（C9）
- **两类连接配置不同**：Queue（生产者）**快速失败** + `enableOfflineQueue: false`；Worker（消费者）**无限等待** + `maxRetriesPerRequest: null`
- ⭐ **BullMQ 用连接参数（由 `QUEUE_REDIS_URL` 得来），不复用 `REDIS_CLIENT`**——BullMQ 要自己管连接（Worker 侧有阻塞命令），共享一个 ioredis 实例是踩坑做法
- **保留策略**：`removeOnComplete: true`（或只留一小批）；`removeOnFail: { count: 5000 }`——⭐ **failed 集合就是"待人工看"的那个队列**（决策 2 §9 的 B 类处置）
- **重试**：`{ attempts: 5, backoff: { type: 'exponential', delay: 200, jitter: 0.5 } }`——⚠️ **BullMQ 默认不重试、默认不退避、抖动默认 0**，三样都要显式配
- ⚠️ 现有 `REDIS_CLIENT` 的注释写着"`maxRetriesPerRequest: null` 为官方推荐（BullMQ 前瞻）"——本条落地后这句指错了对象，顺手修
- **验收**：单测覆盖两类连接配置的差异；顺带实测确认 `attempts` 的实际计数口径（决策 2 §8 第 12 项）

## Task 5 订阅端改造

决策 3 §9 定的"能力最大化"——⭐ **我们只能控制订阅端**（投递 QoS ＝ min(发布, 订阅)，订阅端设的是上限、只能降级）：

| # | 项 | 值 |
| --- | --- | --- |
| 1 | 订阅请求 | `{ qos: 1 }` |
| 2 | 会话 | `clean: false` + `properties.sessionExpiryInterval > 0` |
| 3 | ⭐ `clientId` **固定** | 现状是 `nestjs-server-${pid}` ⇒ 每次重启换一个会话，前两条全白搭 |

- ⚠️ **`clientId` 要可配（env 覆盖）**。固定之后有两个副作用：① 同一台机器上 `pnpm dev:server` 与 e2e 会**互踢**；② 持久会话会让 e2e 连接时**收到上一轮的积压报文**，"干净起点"类断言不再成立 ⇒ e2e 必须能用独立 clientId + 干净会话跑
- ⭐ **简单解析**：只取 `localDeviceId`，不做完整校验（完整解析/校验/计数在消费者）——它同时服务两件事：`seenDevices`、身份校验
- ⭐ **身份校验（C8）**：**主题段 ≠ 载荷 `localDeviceId` ⇒ 丢弃 + 计数 + 告警**。理由：主题是**路由与将来 ACL 的授权单位**，而身份以载荷为准 ⇒ 不拦的话，一个已授权设备可以在**自己的主题**上发别人的编号，数据落进**别人的子表**
- ⚠️ **"丢弃"分两类，归属不同**：**`JSON.parse` 失败 ⇒ 原样入队**，由消费者计数（缓冲层 §3.1 不变）；**身份不一致 ⇒ 订阅端丢弃**
- **入队在解析之前**：job 里放**原始载荷**（信封**不带主题**——贴近生产的环境下主题不参与身份判定，不依赖它的可用性）
- **Redis 挂时落本地**（缓冲层 §3.2）：落原始载荷、FIFO、⭐ **投成功才删本地文件**、目录**可配**（compose 已挂卷，见 T0）、**有上限**、写本地失败要告警
  - **上限值**：按"能装下最长可接受停机"估（**AI 判断**——实施时按实测写入速率定）
  - ⭐ **超限处置：停订阅 + 告警**——不静默丢数据；代价是这一段**完全断流**，且会反压设备侧
  - ⚠️ 这个进程**同时是 API 进程** ⇒ 磁盘满会**连 API 的日志一起写不了**（缓冲层 §3.2 第 4 条点出的失败模式）
- **`seenDevices` 留在订阅端**——增量 4 再定是否迁移；在线状态是瞬时数据，后续迁移不影响历史。每秒汇总日志改为「入队 N 条 / 身份不一致 M 条」
- ⚠️ **连带**：`clientId` 固定 ⇒ 多实例互踢 ⇒ 横向扩要用共享订阅 `$share/<group>/wewant/devices/+/telemetry`（EMQX 对 3.1.1 也支持；**P1 单实例用不上，记下**）
- ⚠️ **连带**：持久会话重连会灌一波积压——BullMQ 正好吸收它，不用额外做
- **验收**：报文进队列；停掉 `redis-queue` 后可见落本地日志；恢复后按序补投；**主题/载荷不一致的报文被拦且有告警**

## Task 6 worker：独立应用 + 消费者

- ⭐ **形态**：**`apps/` 下的新应用**，**不用 Nest、不开 HTTP**，部署为**独立进程 / 独立 compose 服务**
  - 拿到的三个性质：**可独立启停**（重启消费者不重启 HTTP）/ **可多实例** / **可独立扩缩**
  - ⚠️ **参照物是 `nestjs-server` 而不是 `iot-simulator`**：模拟器是本地工具，"tsx 能跑"就够；worker 是**要进镜像的生产进程** ⇒ 有构建产物、镜像里跑产物
- **自带**：`package.json` / `tsconfig` / eslint 薄壳（一行引用 `internal/*`）/ 自己的 env schema（zod）/ 日志 / 优雅停机（`SIGINT` / `SIGTERM` + `worker.close()`）
- **依赖**：`bullmq`（catalog）/ `@tdengine/websocket`（catalog）/ `@multi-admin/device-registry` / `@multi-admin/contracts`
  - ⭐ **`@tdengine/websocket` 随之进 catalog**：平台端后续阶段要查 TDengine（实时监控 / 看板）⇒ 它是 **nestjs-server 与 worker 两个 workspace 的消费者**，满足判据第 1 条。本条落地时把它从应用本地的精确 pin 上提成 catalog 条目——⚠️ **保持 pinned，不加 `^`**（AGENTS.md：catalog 中刻意 pin 的包保持 pinned）
- **Dockerfile 自己写**：**无 `migrate` / `seed`**；构建以仓库根为 context（硬规则）；文件登记进 `check-digests.sh` 的 `FILES`（T0）
- **链路**：解析 → 检测 → 攒批 → STMT 写入
  - **检测**（决策 1 §6.6 清单 + 决策 2 §6 轴 10 的切法）
    - **同步判定**（不需外部信息）：格式 / 字段完整性 / 值域 / **指标是否在超表列集合内**
    - **缓存判定**（需要档案）：设备与采集点存在性——档案来自 `device-registry`（T2）
    - **批内重复 `(子表, ts)`**——本套 schema 的头号失败模式；⭐ 它同时是 `affectRows` 核对的前提（不去重会把"覆盖"误报成"部分失败"）
  - **未知测点**：**丢弃 + 计数 + 告警**——⚠️ 告警**必须带上报的那个 `key`**，否则人只知道"有未知测点"，不知道多了什么
  - **攒批**：条数 500 或 2 s，先到先 flush；单次 bind/exec 硬上限 **32767 行**
  - **写入**：参数绑定 STMT，⭐ **刻意走不带 `USING` 的形态**——带 `USING` 会在子表不存在时**静默建表**，顶掉"表存在 ⇔ 已注册"这条不变量；写具体子表名 ⇒ **每个子表一条语句**（一次 exec 覆盖整批只在 `USING` / `tbname` 形态下成立，见决策 2 §10 N2 / §9 选定）
  - **核对**：`getLastAffected()`——⚠️ 在 STMT1 路径上返回 **`number`**（BigInt 形态属 STMT2 路径，见决策 2 §10 N8）
  - **ack**：⭐ **入库成功 → 再 ack**；ack 粒度＝**整批**（`affectRows` 不给行级定位）。⚠️ 写入层**不另造重试**——失败直接抛回队列，数据全程在 Redis
  - **失败分类**：A 类（可重试）走队列重试；B 类（重试无意义）耗尽后进 failed 集合 + 人工。⚠️ `Table does not exist` 的告警级别**高于其它 B 类**——正常路径下它不该出现，一旦出现就是**平台侧自己错了**
  - ⚠️ **非法绑定与"连接已废"要分开处理**（决策 2 §10 N9）——实测 STMT1 上非法绑定后连接仍健康，但连接级错误（`108` / `104`）仍要作废那**一条**连接
- ⚠️ **P1 不用 sandboxed processor**（**AI 判断**）：官方给它是缓解 CPU 密集处理器阻塞事件循环，P1 单机不是这个场景；触发点＝出现 `Stalled` 日志
- **验收**：数据落库；**强杀消费者 → 重启不丢**（判据 3）
