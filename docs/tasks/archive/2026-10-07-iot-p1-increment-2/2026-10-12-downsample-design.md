## 1. 依据：为什么不再用流

全部本机实跑（脚本见 `/tmp/repro3.sh`、`/tmp/matrix*.sh`）：

| # | 实测 |
| --- | --- |
| 1 | 现形态（`PERIOD` + 流级 `PARTITION BY tbname, deviceId` + 内层 `PARTITION BY tbname INTERVAL`）**每个窗口只产 1 行**，值是**最后写入那个分区**的，且**被复制到全部输出子表**。100 台设备时表现为"每个窗口 100 行、值全同" |
| 2 | 去掉内层 `PARTITION BY` ⇒ 变成**全表聚合**，同样复制给全部子表（本机实测：单台真值 202 行 / 值 ~12500，落库却是 20234 / 1254819） |
| 3 | 官方文档要求的**窗口触发** `INTERVAL(1m)`（作触发类型）在 3.4.2.8 报 `9728 syntax error` |
| 4 | 官方最佳实践的**内层子句顺序**（`INTERVAL(...)` 在前、`PARTITION BY` 在后）报 `9728` |
| 5 | `OUTPUT_SUBTABLE(...)` 报 `9728`；无流级分区时 `TAGS` 报 `16661`；流级只有 `tbname` 时 `TAGS` 报 `16660`；完全不写 `TAGS` 报「tag name mismatch」 |
| 6 | **同一条 `SELECT tbname, _wstart, SUM(...) FROM <超表> PARTITION BY tbname INTERVAL(...)` 单独跑完全正确**（按子表分组、各值不同）⇒ 问题在流，不在查询 |
| 7 | 最新社区版镜像就是 **3.4.2.8**（`latest` 与它 digest 相同、`docker pull` 报 `Image is up to date`；`3.4.3.0` 报 `manifest unknown`；官方版本号规则里新功能走 `Feature` 位，当前 `Feature = 2`）⇒ **没有可升级的目标** |

⭐ 第 6 条是转折点：**读侧的形状是好的**，坏的只是"流"这个执行者。把执行者从"数据库的流"换成"我们自己的定时循环"，第 1～5 条全部不成立。

## 2. 选定

```text
谁算        worker 进程内的一个降采样环（与消费环并列），**不用流**
触发        BullMQ Job Scheduler（复用队列 Redis），★ 每级一个调度
窗口        最近 K 个**已闭合**窗口，K = 3（可配）——**每次都重算这一段**
读          一条普通查询：WHERE 范围 + PARTITION BY tbname + INTERVAL(<窗口>)
写          复用参数绑定 STMT（不带 USING），子表 = {deviceId}_{pointKey}_{level}（折小写，级别进名）
幂等        (子表, ts) 覆盖 —— 与原始库同一条不变量
三级        平级：三条调度**各自从原始超表算**，互不依赖
```

## 3. 机制

### 3.1 触发：BullMQ Job Scheduler

| 级 | 调度 | 窗口 | 说明 |
| --- | --- | --- | --- |
| `1m` | `every: 60_000` | `INTERVAL(1m)` | |
| `1h` | `every: 3_600_000` | `INTERVAL(1h)` | |
| `1d` | `pattern: '0 8 * * *'` | `INTERVAL(1d, 8h)` | 业务日从早 8 点（§11 定的 offset） |

| 项 | 值 | 理由 |
| --- | --- | --- |
| 队列名 | **`iot-telemetry-downsample`** | ⚠️ **不能带冒号**——BullMQ 的队列名含冒号会直接抛（增量 2 实测；现有 ingest 队列同理取名 `iot-telemetry-ingest`） |
| 调度 id | `ds-1m` / `ds-1h` / `ds-1d` | 同为避免冒号 |
| 保留 | `removeOnComplete: true`、`removeOnFail: { count: 5000 }` | 与 ingest 队列同一口径 |
| worker 并发 | **1** | 同一级同时只跑一个；调度本身按 `(调度id, 下一次触发时刻)` 派生**确定性 jobId**（【已核实】：`bullmq@6.3.12` `job-scheduler.js` 的 `getSchedulerNextJobId` + Lua 原子添加）⇒ 多实例部署下同一时刻只有一个 worker 取到 |

⭐ **多实例安全不依赖上面那条判断**：即使两个实例同时算同一段，`(子表, ts)` 覆盖保证结果**照样正确**——调度只买效率与可观测性（失败重试、failed 集合），不买正确性。

### 3.2 算哪些窗口

每次只依赖"墙上时钟"，**不记游标**：

```text
W      = 该级的窗口长度
endMs  = 最后一个**已闭合**窗口的右边界（epoch ms）
startMs= 覆盖最近 K 个窗口的左边界（epoch ms）
```

- **闭合**：右边界 ≤ now ⇒ 不会写出"半截窗口"
- **K = 3**：一个窗口被重算 3 次；⭐ 这就是**补传与停机的自愈机制**——晚到的数据只要落在最近 K 个窗口内，下一轮就会被算进去
- 多算出来的窗口由下一轮覆盖，幂等无害

### 3.3 读（本机实测通过）

```sql
SELECT tbname,
       _wstart                                              AS ts,
       SUM(temperature)  AS sum_temperature,
       COUNT(temperature) AS count_temperature,
       MIN(temperature)  AS min_temperature,
       MAX(temperature)  AS max_temperature,
       LAST(temperature_unit) AS temperature_unit,
       …（vibration / current 同形）
  FROM wewant_iot.telemetry
 WHERE ts >= :startMs AND ts < :endMs
 PARTITION BY tbname
 INTERVAL(1m)
```

⚠️ **两条实现硬要求**（均实测）：

1. ⭐ **时间边界一律用 `epoch 毫秒` 传，不用字符串**。同一范围写成 `'2026-10-12 14:32:00'` 会被按**服务器时区**解释、直接查空（实测返回 0 行，而 epoch 毫秒返回 8 行）。用毫秒 ⇒ 边界无歧义，**时区只影响 `INTERVAL` 的窗口划分**（而那是我们想要它影响的）。
2. ⭐ **`COUNT(<metric>)` 不是 `COUNT(*)`** —— 窗口内某测点缺值时，`sum/count` 还原出的均值才是对的（§14.2 已定）。

### 3.4 写

- **形态**：与原始库同一套——**预建子表 + 参数绑定 STMT + 不带 `USING`**。理由是同样那条不变量：`USING` 会在子表不存在时**静默建表**，顶掉"表存在 ⇔ 已注册"（决策 2 §10 N3）
- **子表名**：⭐ **`{deviceId}_{pointKey}_{level}`**（`{deviceId}_{pointKey}` 折小写即原始库子表名；**级别进名**——三张超表同库、TDengine 子表名库内唯一，同名子表只能挂一张超表）。命名一处定义，建表端与写入端复用
- **单位列**：取窗口内**最后一次**上报的单位（`LAST(<metric>_unit)`）——与决策 1 §4.6"归档层自描述、随数据冻结"一致
- 建表脚本要**同时建降采样子表**。

### 3.5 顺序与并发

- **三级互不依赖**（都读原始表）⇒ 顺序无关、可并行、可各自重试
- 消费环与降采样环共处一个进程、**两条独立队列**；任一条失败不影响另一条

## 4. 为什么不是链式（1h 读 1m、1d 读 1h）

链式能省扫描（§13.4 的那条理由），但**它要求补传自下而上传导**：补传改了某个 1m 窗口 ⇒ 包含它的 1h 窗口必须跟着重算，否则 **1h 会永久继承那个陈旧的 1m 值**。而"哪些窗口变了"要么记水位、要么做对账——**这是新引入的状态与新的失败模式**。

平级把这些代价换成"扫描量"，而扫描量在 P1 规模下是廉价的（见 §6）。**链条留到触发点**（§8）。

## 5. 与决策 4 §14 的关系：schema 一字不改

| §14 定的 | 本设计 |
| --- | --- |
| 独立库 `wewant_iot_ds`，`KEEP 3650 DURATION 10` | 不动 |
| 三张超表 `telemetry_1m/_1h/_1d`，16 列同形 | 不动 |
| 每测点 `sum`(DOUBLE) / `count`(BIGINT) / `min`(FLOAT) / `max`(FLOAT) + `<metric>_unit`(VARCHAR(16)) | 不动 |
| `ALTER STABLE telemetry_1m KEEP 1095`（全案唯一的超表级 KEEP） | 不动 |
| `TAGS (deviceId VARCHAR(16))` | 不动 |

⭐ **那四个可再聚合量本来就是为"应用层也能算"准备的**——`sum/count` 能还原任意粒度的 `avg`、`min/max` 可再聚合。本设计正是兑现它。

**唯一被取代的是 §14.3 的建流语句**（三条 `CREATE STREAM`）与 §11 选定里的「路径：流计算 `CREATE STREAM`」一行。

## 6. 代价陈述

| # | 失败模式 | 什么时候会咬人 |
| --- | --- | --- |
| 1 | **扫描量与设备数成正比**：1h 每小时扫 K 小时原始、1d 每天扫 K 天原始 | 原始库单表扫描进入分钟级时 |
| 2 | **重复写是常态**（K 倍） | 规模上来后第一个要重估的参数 |
| 3 | ⚠️ **窗口对齐 / 时区 / 业务日 offset 全要自己写对**——数据库不再替我们算 | 第一次改窗口或改时区 |
| 4 | **worker 新增"读 + 聚合"的能力面**（原先只写） | 连接与会话数要重算（读连接与写连接分开） |
| 5 | ⚠️ **多算出的"半截窗口"**若闭合判断写错，会写出不完整的聚合 | 实现时忘记排除未闭合窗口 |
| 6 | **降采样与消费争同一进程的资源** | 消费延迟进入秒级时 |
| 7 | ⚠️ **判据②从"数据库保证"变成"我们自己保证"** | 验收与排障时——原先"流在跑"是个可观测状态，现在要自己看 |

## 7. 退出成本

| 换什么 | 代价 |
| --- | --- |
| `K` 的取值 | **零**——可配项 |
| 触发方式（BullMQ 调度 → 进程内定时器） | **低**——换一层薄壳 |
| **平级 → 链式** | **中**——要加"补传传导"（水位或对账），是一次独立设计 |
| 换窗口长度 / offset | **低**（改配置），⚠️ 但**历史窗口边界不同 ⇒ 既有聚合行作废**，要清表重算 |
| **回到"用流"** | **要看 TDengine 版本**——判据：新版能否通过本文件的 §1 最小复现（§8 触发点） |

## 8. 触发点

| 触发 | 回头改什么 |
| --- | --- |
| **原始库单表扫描进入分钟级** | 平级 → 链式（并补上传导机制）；或缩短 `K` |
| **消费延迟进入秒级** | 降采样拆成**第三个独立入口**（与 worker 分开扩缩） |
| ⭐ **TDengine 发布带窗口触发的版本** | 重估是否回到流。**判据不是"版本号够了"，是"新版能通过 §1 的最小复现"** |
| **窗口/时区/业务日规则变化** | 清空降采样库重算；⚠️ 原始数据只在线 3 年，重算窗口受它封顶（§13.3 同一条边界） |
| 降采样库体积成本成为问题 | 重估分钟级 3 年 / 小时·天 10 年（§11 原触发点不变） |

## 9. 判据与验收（改写）

⭐ 原判据②是「**降采样在跑 ＝ 输出表存在且有数据**」——**它挡不住本次这个错误**：真实那批数据在 1m 表里有 1400 行、表也在，却是错的。改成：

> **判据②（改写）**：降采样结果**逐条对账**——对每个 `(子表, 窗口)`，`telemetry_1m` 的 `sum/count/min/max` 与**原始表同子表同窗口**的聚合**逐字段相等**；三条输出表都存在且非空。

- 对账本身可以就是一个脚本：把 §3.3 的查询跑一遍，与降采样表 `JOIN` 比字段
- 落点为 `apps/iot-worker/scripts/downsample-verify.ts`：`pnpm --filter @multi-admin/iot-worker run downsample:verify`；窗口口径复用环的 `window.ts`/`query.ts`（不自算，免得在日级业务日或对齐边缘与环"算一段、比另一段"）。默认**跳过最新一个已闭合窗口**（环按周期触发，最新窗口闭合到下一位 tick 之间可能尚未重算）、比对 `K-1` 个窗口；`K` 之内的差异是真缺陷，`K` 之外可能是晚到数据造成的良性陈旧，脚本不据此判失败。见 [build-and-verify.md](../../../engineering/build-and-verify.md) 的 iot-worker 段。
- ⚠️ 上面那条「单条 `JOIN`」本机**不可行**：**外层套窗口聚合**的 join 报 `9828 Not supported join since 'Join requires valid time series input and primary timestamp equal condition'`（3.4.2.8.community 实测）。约束在**形状**不在库位置——TDengine 要求 join 两侧都是合法时序输入、主时间戳在等值条件里，而**聚合 / 窗口子查询不是这样的输入**（实测：纯子查询 ⋈ 同库超表、两张基础超表跨库 `on ts=` 均 `code 0`；聚合子查询 ⋈ 降采样表、子查询 ⋈ 子查询、`PARTITION BY tbname INTERVAL(1m)` 子查询 ⋈ 超表均报同一条 `9828`）。改走**两条独立读 + 发现差异时重读两侧再比**：只有重读后仍存的差异才报，排除「两次读之间发生一次写入」的假警报。前提是**管道相对静止**；活数据持续到达时，晚到数据造成的差异在环下一轮重算 + 下次对账后消失。
- ⚠️ `COUNT(DISTINCT x)` 在 TDengine 里**不可信**（实测：真值 1 却返回 100）——对账脚本里**不要用它**，用 `GROUP BY` 或直接逐行比
